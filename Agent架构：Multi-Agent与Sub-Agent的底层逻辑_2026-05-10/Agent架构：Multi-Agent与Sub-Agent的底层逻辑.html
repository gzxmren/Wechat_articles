Agent架构：Multi-Agent与Sub-Agent的底层逻辑

 


在折腾AI Agent开发的朋友，大概率都会撞上同一个选择困难症：到底是该搞几个长期驻守的Agent各司其职，还是守着一个大脑袋，遇到事儿再临时拉几个Sub-Agent去跑腿？

这不仅仅是起个名字那么简单。选错了路，后面就是无尽的配置。

别被名字骗了：这是招人和派活的区别

很多人一看Multi-Agent（多智能体）和Sub-Agent（子智能体），觉得不就是多个Agent和一个Agent带几个小弟的区别吗？

大错特错。

这俩货在底层设计上完全是两个物种。我用一个最通俗的职场比喻来说明：

  • • Multi-Agent 是搭建部门架构。 你在招正式员工。每个Agent都是一个独立的个体，有自己的工位、自己的电脑、自己的权限卡，甚至有自己的性格。他们长期存在，各管一摊事儿。
  • • 主Agent + Sub-Agent 是项目经理派活。 主Agent是项目经理，Sub-Agent就是他临时抓来的壮丁或者外包团队。活干完了，Sub-Agent就解散了，不需要长期养着。

简单来说
Multi-Agent 解决的是谁来接这个入口的消息，是路由和隔离问题；
Sub-Agent 解决的是这活儿太重怎么拆着干，是任务并行和分解问题。

把这个逻辑理顺了，后面的架构图就好画了。

Multi-Agent：一群各怀绝技的正式工

在OpenClaw的定义里，一个Agent绝不是简单的一句Prompt，它是一个全功能的大脑。

官方文档里写得明明白白，一个合格的Agent必须拥有独立的地盘：

  • • Workspace（工作区）： 它的私人文件夹，别人动不了。
  • • Auth Profiles（权限卡）： 它有自己的账号密码，不用跟别人混用。
  • • Persona/Soul（人设）： 它是高冷的程序员还是热情的客服，各有一套。

所以，搭建Multi-Agent系统，本质上是在建隔离。

1. 总机的逻辑：Routing

这时候肯定有人要问：这么多Agent，谁来接电话？

这就是Routing（路由）的作用。你可以把OpenClaw想象成一个公司的前台总机。消息一来，它先不急着回话，而是先看一眼：这消息是从哪来的？谁发的？发到哪个群了？

  • • 按渠道分流： 飞书来的消息，转给文档Agent；Discord来的，转给运营Agent。
  • • 按群组分流： 技术交流群的消息给Agent A，摸鱼吹水群的消息给Agent B。
  • • 规则铁律： 这里的规则是谁最具体谁赢。比如你既设了所有飞书消息给A，又设了飞书某个群给B，那这个群的消息肯定走B。这叫确定性路由，别指望AI能在这儿给你搞什么随机应变，稳定压倒一切。

2. 什么时候必须上Multi-Agent？

如果你遇到以下场景，别犹豫，直接上多Agent：

  • • 角色必须分裂： 你既要它写代码，又要它写情书，还要它做客服。别折磨一个脑子了，拆开吧。
  • • 权限必须隔离： 运维Agent能删库，写作Agent只能写文档。这俩必须分开，否则哪天写作Agent幻觉一起，把数据库给删了，你哭都没地儿哭。
  • • 入口天然不同： 你同时运营好几个号、好几个群，每个群的调性都不一样。

代价也是显而易见的： 你得像管人一样管它们。配置多、维护累，要是拆得太细，你自己都记不住谁是谁。

三、Sub-Agent：项目经理的分身之术

再来看主Agent + Sub-Agent这套模式。

Sub-Agent在OpenClaw里，被定义为Delegated run（委派运行）。

这就像你是一个项目经理（主Agent），手里接到一个巨大的任务：写一份年度报告。
你一个人干会累死，于是你把任务拆了：

  • • 小A（Sub-Agent 1），你去搜集数据。
  • • 小B（Sub-Agent 2），你去整理大纲。
  • • 小C（Sub-Agent 3），你去校对错别字。

等他们干完活，把结果汇报给你，你汇总一下，这事儿就结了。小A、小B、小C随后就消失了，不需要长期占着工位。

1. 为什么非要搞Sub-Agent？

我之前也纠结过：一个Agent全包了不行吗？

实操下来发现，真不行。这就好比让一个人一边查资料、一边写文章、一边还要自己审核。结果往往是：

  • • 上下文乱成一锅粥： 查资料的垃圾信息污染了写作逻辑，写着写着就跑偏了。
  • • 效率极低： 所有事串行做，慢得要死。
  • • 很难局部重做： 发现数据错了，想让AI只重查数据，别动文章，一个Agent根本做不到。

用了Sub-Agent，就是专人专事。查资料的只管查，不管写；审核的只管挑刺，不管改。主Agent保持清爽，只负责调度和汇总。

2. Sub-Agent的软肋

这套模式也有局限。Sub-Agent毕竟是临时工，它没有长期记忆，也没有独立身份。你不能指望它记住上次那个客户喜欢什么风格，也不能给它发独立的门禁卡。如果你需要长期维护某个角色的稳定性，Sub-Agent就不是好选择。

四、别做选择题，做混合双打

既然这两种模式各有优劣，那能不能结合？

当然能，而且这是最强打法。

我建议采用长期层 + 执行层的架构：

第一层：长期层（Multi-Agent）

养几个核心的正式工，负责长期驻守：

  • • Main Agent： 总控，也是默认入口，负责接待和分发。
  • • Writer Agent： 专门负责内容创作，有自己的知识库和文风设定。
  • • Ops Agent： 专门负责运维，掌握着服务器的生杀大权。

第二层：执行层（Sub-Agent）

在Writer Agent内部，当遇到复杂任务时，它自己召唤Sub-Agent：

  • • Writer Agent 接到任务：写一篇关于AI架构的深度长文。
  • • 它内部启动 Sub-Agent A 去联网搜素材。
  • • 启动 Sub-Agent B 去本地库里翻旧文档。
  • • 最后 Writer Agent 自己动笔写，写完让 Sub-Agent C 做个校对。

这比单纯的多Agent更灵活，又比单纯的主+Sub更稳定。

五、实操指南

最后，分享几个我踩过的坑。

坑一：Workspace不是沙箱

Workspace只是默认工作目录，不是安全沙箱。别以为分了Workspace就万事大吉，真要做权限隔离，得看Sandbox配置。别让不靠谱的Agent把你系统文件删了。

坑二：一上来就微服务化

很多人刚学会Multi-Agent，恨不得把写标题、写正文、写标点都拆成三个Agent。千万别作死。

正确的路线应该是：

  1. 1. 先用主Agent跑通流程。
  2. 2. 遇到重活、累活，先试着用Sub-Agent拆解。
  3. 3. 只有当某类任务（比如运维、写作）非常稳定且需要独立权限时，再把它升级为独立的长期Agent。

少即是多，简单才是王道。
