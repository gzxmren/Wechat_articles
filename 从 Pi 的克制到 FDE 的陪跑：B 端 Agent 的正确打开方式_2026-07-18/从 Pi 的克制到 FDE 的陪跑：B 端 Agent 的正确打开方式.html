从 Pi 的克制到 FDE 的陪跑：B 端 Agent 的正确打开方式

2026 年，一个叫 Pi 的开源 Coding Agent 项目突然火了——GitHub 70,000+ Star，多次登顶 Trending 榜首，MiniMax 旗下 Code 2.0 桌面端基于它重构底层架构，Flask 作者 Armin Ronacher 专门撰文称赞并收购了它。

为什么一个 Coding Agent 能掀起这么大的浪？

原因很简单：它把「做减法」干到了极致。

第一代 AI Coding Agent——Devin、早期 Cline——走的是「大包大揽」路线：自动规划、多 Agent 协同、后台持续运行。敲下第一个字之前，系统提示词就烧掉了 7,000 到 10,000 个 Token。功能越堆越多，成本越来越高，但开发者真正需要的就一件事：一个听话、快速、不出乱子的终端助手。

Pi 的设计哲学刚好相反。系统提示词极度精简，砍掉自动追踪、后台执行这类内置设定，调用成本和延迟压到最低。创始人 Mario Zechner 的一句话概括了它的定位：最好的 AI 助手不应该是一个替你做决定的包工头，而是一把趁手、轻量、透明、完全听你调遣的瑞士军刀。

Pi 能火，是因为它戳破了 AI Agent「大包大揽」的泡沫。好的 Agent 设计，不是看塞了多少功能进去，而是看核心做得多精简、边界划得多清晰。

这篇文章要讲的，就是这个道理在 B 端垂直 Agent 里的应用。先厘清 B 端 Agent 和 C 端 Agent 在设计逻辑上的根本差异、B 端该把研发资源真正投在哪。然后逐层展开：怎么识别值得 Agent 化的场景、怎么从场景倒推最少组件、怎么在场景升级时精准补丁而不是堆功能、怎么砍掉 C 端思维带来的过度设计——最后，如果企业已经有一套运行多年的智慧化系统，怎么平稳过渡到 Agent，而不是推倒重来。

Part 1：B 端 Agent 的设计逻辑，和 C 端完全是两回事

C 端 Agent 的核心矛盾是「探索」vs「留存」——用户打开 ChatGPT 的心态是「让我看看你能干什么」，所以厂商只能什么都给，功能列表越长越好。

B 端 Agent 的核心矛盾是「精确」vs「信任」——客户部署一个质检 Agent，诉求是「把这几条规范给我查了」。多一个按钮都是干扰，多一次误判都是信任损伤。B 端不是在跟竞品比功能清单，是在跟客户的人工比：必须比人更准、更稳、更能被追责。

这个差异决定了 B 端 Agent 真正的投入方向不是「还能做什么」，而是做好两件事。

准确性闭环。 C 端错了重来，B 端质检漏判一次是客诉、合规误判一次是事故。重心不是「模型更强」，而是错了能追溯到哪一步、哪个知识片段导致误判、怎么在可接受时间内修好。Salesforce Agentforce 把 Trust Layer 放在售前 PPT 第一页——数据脱敏、策略执行、可审计日志，C 端没人关心，B 端是上生产的前提。

人机协同是产品本身，不是兜底。 C 端 Agent 的理想是全自动，B 端的理想是「人和机器各管各的，配合成本最低」。质检 Agent 里「置信度低于阈值自动挂起等组长审核」这个动作，不是故障降级，是核心功能。边界设计和集成深度，是这两件事的自然延伸。而多模态、多 Agent 协作、语音交互、插件生态——那是 C 端军备竞赛的战场。

C 端 Agent 的竞争逻辑是「我比你多一个功能」，B 端 Agent 的竞争逻辑是「你多的那个功能我的客户用不上，我少的那个环节客户不敢用」。

Part 2：先识场景——什么工作值得被 Agent 替代

组件是手段，场景才是起点。在讨论该用什么组件之前，必须先把这个问题回答清楚：这笔生意，值不值得用 Agent 来做。

注意这六个维度不是等权重的。数字化可接入和合规允许是一票否决项——数据拿不到，Agent 再聪明也白搭；监管不允许，技术上能做到也没用。错误可接受也是硬门槛——做错没法改、没审核兜底的场景，哪怕其他维度全满足也不该碰。相比之下，ROI 直接可核算偏黄（不满足）的场景，只要其他条件成立，仍然值得做——只是立项时需要花更多功夫算账。

六个维度全绿的场景是 Agent 的甜点区——客服工单和质检报告就是典型案例（质检报告这个全绿场景，后面 Part 3 会详细拆解）。有一个否决项亮红灯的直接出局；其余维度两三个偏黄的可以做，但需要针对性设计。以合规审查为例——合规允许偏黄（终审必须有法务签字），意味着 Agent 只能是辅助角色而不能做终审决策，但不影响它在审查环节独立完成初筛。

识别 B 端场景的过程，本质上就是回答一个问题：给这个人一个只会打字和调 API 的助手，他的效率能提升多少？

这个问题的妙处在于，它自动过滤掉了那些「看着很 AI但其实不需要 AI」的场景：设备物理检修直接倒在数字化可接入上（拧螺丝不是 API 调用）；传统报表生成不需要 Agent——SQL + Excel 早就搞定的事，规则完全可穷举。

2.2 四个行业，拆到具体工作

泛泛地说「医疗场景适合 Agent」毫无意义。必须拆到具体工作，才能看出哪些是真正的机会，哪些是概念泡沫。

拆解之前先澄清一件事：不是每个工作都只有「能替代」和「不能替代」两种答案。 真实世界更接近一个光谱——

  • • 自主处理：数字化可接入、决策逻辑可描述、错误可接受且有兜底、传统规则化不经济、ROI 可核算、合规无禁止。
  • • copilot 辅助：需要人的最终判断、需要物理在场、需要创造性，但 Agent 可以在旁边提供信息、草拟方案、检查遗漏——不替代人，而是放大效率。
  • • 不该碰：涉及生命安全、法律责任、不可逆决策——边界不是技术划的，是法律、制度、伦理划的。

下面用这个三层光谱拆解四个行业。

医疗

医疗是四个行业里最保守、合规壁垒最高的——但也是电子病历普及率最高的，三级医院 4 级达标率 87.99%。

自主处理：病历结构化录入（从自由文本提取字段填入 HIS）、检查报告摘要生成、医保规则审核（适应症-用药-剂量匹配检查）、药物相互作用查询。本质是信息处理和规则匹配——需要理解医学术语，但不需要承担诊断责任。

copilot 辅助：诊断决策——Agent 不能替医生拍板（NMPA 不给批，《民法典》也不允许），但可以列出鉴别诊断清单、提醒罕见可能性、对照最新指南标注医生遗漏的检查项。AI 三类证累计超 100 张，全部集中在肺结节 CT、眼底筛查这类「辅助诊断」而非「独立决策」——NMPA 划的边界很清楚。医患沟通——Agent 不能替医生共情，但可以帮医生把「急性心肌梗死」翻译成「心脏的一根血管堵了」，准备通俗版解释草稿。

不该碰：手术操作（物理世界）、急诊分诊（时间压力 + 生命风险 + 不可逆后果）、术中监护。

文旅

文旅是在线化渗透率最高的消费行业之一，OTA 智能客服 AI 化率 35-50%。

自主处理：行程规划推荐、票务查询退改、游客 FAQ、酒店比价、多语言翻译。本质是信息聚合和重复咨询——把游客从「查攻略-比价格-看评价」的重复劳动里解放出来。

copilot 辅助：现场导游讲解——Agent 无法替代物理空间的在场感，但可以给导游提供实时知识库：这条街的历史典故、这栋建筑的设计师、附近刚开的展览。导游负责情感和临场，Agent 负责信息供给。文创设计——Agent 做不了最终创意判断（需要文化理解和审美），但可以生成数百个初稿变体、提取流行视觉元素、快速迭代配色方案，让设计师从琐碎试错中解放出来。

不该碰：危机公关——旅游事故和投诉升级涉及品牌声誉和法律风险，必须有真人根据现场态势拍板，Agent 最多提供历史类似事件的处理参考。

能源

能源的 IoT 基础设施是四个行业里最完善的——电网无人机巡检覆盖率超 80%，工业 IoT 连接数超 50 亿。

自主处理：巡检报告生成（无人机影像+传感器数据→结构化报告）、异常数据根因分析建议、维修工单自动分派（故障类型→技能匹配→排程优化）、维护知识问答。数据管道已经铺好了，Agent 做的是最后一公里：把原始数据变成结构化输出。

copilot 辅助：能源调度建议——Agent 可以跑负荷预测、发电计划和约束条件推理，生成几个方案供调度员选择，最终拍板必须是人。Agent 出错是效率损失，人出错可能是一条人命。现场应急处置——Agent 到不了现场换绝缘子，但可以在后方实时分析传感器回传数据，提醒现场工程师关键参数变化。

不该碰：重大安全风险评估、设备物理检修——涉及不可逆后果或物理操作。

政务

政务场景标准化程度极高——省级一网通办覆盖率 100%，事项网上可办率超 90%。数字政府市场规模约 6000 亿。

自主处理：办事指南问答、表单填写辅助、材料预审与补正提示、多部门信息跨系统查询、政策文件摘要与新旧版本对比。深圳「秒批」系统覆盖超 200 项事项，本质是形式审查自动化，不是实质审批。

copilot 辅助：行政审批——终审决定必须由有签字权的人做出（《行政许可法》的制度规定），但 Agent 可以在审批前圈出所有不合规项、附上相关法规条款、给出初步建议。审批人做最终判断，Agent 让判断更快更准。政策制定——Agent 做不了价值判断和政治权衡，但可以检索国内外类似政策的实施效果、标注不同利益群体的可能反应、整理听证会反馈摘要，给决策者一个更完整的信息底板。

不该碰：行政审批终审（签字权不可替代）、信访处理（需要真人共情和自由裁量）、重大行政处罚决定。

四个行业的拆解指向同一个结论：真正值得 Agent 化的场景，集中在「自主处理」那层光谱带里。 copilot 层也有价值，但那是辅助人而不是替代人，省的是时间而不是人头，投入产出比要单独算账。「不该碰」的边界是物理约束、法律框架和制度设计刻在石头上的，跟技术能力无关。

知道了这个光谱，接下来的问题是——在「自主处理」的甜点区里，最少需要什么。

Part 3：从场景出发，定最少组件

场景明确了，组件才有意义。这一节用质检 Agent 做完整推导，展示「场景需求 → 最少组件」的一一映射。

场景：某客服中心——每条客服对话记录需要对照质检规范逐条检查，标记异常条目，疑似问题甩给组长人工复核。质检规范是一份 30 页的 PDF 文档，包含 47 条检查项（用语规范、合规红线、流程完整性等）。质检员每天看 200 条记录，漏检率约 12%。

把场景需求拆开，逐条映射到组件：

场景需求                                 →  最少组件                →  为什么不需要更多
────────────────────────────────────────────────────────────────────────────
需要理解 30 页质检规范里的 47 条检查项      →  RAG（知识库）           →  不是 FAQ，不需要关键词匹配；
                                                                     是理解规范语义，所以 RAG 足够

需要读取工单系统中的对话记录               →  Tool（工单 API）        →  一个 GET 接口，不需要编排引擎

需要逐条对比对话内容和检查项               →  LLM + 系统提示词        →  规范就是标准答案，不需要「辩论」；
                                                                     单步判断，不需要 Agent 策略的
                                                                     推理-行动-观察循环

需要标记异常并写回工单系统                 →  Tool（写回 API）        →  出结果就写回，不需要 Workflow 引擎

需要疑似问题甩给人工复核                    →  人机协同（升级模式）    →  设置置信度阈值，低于阈值自动挂起
                                                                     等人工，不需要多 Agent 协作

这个质检场景，4 种核心能力就够了：RAG、Tool、LLM、人机协同。 场景涉及两个 Tool（读工单和写工单），但它们是同一种能力类型。

不需要编排引擎——质检做的是一步判断，不是多步骤决策链。不需要长期记忆——每条工单独立检查，今天查的和昨天无关。不需要多 Agent 协作——检查项是并行的，一条 LLM 调用全部覆盖。不需要推送通知——结果就是「通过/不通过」，组长刷新工单列表即可。

当然，「4 种」是针对质检这个具体场景的——不同场景的最少能力数可能是 3，可能是 5。关键是推导逻辑，不是具体数字。每一个被排除的组件，排除理由都是同一个：场景没要求它。

按 C 端产品的思维来做这个质检 Agent，大概率会长成这样：智能报表（「本月话术合规率同比提升 3.2%」）、多轮对话（「您觉得这条判得有问题吗？我重新检查一下」）、主动预警（「叮！检测到近 24 小时开场白偏离率上升」）、知识自动更新（「质检规范 v3.1 已更新，Agent 已同步学习」）。

全是客户不会买单的技术债。

客户的需求很明确：替掉质检员每天看 200 条记录这摊事，漏检率从 12% 降到 3% 以下。 报表？质检组长自己会拉 Excel。预警？组长的需求是「别打扰我」，不是再多一个推送。知识自动更新？规范一年改两次，拖进新 PDF 重新索引即可——这个动作的价值抵得上一个「自动更新」功能三个月的开发量。

从场景倒推，质检 Agent 只需要 4 种核心能力。多出来的每一样，都是成本。

这个结论反过来看，才是本文的核心主张——不需要从开源框架的 21 个节点类型里选，不需要从大厂 SaaS 的 8 层架构里挑。只需要问一个问题：这个场景，最少需要什么？

Part 4：精准补丁——当最少不够用时，加什么

场景不是静止的。质检 Agent 上线后，使用方会提出新需求——但这些需求不是「再加几个功能」，而是「场景升级了，缺了点能力」。

第一个变化最典型。上线第一周就跑出了问题：系统把家电产品的质检规范用在了手机品类上——产品类型不一样，规范不一样，但 Agent 不知道。

性能优化，不是功能叠加。能力补丁 ≠ 新按钮

每一步补丁都有明确的场景驱动力：不是「竞品有所以我们也要有」，而是「现在这样跑不通了，必须补一刀」。补丁的逻辑是——场景撑开了，组件才跟上。不是组件先备着，等场景来用。

C 端 Agent 的升级逻辑是「我们又多了 10 个功能」，B 端 Agent 的升级逻辑是「这个场景现在可以少一个人了」。

前者看覆盖率，后者看替代率。衡量标准完全不同。

Part 5：警惕过度设计——C 端哪些功能 B 端不需要

C 端 Agent 在过去几年里卷出了一整套「标配」能力清单。但这些功能拿到 B 端场景里逐条审视，大部分是过度设计。

这张表背后的逻辑很简单：C 端堆功能是因为「用户探索边界」——厂商不知道用户想干什么，所以什么都给。 但 B 端场景的边界是客户划好的。质检就是质检，不会突然要写诗。客服就是客服，不会突然要写代码。边界越清晰，能砍掉的功能越多。

一个常见的坑：厂商最爱说「先加上，数据会告诉我们用户需要什么」。这句话在 C 端可能成立，在 B 端是危险的——客户付了钱，要的是一个能用的东西。多一个用不到的功能不是「潜在价值」，是「潜在风险」。那个用不到的多 Agent 模块出了安全漏洞，安全团队不会关心它是不是可选模块——它在产品里，就在攻击面上。

B 端 Agent 需要的不是功能对比表，是一场断舍离——面对厂商的功能清单，问三遍：真的需要吗？不需要。真的不需要。砍掉。

Part 6：完整框架 + 决策路径 + 行业对照

前面拆了五个 Part，这一部分把方法论收束成一个可操作的工具箱。

6.1 四步方法论

Step 0：场景 6 维筛查
  数字化可接入？决策逻辑可描述？规则化不经济？

Part 7：如何从传统智慧化系统过渡到 Agent 产品体系

前面六个 Part 讲的是「从零搭建」。但现实是——绝大部分 B 端客户已经有运行多年的智慧化系统。智能客服、智慧质检、智能审批，可能不好用，但已经在跑了。问题不是「要不要上 Agent」，是「怎么平稳过渡」。

7.1 本质区别：新旧系统差在哪

传统智能客服是四层架构：接入层（电话/微信/App）→ 意图识别层（关键词匹配 + 正则模板 + 浅层 NLP）→ 对话管理层（决策树 + 填槽 + 流程编排）→ 知识管理层（FAQ 库 + 文档库）。传统智慧质检是规则引擎：语音转写→关键词/正则匹配→模板偏离检测→加权打分→输出报告。

它们的共同底层特征：规则驱动。 所有行为由人工预定义的 if-else 规则树控制。改业务流程 = 改规则 = 改代码 = 排期上线。

Agent 系统的底层特征完全相反：推理驱动。 规则不再是硬编码的决策树，而是注入给 LLM 的知识约束。改业务流程 = 改提示词 = 即时生效。

旧系统是把人的经验写成规则让机器执行，Agent 是给机器知识和方法让它自己判断。差的不是功能列表，是决策范式。

举质检场景为例——旧系统：ASR 转写 → 关键词/正则匹配（命中「投诉」「12315」→ 高风险）→ 模板偏离检测 → 加权打分 → 输出报告。规则覆盖到就好用，覆盖不到就漏检。Agent 质检：读取规范（RAG）→ 语义理解逐条对比（LLM）→ 标记异常 → 低置信升级人工。旧系统在「匹配」，Agent 在「判断」。

但旧系统的资产不是废品。那些决策树里藏着最真实的业务经验——47 条质检规则、客服 FAQ 对、审批合规红线，都是几年迭代沉淀下来的。Agent 化的第一步不是扔掉它们，是吃掉它们。

正是因为大部分能复用，过渡才切实可行。 如果每次都要推倒重来，B 端 Agent 永远落不了地。

7.3 三步平稳过渡

过渡不是一次切换，是建立信任的过程。以下是基于行业实践的粗略参考，具体时长取决于客户体量和场景复杂度。

阶段一：影子模式（1-2 个月）

Agent 在背后运行，不面向用户。旧系统继续作为主系统响应，Agent 并行接入真实流量但不输出——仅将判断结果与旧系统输出做日志对比。找差距、找幻觉、找薄弱点，积累数据信心。

阶段二：部分接管（2-3 个月）

Agent 接简单场景，复杂/高风险仍由旧系统或人工处理。通过意图路由分发——简单工单自动处理，高风险走旧系统兜底，低置信升级人工。让 Agent 接约 30% 的低风险流量。这个阶段不是验证 Agent 有多强，是验证它不会闯祸。

阶段三：全面接管（3-6 个月）

Agent 成为主系统，通过 RAG + Tool Use + Guardrails 完整服务。旧系统降级为兜底——仅极端场景使用。旧规则引擎做最后一道安全闸，不是因为它好用，是因为它不会出错。

Agent 落地的最大障碍不是技术，是信任。三步过渡的本质，是用几个月让客户从「我觉得它不行」变成「我觉得它比我行」。

这三个阶段跟旧系统本身的能力高度相关。阶段一能跑是因为旧系统 FAQ 可以喂给 RAG 做基础语料。阶段二能跑是因为旧系统规则可以转为 Guardrails。阶段三能跑是因为旧系统留下的审查流程定义了人机协同边界。旧系统不是敌人，是过渡期的脚手架。

7.4 最后一公里

最近前向部署工程师（Forward-Deployed Engineer，FDE）已经成了一个越来越常见的岗位。FDE 和传统实施顾问的关键区别在于：实施顾问只能配置和部署现有产品功能，FDE 有产品修改权——能直接改产品来适配客户场景。他们干的本质上就是：蹲在客户现场，把旧系统里沉淀了多年的决策经验翻译成 Agent 能理解的约束，梳理该接哪些系统、该按什么节奏过渡，然后和客户的 IT、合规、业务三方反复对齐。Agent 引擎早就在云端跑起来了，难的从来不是代码。

回头看那些真正跑起来的 B 端 Agent 案例，ARR 从几十万涨到上千万甚至过亿——没有一个是靠模型能力单打独斗干出来的。全是一群人反复看 Agent 哪里被绕过去了、哪个知识库条目缺了、哪个场景该升级人工但硬撑着回答了，然后改提示词、补知识、调路由。循环。

技术可以买，陪跑买不到。选 Agent 供应商，说到底不是选功能最强的，是选那个愿意蹲在现场、理解旧系统里每一行规则的团队。

结语

回到开篇的 Pi。

一个把系统提示词砍到极致、把架构拆成四层独立模块、靠做减法拿下 70,000 GitHub Star 的开源项目。它证明了最好的工具不是大包大揽的黑盒，而是趁手、透明、自由组合的瑞士军刀。

B 端 Agent 的世界，其实比开发者工具更需要减法——边界清晰、结果可量化、需求明确。不需要预判一百种可能性，只需要把一件事实实在在地做好。识别真实场景、匹配最少能力、砍掉所有多余。

如果企业已经有一套旧系统——那才是大多数生意的真实起点。Agent 落地最难的部分不是搭什么，是让客户相信它比旧系统强。这个信任，需要过渡期，需要那个愿意蹲在现场的人。

少即是多，陪才是赢。
