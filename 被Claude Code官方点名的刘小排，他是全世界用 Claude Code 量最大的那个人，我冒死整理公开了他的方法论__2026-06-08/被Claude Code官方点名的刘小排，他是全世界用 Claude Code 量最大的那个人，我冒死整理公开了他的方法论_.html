第一条：CLAUDE.md 是你的命根子


Claude Code 每次启动，第一件事就是读项目根目录的 CLAUDE.md。


这个文件，就是你给 Claude 写的入职手册。


没有它，Claude 每步都在猜：


· 技术栈是什么？

· 命名规范是什么？

· 哪些文件不能动？


猜对了算你运气，猜错了你买单。


CLAUDE.md 里写什么？直接上模板：


```markdown

## 项目背景

这是一个企业级 SaaS 产品，核心功能是 xxx


## 技术栈

- 前端：Next.js 14 + Tailwind

- 后端：FastAPI + PostgreSQL

- 部署：Vercel + Railway


## 目录结构

/src/app       页面路由

/src/components 组件库

/src/lib       工具函数


## 编码规范

- 使用 TypeScript，禁止 any

- 组件用函数式，禁止 class

- 提交前必须跑 npm run lint


## 禁止事项

- 不要修改 /src/lib/auth.ts

- 不要引入新的第三方依赖，除非我确认

```


越细越好。一次写好，后面每次对话都白捡效率。

第二条：先规划，再动手——少走 90% 的弯路


Claude Code 有一个 Plan Mode，快捷键 Shift+Tab。


开了它，Claude 只出计划，不碰任何文件。


为什么这一步能救命？


因为如果你直接让它干，它会立刻开始改。改到一半你发现方向错了，代码已经乱成一锅粥，回滚的成本高到你心疼。


正确流程：


```

1. 开 Plan Mode

2. 说任务

3. 看 Claude 输出的计划——改哪些文件？改什么？

4. 你确认没问题

5. 关 Plan Mode，执行

```


多花 30 秒看计划，少花 30 分钟擦屁股。


---


第三条：任务切得越小，Claude 越不容易抽风


这是最容易被忽略，但最要命的一条。


❌ 错误示范：


“帮我优化一下这个项目的性能”


✅ 正确示范：


“修改 src/api/users.ts 里的 getUserList 函数，给数据库查询加分页，每页 20 条，参数从 query string 读 page 字段。改完跑 npm test，确认通过。”


任务越具体，Claude 跑偏的概率越低。


一个 Session 只干一件事。大任务先拆，再一步步喂给它。


---


第四条：对话越长，Claude 越蠢


这是 Claude Code 的物理天花板，别硬杠。


对话越长，它“记”得越模糊，越容易前后矛盾、自己打脸。


实操守则：


· 上下文用到 50% 左右，果断开新会话

· 用 /compact 压缩历史，省 token

· 重要约定写进 CLAUDE.md，别靠对话硬记

· 新会话开头，花 10 秒交代“我们在做什么”


---


第五条：Git 是你的安全绳，别嫌麻烦


每完成一个小功能，立刻 commit。


Claude 写的 commit message 比大多数人认真，放心让它写。


好处是什么？Claude 改坏了，git reset 一键回到上一秒。


进阶操作：git worktree


这是刘小排方法论里最硬核的一招。


git worktree 让你在同一个仓库里，同时 checkout 多个分支到不同目录。


配合多终端，多个 Claude 并行干活：


· 终端 A：Claude 写前端组件

· 终端 B：Claude 写后端 API

· 终端 C：Claude 补测试


互不干扰，效率直接翻倍。


---


第六条：会问问题，比会改代码重要


整理几个刘小排日常在用的 prompt 模板，拿走直接用：


给角色定位：


“你是一个有 10 年经验的 Go 后端工程师，严格遵循 Clean Architecture”


加约束边界：


“不要修改测试文件，不要引入新的第三方库”


要求先列计划：


“在动手之前，先列出你要修改的文件和修改原因”


指定验证步骤：


“改完后运行 go test ./...，确认全部通过再告诉我结果”


---


避坑指南（直接划重点）


刘小排反复强调，下面这几条是最容易踩的坑，你一定要注意：


别让它一次重构整个项目，正确的做法是拆成 5 个小任务，一步步来。

别跳过 Plan 模式就直接执行，先看计划再动手，方向错了什么都白搭。

别在上下文很长的时候硬扛，用 /clear 开新会话，干净利落。

别靠对话去记重要约定，那些东西一定要写进 CLAUDE.md。

别不提交就继续改，每个功能点 commit 一次，安全第一。


把这几点刻在脑子里，你就能避开 90% 的坑。
