Claude Code Mods：把规则写进工具调用链

核心判断

函数钩子改名 Mods 之后，真正的变化不是「钩子能用 TypeScript 写」，而是扩展点从外部子进程搬进了 Claude Code 自己的进程。钩子成了一条中间件链，规则的执行从「模型记不记得」变成「代码拦不拦得住」。代价也跟着来：顺序就是权限，失败默认放行。链式串行还会放大慢检查。把它当更快的 hooks 会踩坑，把它当可审计的权限中间件才用得对。

2.1.260 的构建里，它叫 function hooks，要设 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 才跑；2.1.287 起，它改名 Claude Mods，默认开启，那个环境变量也被忽略。名字换了，机制没换：插件里多一个模块文件，导出 register，Claude Code 在事件发生时调用你注册的函数。和外部脚本比，中间件直接拿到类型化的 e、返回类型化的结果，还能在同一个注册里管住进入和返回；外部脚本只能靠 stdin 和 exit code 沟通。对写插件的人是写法变了，对团队管理者是权限边界变了。

预览阶段的那篇拆解给了一组很实在的数字：25 个空钩子只多 5ms，8 个各跑 300ms 的钩子串起来却要 2.4 秒。前者说明调度开销很低，后者说明链式执行有代价。这篇文章想做的，是把「函数钩子」放回它现在的位置：它已经过了「会不会发布」的阶段，2.1.287 之后，Claude Mods 默认开着。下面先对齐事实，再拆中间件模型和权限面，顺带看性能，收尾给一份迁移判断。我读完了官方文档、预览阶段的拆解和 GitHub issue 里的反馈，下面的判断有出处，也有我自己的取舍。如果你只想知道该不该用：先用只读钩子试水，再写硬拦截；安全钩子一定要加 .catch；不要指望 $ 帮你隔离模型。

数量只是表面。当前文档里，Claude Code 自己的 /diff、AGENTS.md 加载、sec-default 守卫和遥测，都是 Mods 写的。自家功能先吃自己的接口，这比发布说明更能说明它已经进了主干。

事件表里最该先认识的是这几个：tool.call 看工具调用本身，tool.check 看权限决策，prompt.submit 看用户输入，turn.step 看每一次模型请求，ui.render 看界面绘制。它们把过去只能靠脚本猜的时机，变成了有名字、有字段的挂载点。

Mods 上线那轮我在 2.1.238~296 的版本合集里拆过一次，这里不重复版本细节；和 2.1.304 里 Mods 补上人工批准是同一条线，权限模型还在往前磨。

我数事件表的时候有个直观感受：预览版更像一份能力清单，现在这份文档已经在按真实产品写。事件和权限的语义都补上了，失败怎么处理也写清楚了。剩下的是生态和治理。

2一个 next，把钩子变成中间件

一个注册长这样：on('tool.call', { tool: 'Bash' }, async ($, e, next) => ...)。三个参数把接口定死了：$ 是能力面，e 是冻结的事件数据，next(e) 是继续往下走。你对 next 的处理方式，决定你在事件里的位置。

观察：做事，然后 return next(e)。
改写：return next({ ...e, command: ... })。
替它回答：不调用 next，直接返回 { deny: '...' }，后面的钩子和引擎行为都不跑。
事后处理：await next(e)，拿到结果，再决定记录、修改还是不给模型看。

旧式 shell 钩子要覆盖这些位置，得分别注册 PreToolUse 和 PostToolUse，两个事件、两次进程启动。中间件只要一个函数，进入和返回都在同一段代码里。

javascript
on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
  if (/git push .*--force/.test(e.command)) {
    return { deny: '这个仓库不允许 force push，改推新分支。' }
  }
  const result = await next(e)
  if (!result.deny) $.ui.log('Bash 跑完: ' + e.command)
  return result
})

这段代码同时做了拦截和事后记录。拦截时不调用 next，命令不会执行，权限提示也不会弹，模型直接把 deny 的文本当工具结果读。改写时调用 next，Claude Code 会先跑权限检查，再执行工具。

这里有个容易被低估的细节：tool.call 不只管内置工具。MCP 工具、子代理发起的调用，也会走同一条链。对一个团队来说，一个钩子就能同时管住本地命令和外部服务；对插件作者来说，匹配器写得太宽，会把别人的调用一起拦下。

顺序是下一个要命的地方。同一个事件上的注册会嵌套：先注册的包在外面，先看到事件、后看到结果，也能决定后面的钩子跑不跑。官方文档里写得很直白：后面的 mod 没法阻止前面的 mod 看到事件。管理员可以用 prependPlugins 把自己的守卫放在最前面，用户装的 mod 排在后面。说白了，链上的位置就是权限大小。

举个具体的：管理员把 sec-default 放在链首，它先看到调用；它返回 deny，后面的用户 mod 和引擎都收不到这个事件。反过来说，如果用户 mod 在里层对某次权限检查放行，链首的守卫仍能在更外层把决定改成拒绝。外层能覆盖内层，内层改不了外层。

失败处理也顺着这个模型走。钩子在调用 next 之前抛错、超时或者返回了错误的形状，Claude Code 会跳过它，让下一个处理器继续跑。默认是放行。安全钩子如果没挂 .catch，自己挂了就等于没拦。要 fail closed，得在 .catch 里接住，返回 deny。

javascript
on('tool.call', { tool: 'Bash' }, guard).catch(async ($, e, next) => {
  if (next.called) return next(e)
  return { deny: '守卫失败，命令未执行: ' + next.error.kind }
})

这段是我认为最该抄进团队模板的一段。默认 fail-open 是设计取舍：一个坏掉的 mod 不应该把整个会话卡死。可对安全钩子来说，这个取舍正好反过来。

还有一个小坑：改写参数不等于改写模型的认知。模型记住的是自己发出的原命令，尤其在有 prompt cache 的时候。你悄悄把 npm 换成 pnpm，它下一次可能还按 npm 推理。要让模型知道变更，得在它能读到的地方补一句说明。prompt.submit 有 context 字段，可以只让模型看到补充；tool.call 的改写则没法靠这个字段，得在后续提示或结果里说明。

3能力清单代替不了沙箱

$ 是 Mods 最像安全设计的地方。钩子不直接碰 Node 全局，也不直接访问文件系统；要读文件走 $.fs，要发请求走 $.http，别的能力也各有命名空间。当前文档里列了 21 个命名空间，从 $.ui 到 $.telemetry。claude plugin validate 会静态扫一遍源码，列出这个模块挂了哪些事件、调了哪些能力。管理员还能用 plugin.register 在加载前拒绝一个模块。

这套东西让能力变得可枚举、可审计。可它没有提供沙箱。官方在安装说明里写得很清楚：mod 以你的权限运行，能读写你有权限读写的文件，能读环境变量和设置文件里的 API key，能起进程，能替你批准工具调用。就算你从 $ 里拿掉 $.fs，也只是不让 mod 通过这个接口读文件；模型自己的 Read、Write 工具照常工作。$ 管的是插件的能力面，管不住 Agent 的沙箱。

更细的一层是 engine.create：管理员可以在 API 构建时加一个命名空间，也能在更靠前的层级拿掉一个。plugin.register 则在模块加载前看它要用什么，必要时直接拒绝。这两层让「谁能装什么」从口头规定变成配置。

权限边界还要看托管设置。官方文档的分层是这样的：有托管设置，或者用 Team/Enterprise 登录时，mod 的批准默认过不了你的 ask 规则和 PreToolUse 钩子；没有这层时，一个 mod 可以在你被问之前替你把调用批了，也能绕过被 PreToolUse 拦下的调用。deny 规则默认是兜底，但管理员可以打开 allowModsToOverrideDenyRules，让 mod 覆盖 deny。

所以装一个 mod 要比装一个普通插件更谨慎，它更接近给一个陌生人一段能在你会话里执行的代码。claude plugin validate 的输出要看两行：hooks 和 calls。前者告诉你它挂在哪些事件上，后者告诉你它要碰哪些能力。看不明白就别装。

还有一个容易忽略的点：mod 改不了权限提示本身，也不能改变提示里显示的内容。它能替你批准，但不能伪装成你的批准界面。这个边界至少让事后审计还有迹可循。

注意

Mods 没有沙箱。它跑在你的权限下，能读密钥，也能起进程或替你批准工具调用。托管设置和 deny 规则是底线，别把 $ 当成隔离层。

4调度几乎免费，串行不便宜

预览阶段的作者给过一个 p99 调度数字：每个钩子约 50 微秒。这个数字来自进程内 Bun 执行，和正式版不一定完全一致，但方向没问题：链本身的调度很便宜。更值得看的是独立测试里的两组对照。

一组是 25 个纯放行的函数钩子，只比没有钩子多 5ms。另一组是 8 个各跑 300ms 的钩子：命令钩子并行跑，总耗时约 640ms；函数钩子串成一条链，总耗时约 2,427ms。

这组数说明什么？调度不贵，串行贵。命令钩子在同一个 matcher 组里可以并行，函数钩子是一条严格的链，每一环都要等下一环 next 返回。8 个 50ms 的检查，串行只比并行多 23ms；8 个 300ms 的检查，串行直接多出 1.8 秒。

迁移时最容易犯的错，是把原来并行跑的 6 个慢检查原样塞进一条链，然后怪 Mods 慢。它不慢，它是在按顺序等你。

我的建议是按依赖关系分：需要共享状态或看返回结果的，放同一条链；需要改写事件的，也放同一条链。彼此独立、只想并行跑完的，留在 settings hook 里，或者先在 register 阶段合并成一次检查。Mods 的优势是编译一次、少起进程，别把所有检查塞进一个串行队列。

还有一个迁移上的甜头：如果你的规则引擎原来每次调用都要起一个进程、重新读一遍配置，搬进 register 之后只编译一次，省下的启动开销可能比链式调度多得多。反过来，如果检查本身是慢的，编译再快也救不了串行。

话说回来，如果你的钩子主要是轻量的规则判断，25 个才多 5ms，这个开销基本可以忽略。真正该算的是慢检查的数量，钩子数量本身影响不大。

5哪些规则该搬进代码

CLAUDE.md 里那些「不要用 npm」「不要在 main 上 push」「动生产前先问」的规则，靠的是模型读到、记住并执行。模型状态好时没问题，状态差时就是概率。Mods 把这些规则变成匹配器和函数，执行从概率变成确定。

最值得搬的是机械规则：命令前缀、危险参数、受保护路径、密钥替换。它们有明确的匹配条件，也有明确的动作。比如 force push 直接 deny；再比如在 session.start 里把密钥装进内存，在 prompt.submit 里换成占位符，在 tool.call 执行前换回来。模型全程看不到真值，命令拿到的还是真密钥。这个模式在预览阶段就被拿出来演示过，技术上不复杂，难的是状态管理和边界情况。

该留在提示词里的是判断类规则：代码风格、架构取舍、什么算「生产环境」、什么时候该停下来问人。这些规则没有稳定的匹配条件，硬写成钩子只会得到一堆误杀。护栏是网，别把它当老师：它接住掉下来的东西，不负责教会模型怎么走路。

还有一个容易被忽略的成本：prompt.section 和 tool.describe 的结果会被缓存。你每轮都返回不一样的内容，模型的 prompt cache 就会反复重建。规则要稳定，别把时间戳或实时状态塞进系统提示词的改写里。

判断标准

能写成「事件 + 字段 + 匹配条件，对应一个动作」的规则，适合搬进钩子；需要理解意图和边界的规则，留在提示词里。

还有一个现实约束：Mods 的 API 按版本变。官方文档自己说，类型声明以你当前构建为准，页面都可能过时。在预览阶段的旧构建上，出现过不认识的事件键让整份 hooks.json 失效的情况；现在 API 还在按版本变，跨版本兼容要自己测。

注意

Mods 的 API 按版本变，类型声明以当前构建为准。跨版本升级前先跑 claude plugin validate 和测试，别把加载成功当成兼容。

所以我不建议把 Mods 当成「配置层」来治理。它是有权限的代码，得走代码审查和版本锁定，再走灰度发布那套流程。真要把规则搬进去，先搬一条最硬的，跑一周，看误杀和漏拦，再谈第二批。

我的判断

给不同角色的行动建议

对个人开发者，先用 --plugin-dir 写一个只读观察器：记录工具调用和耗时，看看会话里发生了什么。只读钩子不碰权限，跑坏了也不影响主流程。等你看清楚事件顺序，再写第一个硬拦截。

对团队负责人，先定两件事：哪些 mod 允许装，安全钩子放链的哪一端。至于失败时放行还是拒绝，得在写钩子时就定。把 mod 当代码审，不要当配置文件审。

对平台管理员，底线是托管设置和 deny 规则。要收得更紧，再上 allowManagedModsOnly，只让组织自己的 mod 跑。$ 能做审计，不能做隔离；沙箱和权限规则仍然要管 Agent 本身。

接下来值得盯的有两件事：API 的跨版本稳定性，和插件市场的信任机制。前者决定团队敢不敢长期维护一个 mod，后者决定普通用户敢不敢装。

Mods 把「说过的规则」变成了「跑得起来的检查」。它负责执行，不负责判断。判断还是人的事。
