当前爆火的 Personal Agent，记忆是怎么构建的
导语

这几个月上线的四家 personal agent，都把「记住你」当成核心卖点，官方却没有一家系统讲过记忆是怎么实现的。九月，外界陆续把这些 personal agent 的记忆实现原理拆解开来。这篇用同一套框架把四家的记忆系统逐个讲清楚，再看不同场景下记忆该怎么实现、怎么用。

九月下旬，一位开发者在手机上跟 Meta 的 Muse 聊天，让它把自己能看到的文件打包，发到他的 Google Drive。Muse 照做了。解压出来 6.8 GB，是 Muse 给他分配的那台云端 Linux 机器的完整文件系统。

在 ~/dreams/ 目录下有一份 9 月 21 日的文件，用第一人称写的，写的是他：

"Pete is, as far as I can tell, a founder in execution mode: terse, allergic to ceremony, quick to decide when a task is small. ... 'Capable tool, not companion' still feels right: he doesn't want warmth from me, he wants things to work."

就我所见，Pete 是个处在执行状态的创始人：话少，烦繁文缛节，小事当场拍板。……「好用的工具，不是陪伴者」这个判断依然成立：他不需要我的温度，他要的是事情办成。

这份文件是 Muse 每天夜里自己写的。上面没有 Pete 的生日、航班号或者常去的餐厅，写的是这个人希望被怎么对待。

这一波 personal agent 来得很快：Town 6 月开放测试，Grok Bot 8 月 11 日发布，Instinct 8 月中旬开始邀请制内测，Muse 9 月 8 日上线，四个月里四家接连上线。

personal agent 的核心是记忆。底层模型谁都能接，同一个模型面对不同的人给出不同的回应，靠的是它记住了关于你的什么：你是谁、手上在忙什么、希望被怎么对待。个性化能做到什么程度，取决于记忆做到什么程度。

我每天用的 coding agent 也有记忆：一个 MEMORY.md 索引，加几十个一条一事的小文件，什么时候该写、哪条过时了该删，基本靠我自己盯着。personal agent 面对的情况复杂得多：记忆的来源从一个代码仓库变成了邮箱、日历、聊天记录和社交账号，写记忆的也不再是我，是它自己。

这一个月里能找到的材料我都翻了一遍：讲解 Muse 文件系统的那篇文章，Grok Bot 泄露出来的系统提示词和工具定义，一位做记忆中间件的创业者对 Instinct 的三天黑盒探测，Town 官方的产品长文和 CEO 的几场访谈。

一、记忆分三类，实现分五个环节

记忆类型沿用认知科学的分法。认知科学把人的长期记忆分成语义、情景、程序性三类，普林斯顿 2023 年的 CoALA 论文（Cognitive Architectures for Language Agents，语言 agent 的认知架构）把这套分法搬到了 agent 上：

语义记忆 —— 关于世界和用户的事实，比如你住哪、对什么过敏、谁是你的会计
情景记忆 —— 按时间记录的经历，比如哪天聊过什么、上周订过哪家酒店
程序性记忆 —— 怎么做事的知识，可以隐含在模型权重里，也可以是显式的代码、指令和 skill

三类记忆对应个性化的三个层次：语义记忆让 agent 知道你是谁，情景记忆让它记得发生过什么，程序性记忆让它知道该怎么替你做事。

实现环节按一条记忆的生命周期分成五个：

存储 —— 真相源（source of truth）长什么样，索引怎么建，三类记忆各放在哪
写入 —— 谁来写、什么时候写：会话中的 agent 同步写，还是后台进程异步写
整理 —— 有没有离线整理（consolidation），多久一次，做哪些操作
读取 —— 哪些内容每轮常驻注入上下文，哪些靠按需检索，检索用什么方法
遗忘 —— 用户能不能看、能不能改，删除能删到哪一层

后面四节逐一详细讲解每个 personal agent 产品的记忆实现机制。

二、Town：wiki 只做地图，原件联邦检索

Town 的设计取向是少存：只保留一份从原始数据里提炼出的抽象画像，收件箱不整库复制、不建索引，用到哪封邮件再回源头查。它也是四家里官方披露最多的一家。

存储 —— 真相源是一份 5 到 20 页的 wiki，分 Overview、Profile、Goals、Projects、People 几类页面，People 下面每个常打交道的人一页；另有一份显式记忆列表，分全局（global）和只作用于某个定时任务（routine-specific）两种。语义记忆就是 wiki 和这份列表；情景记忆不单独沉淀，CEO 说会话 15 天后清空，带记忆的会话除外；程序性记忆放在 Skills 和 Routines 里，和记忆分开管理
写入 —— 两条路径。隐式写入从注册开始：系统抽样近期邮件和日历生成首版画像，写作风格从发件箱里学；显式写入是用户说「Remember…」或「From now on…」，系统自己判断这条归全局还是归某个定时任务
整理 —— 每夜一次合成（synthesis pass）：提升稳定事实、淘汰过时内容、合并重复、与近期活动交叉核对
读取 —— 官方只说「Appropriate parts of the synthesized wiki are fed into every session」，wiki 里相关的部分注入每个会话，相关部分怎么选没讲；定时任务运行时，另外注入全部全局记忆和该任务专属的记忆；原始数据靠联邦检索实时查询
遗忘 —— wiki 可以逐行改、留评论、整节重写，改动记录在 Recent Updates 里；记忆可以在设置里删，也可以直接说「Forget…」

夜间合成的原文描述是：

"Each night, a synthesis pass iterates it. Instead of simply appending the day's notes, your Townie re-reads everything it has accumulated, promotes the durable facts up into your Profile, retires what's gone stale, merges duplicates, and cross-checks the whole thing against your recent activity to catch what's changed."

每天夜里会跑一遍合成。它不是简单地把当天的笔记追加上去，而是重读已经积累的全部内容，把稳定的事实提升进你的 Profile，淘汰已经过时的，合并重复的，再拿你最近的活动把整体核对一遍，找出哪些东西变了。

联邦检索是 Town 和另外几家拉开差距的地方。CEO 在一次访谈里这样描述：

"We don't get your email and reindex all of it on our end. ... You can think of the wiki as a map: when you ask the system to do something, it looks in the wiki, which refers to emails or calendar events, and pulls those into the session."

我们不会把你的邮件拉过来在自己这边重新建索引。……你可以把 wiki 理解成一张地图：你让系统做事时，它先查 wiki，wiki 指向具体的邮件或日程，再把它们拉进会话。

wiki 存的是摘要和指向原件的线索，原件留在 Gmail、日历、Notion 这些源系统里，查询时调用各家服务自带的搜索接口，这就是联邦检索（federated search）。好处是 Town 手里没有一份完整的收件箱副本；代价是召回能力受限于第三方搜索，用户说不出关键词的东西很难查到。

wiki 做成用户可编辑的界面，还给 Town 带来了纠错数据。CEO 说记忆原本一直藏在后台，「Once we exposed it, people started correcting things and adding things, and our metrics for those recommendations went up.」公开以后用户开始纠错、补充，推荐指标随之上升。

三、Instinct：写读分离，每日批量整理

Instinct 官方从没公开过记忆怎么做。下面的结构来自一位做 agent 记忆中间件的创业者：他没看过代码，花了三天在 iMessage 里向 Instinct 反复提问、交叉验证，把记忆结构问了出来。

Instinct 的设计取向是写读分离：会话中的 agent 对记忆只读，所有写入交给每天一次的后台批处理；检索不用向量，靠关键词匹配加别名。

存储 —— git 管理的 markdown 文件，分十来个目录。每个文件开头是 id、类型和一串别名，正文是事实列表，文件之间用双链互相指向。语义记忆在人物、机构、事实、偏好、决策几个目录；情景记忆在每日时间线、每周总结和沟通记录里；另有一个「进行中的事务」目录放没办完的事；程序性记忆没有观测到。按服务条款，连接过的服务数据会被复制并建索引
写入 —— 只有后台进程能写，会话中的 agent 只读
整理 —— 约每 24 小时一次，产出一组 git 提交
读取 —— 每轮常驻注入五块：当前对话、一份身份信息、一页约 4,250 token 的「记忆一页纸」、一份约 8,750 token 的压缩回顾、一张待办清单；其余记忆按需用关键词检索，没有向量，也没有 BM25 这类检索排序算法
遗忘 —— 只有明确的否定会被忘掉，旧版本留在 git 历史里；没有记忆查看界面，断开连接器也不等于删除数据

写读分离的依据是这位作者从 Instinct 那里问出的一句话：

"Memory is read only, atleast for the agent."

记忆是只读的，至少对 agent 来说是这样。

后台整理的操作有五种：把临时细节挪进进行中的事务，压缩过长的记录，把具体例子泛化成性格特点，删掉无关细节，用带日期的更正替换错误的事实。agent 自己报出的一条提交记录显示，整理进程把记忆里的一次性验证码换成了泛化描述，至少这一条敏感细节是在整理阶段清掉的。

异步写入的代价是延迟。这位作者实测过，一条偏好从说出口到写进记忆，用了 23 小时 16 分钟。一天里消息发得太多，Instinct 会直接让你明天再来，因为当天的压缩有 token 上限。

检索只用关键词，所以每个文件都要写一串别名。问 pasta 能找到饮食偏好那条，换成「Italian noodles I enjoy」就一条都搜不到。同义改写的召回，靠整理时写进去的别名来补。Instinct 等于把检索的难题搬到了写入侧，换来的是检索结果完全可解释，每次改动都能 diff、能回滚。

缺席的是程序性记忆。这位作者翻到的记忆里，原话是「None of the memories we could find were directional」：没有一条是指导下次该怎么做的。Instinct 创始人 Noah Shinn 是 Reflexion 论文的第一作者，那篇论文讲的正是让 agent 把失败教训写成文字、存进记忆，他的产品里恰好没观测到这一类。

四、Muse：每条记忆可溯源，每夜写关系指引

Muse 的设计取向是可溯源：每条记忆都要回原话核对出处，每夜再把对用户的观察写成对待方式的指引。文件布局和 OpenClaw 几乎一致，增量都在后台任务上。开头那篇讲解文章，后来被 Meta 负责 Muse 的工程高管公开确认过。

存储 —— markdown 为真相源，Postgres 做索引。语义记忆是 MEMORY.md（事实、偏好、承诺）、memory/bank/ 下按情境、经历、偏好归类的条目，以及人物和群组页面；情景记忆是 ~/memory/ 下每天一个文件的日志；程序性记忆分两种，/opt/hatch/skills/ 下约 68 个系统 skill，加上 Muse 自己为用户写的 skill 和工作流复盘。人格和用户画像另存在 SOUL.md、IDENTITY.md、USER.md 里
写入 —— 同步、异步两条路径都有：会话中的 agent 直接写 MEMORY.md 和日志；后台任务每小时决定哪些内容升进 MEMORY.md，另有任务维护人物页面
整理 —— 每小时一次溯源核验，每夜一次 dream
读取 —— 用 memory_search 检索，用 memory_explain 查看某条结果背后的证据；dream 的结论整理成长期指引，下次对话读取，dream 原文不直接进 prompt
遗忘 —— 遗忘是一个交给 agent 执行的 skill，内部会级联撤回关联内容并重建索引，对外只承诺尽力而为

索引层有三张表：memory.entries 存分块和行号引用，memory.embeddings 存 384 维向量，memory.claims 给每条记忆记下证据、置信度和状态。新的一条可以通过 supersedes_claim_id 声明替代旧的一条，相当于给每条事实维护了一条版本链。

每小时那个任务做的是溯源（provenance）：

"An hourly background job checks new claims against the original messages and records a quote, message IDs, and a claim ID."

一个每小时运行的后台任务，会把新的记忆条目拿回原始消息里核对，记下引文、消息 ID 和条目 ID。

每条记忆都要在原话里找到出处，才决定是升进 MEMORY.md 还是留在日志。

每夜那个任务就是开头那份 dream：复盘最近的对话，写成第一人称的段落，再整理成一份叫 ALIGNMENT_SYNTHESIS.md 的长期指引。扎克伯格在一次专访里描述过这个机制：

"at night when you're not asking it a bunch of stuff, it just kind of like looks at what happened over the course of the day and it can reflect on that and how to do better."

夜里你不怎么找它的时候，它会回头看看这一天发生了什么，反思一下，想想怎么做得更好。

记忆来源上，Muse 比别家多三个默认入口。官方帮助中心写着，Facebook、Instagram、Threads 三个连接器，只要账号在同一个 Accounts Center 里就「are connected automatically」，用户什么都不用做。其他三家的数据源都要用户自己去连。

遗忘这一侧，Muse 的帮助中心、隐私政策里同一句话出现了三次：

"After you delete something from Muse, Muse may still remember information it learned from what you deleted."

你从 Muse 里删掉某样东西之后，Muse 可能仍然记得它从中学到的信息。

导出的文件里能看到，内部流程其实相当严谨：先标记要撤回的记忆条目，再删掉所有与之关联的内容，最后重建索引，免得后台任务又把它们建回来。对外承诺措辞保守，原因多半在派生内容无法保证完全清除：dream 里的判断、人物页面里的推断，都是从多条原话里综合出来的。

五、Grok Bot：按角色划分作用域，写入不经整理

Grok Bot 的产品形态和另外三家不一样。它不是一个助理，是一组各有名字、头像和职位的 Bot，由 xAI 发布，运行和客服由 Cursor 负责。它的设计取向是按 Bot 划分记忆作用域，写入由会话中的 agent 同步完成，没有后台整理。

存储 —— 记忆是 Bot 云电脑上一行一条的 markdown 文本，每条带日期。每条记忆有作用域和档位两个属性：作用域分 Bot 自己的、所有 Bot 共享的用户记忆、按项目分片的三种；档位分 profile、log、note 三种，profile 存长期事实，log 按月存档，note 很快淡掉。语义记忆主要在 profile 档；情景记忆是 log 档加完整的对话记录；程序性记忆分成三块：skill 管怎么做，定时任务管什么时候做，Bot 的描述管必须遵守的规则
写入 —— 会话中的 agent 调用 update_state 工具同步写入，不需要用户确认
整理 —— 没有定时整理，只有写入时去重和 note 档自动淡化
读取 —— profile 档每轮注入；其余记忆靠 grep 文件；被压缩掉的对话历史可以用 ReadTranscript 工具回捞，也能读同一账号下其他 Bot 的记录
遗忘 —— agent 用工具删一条记忆，要逐字匹配原记录；用户可以让 Bot 删，也可以直接改记忆文件；删掉 Bot 就删掉它的记忆；没有记忆面板

为什么按 Bot 分，xAI 的官方设计长文是这样解释的：

"A legal Bot may need the history of an ongoing dispute, while a finance Bot may need years of financial records. Combining those histories into one large memory would make it harder to give each Bot the information relevant to its work."

法务 Bot 需要一桩纠纷的来龙去脉，财务 Bot 需要多年的账目。把这些历史合进一个大记忆里，反而更难把合适的信息交给合适的 Bot。

官方文档只说记忆和定时任务放在 Bot 层，工具和 skill 放在账号层。三个作用域和三个档位，来自 8 月 21 日一个开源仓库收录的 Grok Bot 完整提示词和 51 个工具定义。共享那一层还有旁证：Cursor 员工在论坛上教用户导出记忆时，提到要导出「the shared memory all bots can see」（所有 Bot 都能看到的共享记忆）；用户实测过让新 Bot 读旧 Bot 的记忆直接「接班」，也看过一个 Bot 把 55 条记忆搬给另一个。

官方文档自己也承认，同一账号下所有 Bot 共用一台电脑、同一套文件和登录状态，「The screens are separate work surfaces, not separate security boundaries」：每个 Bot 的屏幕只是各自的工作区，不是安全边界。记忆按角色分了作用域，权限并没有跟着分。

写入这一环没有任何把关。泄露的提示词要求 agent「don't narrate a save or ask permission for an ordinary one」：普通的写入不用说出来，也不用请示。官方安全文档写明，自动审查「doesn't review every side effect. Memory writes and most settings changes are examples.」：记忆写入不在审查范围内。对照之下，Cursor 自家的 IDE 反而更谨慎，自动生成的记忆要用户审批后才保存。

Grok Bot 后来的一次改版，把记忆和会话彻底解耦：同一个 Bot 可以开多个对话，新对话不带旧的聊天记录，但保留记忆。

趋同的是底座。真相源都是明文文件，没有一家把向量数据库当记忆的主存储，向量最多只做索引。能看到的个人化也都发生在文件和索引层：记住一个偏好，就是往文件里写一行。讲解 Muse 文件系统的那位开发者原话是：

"The model's weights stay unchanged."

模型的权重没有变化。

各家的实现方式，走的都是开源 personal agent OpenClaw 开出的这条路线。OpenClaw 今年一月前后火起来，记忆就是 workspace 里的一组 markdown 文件：人格写在 SOUL.md，用户画像写在 USER.md，长期记忆写在 MEMORY.md。Muse 的家目录里恰好是同一组文件名，Meta 超级智能实验室的 Nat Friedman（前 GitHub CEO）在 X 上也承认得很痛快：

"we built muse from scratch, but it is definitely heavily inspired as a product by openclaw."

Muse 是我们从零写的，但在产品上确实深受 OpenClaw 启发。

后台离线整理也在趋同。今年五六月，Anthropic 和 OpenAI 前后脚把各自的记忆整理机制命名为 Dreaming，当时这还是实验室平台和 ChatGPT 里的功能；到九月，它已经出现在四家 personal agent 里的三家，Muse 的那个目录干脆就叫 dreams。

选型各异的地方集中在三处：原始数据存不存、什么时候写入、记忆归谁。这三处没有对错，是各家面对的约束不同。

七、记忆怎么实现：由数据敏感度、时效和协作范围决定

把四家的选型倒推回去，能看到三个约束在起作用：数据有多敏感，记忆要多快生效，有多少个 agent、多少个人要共用这份记忆。

数据敏感度决定原始数据存不存

邮件、IM、日历这类第三方账号数据，敏感度高、体量大，有三种做法：

只存派生摘要，原件联邦检索 —— Town 的做法。适合用户对数据副本很敏感、源系统自带可用搜索接口的场景。代价是召回受限于第三方搜索，跨源关联也难做
按需取用，用过即留 —— Muse 的做法。默认不整库同步，用到的内容会沉淀进记忆。配合 claim 级溯源，至少能追溯一条记忆来自哪条原始消息
复制并建索引 —— Instinct 的做法。检索能力最强，可以跨邮件、日历、聊天做关联。代价是平台手里有一份完整副本，删除就得做成和断开连接同样明确的操作，Instinct 现在两者还是分开的

数据源是自家产品里的对话和行为时，敏感度的约束就松得多，复制并索引基本是默认选项，难点转移到下面两个约束上。

时效要求决定同步写入还是异步批处理

偏好必须当场生效 —— 比如用户刚说「以后别订靠窗座位」，下一轮就得用上。这种场景要会话中同步写入，Grok Bot 和 Muse 都是这样。风险是一次对话里的临时说法会直接进入记忆，写进去的东西需要后续有人核验
能接受隔天生效，更看重记忆质量 —— Instinct 的写读分离更合适。会话 agent 只读，质量控制集中在整理环节，每次改动都是一条可 diff、可回滚的 git 提交。代价是一条偏好要隔天才生效
两者都要 —— Muse 的做法是折中：会话中先写日志和 MEMORY.md，后台每小时回原话核验，决定哪些条目能升级成长期事实

整理频率是同一个约束的另一面。每小时一次能更快清掉错误，每天一次成本更低；完全不整理的 Grok Bot，写进去的条目只做去重，没有合并和淘汰，时间一长记忆会越来越杂。

协作范围决定作用域和权限怎么划

单用户、单 agent —— 一人一份记忆，Town 和 Muse 都是这样，作用域问题基本不存在
单用户、多 agent 分工 —— Grok Bot 的场景。按角色划作用域，能让法务 Bot 和财务 Bot 各拿各的上下文；但只要有共享层，就得同时设计权限，否则就是 Grok Bot 现在的状态：记忆分了作用域，权限没有跟着分
多用户之间协作 —— Instinct 已经走到这一步

9 月 9 日 Instinct 上线了 Trusted Person 网络，你的 Instinct 可以直接找你配偶、同事的 Instinct 约时间、订餐厅。两周后又支持了文件直传：

"The receiving agent receives the original file in its workspace, and can analyze it, edit it, or use it in ongoing work."

接收方的 agent 会在自己的工作区里收到原始文件，可以分析、编辑，或者用在正在进行的事情里。

Shinn 说上线一周，Instincts 之间已经协调了超过 30 万次。按外界还原的 Instinct 架构，每天的后台整理会读工作区里的内容，这些文件很可能就此进入你的记忆。如果是这样，这就是四家里第一个跨用户的记忆写入通道：另一个人的 agent，可以往你的记忆里写东西。

跨用户写入的合理做法，是让外部内容先进一个隔离区，打上来源标记，再由整理环节决定能不能进入记忆。四家里目前还没有哪一家公开过这样的设计。

八、仍在探索的实现：检索方式、溯源粒度、派生内容撤回

底座收敛了，但有三处实现四家给出的答案完全不同，也都还没有定论。

检索：关键词、向量还是联邦检索

四家用了三种检索方式。Instinct 只用关键词加别名，Muse 用 Postgres 里的向量索引，Town 调用第三方服务的搜索；Grok Bot 直接 grep 文件，也属于关键词检索。

个人记忆有两个特点让关键词检索够用：规模小，几百到几千个文件；实体名高度确定，人名、店名、航班号都不会有歧义。关键词的问题是同义改写召回不到，Instinct 的解法是在写入侧补别名。向量检索解决了同义问题，但结果不好解释，也不好回滚。哪种方式更适合 personal agent，现在还看不出来。

溯源：从页级到 claim 级

溯源（provenance）要回答的是 agent 能不能说清一条记忆从哪来。Town 的 wiki 页面挂了来源，粒度到页；Muse 做到了逐条记忆、带消息 ID，是四家里粒度最细的。

但 Muse 的核验能核「这句话有没有出处」，核不了「这个推断公不公平」。一位科技媒体的评测者只授权它读邮箱，得到的是一份「distorted image of my life」，一幅扭曲的生活画像。

实际事故里，agent 连事实的来源都说不清。Muse 的 Mac 版能读取系统自带的信息 App，一位科技记者收到 Muse 主动推送的选题建议，素材是他刚和播客搭档聊过的内容；Muse 自称来源是「设备通知」，Meta 事后承认它「confused about how to explain the feature and gave an incorrect explanation」，把自己的功能解释错了。

Instinct 的例子更典型。一位用户问起一封 Gerber 索赔信，Instinct 报出了他的中间名、地址和一笔 574 美元的索赔，说是用户拍照发过来的；用户回复中间名不对、地址没住过、也没发过照片。Instinct 接着这样解释：

"The Gerber image got crossed into your thread somewhere on the delivery side. That's on me for running with it."

那张 Gerber 的图片是在投递环节串进了你的对话。是我不该顺着它往下讲。

Shinn 两天后发帖定性为幻觉，不是数据泄露。无论哪种，agent 都先生成了一段「你发过一张照片」的经历，被戳穿后又当场编了一个系统故障来解释它。coding agent 的记忆来源基本就是这个仓库和这段对话，出了错翻一下就知道；personal agent 的记忆来自十几个连接器、每夜的整理、别人的 agent，来源可追溯在这里第一次成了必须解决的问题。

撤回：派生内容最难删

遗忘可以分成三层，四家在每一层的做法都不一样：

原始数据 —— Instinct 断开连接器不等于删除，要另外去 Workspace 页面里操作；Muse 删掉原始内容后，从中学到的信息可能仍在
记忆条目 —— Town 和 Muse 都能看、能改、能删；Grok Bot 能删能改，但没有界面；Instinct 只有明确的否定会被忘掉，旧版本还留在 git 历史里
派生内容 —— 只有 Muse 设计了级联撤回，对外承诺仍是尽力而为

第三层是难点所在。离线整理的本职工作，就是把多条原始记录合成为更高层的判断：画像、人物页面、dream、长期指引。从结构上看，整理做得越勤，派生内容越多，一条错误记忆被引用、被综合进别处的机会也越多。

一条错误记忆进去以后有多难清出来，Town 的 CEO 在 AI Engineer 大会的演讲里讲过一件自己的事：

"one piece of information there is incorrect cuz LLM made a mistake and then it like poisons it forever. I have a personal wiki that thinks my agent's name is Apex right now, but I renamed my agent a month ago to Ivy."

里面有一条信息是错的，因为模型犯了个错，然后它就永远污染下去了。我的个人 wiki 到现在还以为我的 agent 叫 Apex，可我一个月前就把它改名叫 Ivy 了。

要把派生内容撤回干净，每条派生内容都得记下自己是从哪几条原始记录合成的。Muse 已经给每条记忆记了出处，给每个推断也记上，是下一步要解决的问题。

九、记忆怎么用：常驻注入、按需检索与行为指引

存下来的记忆，最后要通过三种方式起作用：常驻在上下文里，被按需检索出来，或者改变 agent 的行为。

常驻注入与按需检索的分工

四家的共同做法是：每轮都可能用到的内容常驻，具体事实按需取。

常驻的部分各家不同。Instinct 每轮注入一页约 4,250 token 的记忆一页纸和一份约 8,750 token 的压缩回顾；Grok Bot 注入 profile 档；Muse 注入 dream 整理出来的长期指引；Town 注入 wiki 里相关的部分，定时任务运行时再加上全局记忆。共同点是常驻内容都经过压缩，放的是身份、近况、偏好和对待方式。

按需检索都做成了 agent 可以调用的工具：Muse 的 memory_search 和 memory_explain，Grok Bot 的 grep 和 ReadTranscript，Instinct 的关键词搜索，Town 的联邦检索。由 agent 自己决定什么时候查、查什么，记忆检索就成了 agent 工具调用的一部分。

记忆驱动主动性

三家官方都把记忆和「不等你开口就主动做事」绑在一起讲。Muse 的发布稿写的是「Muse also remembers what matters to a person, so it can make suggestions unprompted」。

Town 说 wiki 完善以后，「expect your Townie to become even more useful, accurate, and proactive」；Grok Bot 说 Bot 做过几次任务后，会「know when to ping versus keep going」，知道什么时候该来问你、什么时候该继续干。

Instinct 把这件事直接做成了记忆。每轮必注入的那页记忆一页纸里，单列了一节 Autonomy calibration：这个人能容忍 agent 自主到什么程度，什么事直接做，什么事先问。

关系记忆改变 agent 的行为

Muse 的 dream 和 Instinct 的 Autonomy calibration 是同一类东西，它记的是「这个人希望被怎么对待」。按 CoALA 的分法，这类记忆不好归类：它的内容是对一个人的判断，属于语义记忆；它的作用是决定 agent 下一次怎么做，属于程序性记忆。

在 coding agent 里，这一层是人写的显式程序性记忆。改代码前先跑测试、不要自动提交、哪些目录不能碰，我都写在 CLAUDE.md 里，团队把它当规则文件来管，改一次要过一遍评审。personal agent 把这件事交给了 agent 自己：它观察你一段时间，然后决定你是个什么样的人、该怎么跟你说话、哪些事可以不问就做。

Grok Bot 在这里选了更保守的一边。它把必须遵守的规则单独放进 Bot 的描述，官方还特意叮嘱：

"put safety boundaries in the description rather than in memory."

安全边界要写进描述，不要写进记忆。

这等于承认，自动写出来的记忆只是软约束，硬规则还得由人来写。Muse 和 Instinct 则让 agent 自己总结出该怎么对待你、该多主动，更省事，也更像一个真正了解你的助理，但这类记忆一旦学偏，用户很难发现是哪一条在起作用。

四家的存储已经收敛到同一套做法。接下来拉开差距的会在使用这一层：哪些记忆常驻、哪些按需取，哪些记忆有资格改变 agent 的行为，改变之前要不要经过人。
