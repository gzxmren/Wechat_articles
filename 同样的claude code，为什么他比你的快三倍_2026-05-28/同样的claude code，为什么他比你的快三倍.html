同样的claude code，为什么他比你的快三倍

同样是用 Claude Code 写一个功能，有人要来回确认十几次，有人三条命令就把任务扔进后台去跑了。

差距不在于谁的需求描述得更好，在于有没有用斜杠命令管住上下文、控住节奏。

这些命令负责的事情比你想象的多——管会话、压上下文、切模型、做审查、跑后台任务。

用好它们，才算真正在"指挥 AI 干活"，而不是陪它聊天。


一、会话基础命令
每天必用

最基础、最高频的一组命令。先把这组摸熟，日常使用就已经顺很多。

/clear 别名 /reset · /new

清空当前对话历史，释放上下文空间。切换任务时用，避免上一个需求影响新任务。

/init

在项目根目录生成 CLAUDE.md，扫描代码结构、注入项目背景知识。新项目建议先跑一次，相当于给 Claude 做一次项目入职。

/model [model]

会话中途切换模型，适合在“快速处理”和“深度推理”之间切换。

/model opus → 切到更强模型
/model sonnet → 切到日常主力模型
/model haiku → 切到轻量模型

/help

查看当前版本所有可用命令。Claude Code 更新很快，有疑问先查它，比记任何文章都可靠。

/config 别名 /settings

打开设置界面，调整主题、模型偏好、输出风格等全局配置。

/memory

编辑 CLAUDE.md 记忆文件，管理自动记忆和已保存条目。适合沉淀项目约定、编码规范和个人偏好。

/status

查看版本号、当前模型、账号状态和网络连通性。排查问题时第一步先看这个。

/doctor

诊断 Claude Code 安装和配置问题。遇到环境异常、插件异常、认证异常时，可以先跑一遍。

/copy

复制最新回复到剪贴板。有多个代码块时可以选择单独复制某一块，写文章或整理笔记时很省事。

/export [filename]

把对话导出为纯文本。适合把一次完整排查、一次方案设计、一次代码审查保存下来。

/theme/color

/theme 切换整体配色；/color 设置当前会话提示栏颜色。多个项目同时开时，用颜色区分会话很实用。

/feedback 别名 /bug

向团队提交使用反馈或 Bug 报告。

/exit 别名 /quit

退出 CLI。


二、上下文管理
效率倍增

Claude Code 用得稳不稳，很大程度取决于你会不会管理上下文。

/context 🔥 高频

用可视化方式查看当前 token 占用，并给出优化建议。准备压缩上下文前，建议先跑它。

/compact [instructions] 🔥 高频

智能压缩对话，而不是直接清空。可以明确告诉 Claude：哪些决策、接口、报错、测试结果必须保留。

/compact 只保留 API 设计决策和已完成接口列表

/btw <question> 🔥 高频

提旁支问题，不污染主线上下文。工作过程中临时查概念、确认语法、问一个小问题，用它非常合适。

/add-dir <path>

把其他目录加入当前会话的工作范围。monorepo 或跨仓库排查时很有用。

/rename [name]

给当前会话命名，方便之后恢复和区分任务。不带参数时，可以让它根据内容自动生成。


三、自动驾驶
进阶核心

这组命令的关键，是让 Claude 从“单轮回答”变成“围绕目标持续推进”。

/goal ★ 最强命令

设置会话级完成条件。Claude 会围绕目标持续工作，直到达到你指定的停止标准。

/goal 修复结账页面的单测，所有测试通过后停止
/goal clear
适合大型重构、批量修 Bug、全项目扫描、文档补齐等有明确完成标准的任务。

/effort [low|medium|high|xhigh|max|auto]

调节推理深度。轻量任务用低档，架构设计、性能分析、安全排查用高档。

/effort low # 改注释、改变量名
/effort high # 架构设计、性能优化
/effort max # 当前会话最强推理

/plan [description] New

进入计划模式：先探索代码库、拟定实施方案，确认后再动手。大任务建议先 plan，避免一上来就改错方向。

/fast [on|off]

开启快速模式，适合不需要深度推理的日常任务，减少等待。

/schedule [description] New

创建、更新、列出或执行定时例行任务。适合定期构建检查、周期性代码扫描、每日项目巡检。


四、容错与回溯
保命技能

/rewind 别名 /checkpoint · /undo

回退到上一个检查点，对话和代码文件一起回滚。AI 改坏文件或方向跑偏时，这就是保命键。

/fork [name] 别名 /branch

从当前节点分叉新会话，平行探索不同实现方案。适合技术选型、重构方案对比、试验性改造。

/resume [session] 别名 /continue

通过 ID、名字或选择器恢复历史会话。长任务断了之后，可以接着之前的上下文继续。


五、代码审查与安全
上线前必看

/diff

打开交互式 diff 查看器，浏览未提交改动和每轮对话造成的修改。提交前先看 diff，是用 AI 改代码的基本习惯。

/security-review New

分析当前分支未提交改动中的安全风险，例如注入、认证问题、敏感数据泄露等。上线前建议跑一遍。

/pr-comments [PR URL|number]

拉取 GitHub PR 的 reviewer 评论，自动识别当前分支对应的 PR，也可以手动传入编号或 URL。

/autofix-pr [prompt] 🔥 新功能

开启一个 Web 会话持续监听当前 PR，CI 失败或 reviewer 留言后自动修复。适合明确边界的自动修复任务。

/autofix-pr 只修复 lint 和类型错误，不改业务逻辑

/cost 别名 /stats · /usage

查看详细 token 用量和费用统计，适合复盘一次复杂任务到底消耗了多少。

/insights New

生成 Claude Code 使用分析报告，帮助你发现高频项目、交互模式和工作流瓶颈。


六、Agent · 扩展 · 集成
顶级玩家

/agents

管理子 Agent 配置和 Agent 团队。复杂任务可以拆给不同专长的 Agent 并行处理。

/mcp

管理 MCP Server 连接和 OAuth 认证。接入外部系统后，对应能力会变成可调用命令。

/mcp__github__list_prs # 示例：接入 GitHub MCP 后可用

/hooks

配置 Hook 脚本，在工具调用前后、Session 启动等事件触发自定义逻辑。适合团队规范和自动化工作流。

/permissions 别名 /allowed-tools

精细管理 Claude 的工具权限：允许、询问、拒绝。控制 AI 能操作什么、不能碰什么。

/sandbox

开关沙盒模式，在隔离环境里运行代码，减少对真实项目的影响。

/plugin/skills/tasks

/plugin 管理扩展插件；/skills 查看可用技能；/tasks 管理后台任务。

/remote-control 别名 /rc

让当前 CLI 会话可以从 Claude 网页或 App 远程控制，便于查看和干预终端任务。

/ide/install-github-app/install-slack-app

/ide 管理 VS Code / JetBrains 集成状态；后两个命令用于接入 GitHub 或 Slack。

/powerup New

通过交互式 Demo 学习 Claude Code 功能，新手熟悉工具时很适合。

⚡ 5 个内置技能（Bundled Skills）

它们本质上更像一组高级工作流 prompt，可以手动触发，也可能被自动触发。

/batch

批量处理：把任务拆成多个独立单元，每个单元交给后台 Agent 并行执行，适合大规模重构或批量修复。

/debug [description]

深度 debug 模式，开启更系统的问题定位流程。复杂 bug 不要只让它“看看”，可以直接进入 debug。

/loop [interval] [prompt]

循环执行指定任务，例如每隔几分钟检查部署状态，或者持续观察某个构建结果。

/simplify

让 Claude 简化代码，降低复杂度，提升可读性和维护性。

/claude-api

为项目加载 Claude API 参考文档，在检测到相关 SDK 时也可能自动激活。

功能

九、3 个可直接复用的工作流
🐛 工作流一：自动修复一批 Bug
1/effort high  拉高推理深度。
2/goal 修复所有 P0 Bug，单测全绿后停止。
3
途中用 /btw 快速确认某个函数行为，不打断主线。
4/context → /compact 保留关键决策，清理冗余上下文。
5
跑偏了就用 /rewind 回到上个检查点。
🔒 工作流二：上线前安全审查
1/diff
 浏览所有未提交改动，确认本次上线范围。
2/security-review
 扫描注入、认证、数据泄露等风险。
3/pr-comments
 拉取 reviewer 评论，逐条处理。
4/batch
 对同类问题批量应用修复。
⚖️ 工作流三：技术选型平行对比
1
先描述需求和约束，用 /plan 拟定方案框架。
2/fork 方案A-PostgreSQL 让 AI 完整实现一版。
3
回到主线，再 /fork 方案B-MongoDB 跑另一版。
4
对比两个分支的改动、复杂度、测试成本，再决定采用哪一版。
