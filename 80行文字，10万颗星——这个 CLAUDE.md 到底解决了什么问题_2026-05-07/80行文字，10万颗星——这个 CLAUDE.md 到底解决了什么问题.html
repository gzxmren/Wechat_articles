80行文字，10万颗星——这个 CLAUDE.md 到底解决了什么问题

我用 Claude Code 写了一年代码，有一段时间特别抓狂。

不是 bug，是一种更难描述的感觉：它做了我让它做的，但不是我想要的。让它加个表单验证，它顺带重构了整个表单组件；让它修一个登录 bug，它把附近的注释也"清理"了；让它写个简单的工具函数，它给我搭了一个可扩展的插件架构。

每次都"更好"了。每次都让我头疼。

这不是 Claude 的问题，是我们对 AI 的理解出了偏差

我当时傻乎乎地以为，AI 编程助手跟搜索引擎一样——你问什么，它答什么。

错。

Claude Code 更像一个聪明到有点过头的初级工程师：充满热情、能力很强、但边界感极差。你说"帮我改这个函数"，它理解成"帮我把这块代码变得更好"，然后开始发挥创意。

Reddit 上有人把这种行为叫 confident junior engineer。聪明、快速、自信——但是不可靠。恰恰是那种需要你明确说"你只能动这一行，其他的别碰"的类型。

2026年1月，Andrej Karpathy 发了一条推文，把这个问题说得非常具体：

"模型会替你做出错误的假设，然后一路跑下去——不管理自己的困惑，不寻求澄清，不暴露矛盾，也不在该反驳的时候反驳。"

"它们特别喜欢把代码搞复杂，堆抽象层，明明100行能解决，偏要搞出1000行的庞然大物。"

第二天，一个叫 Forrest Chang 的开发者，把这些抱怨变成了一个80行的文件——CLAUDE.md，放进 GitHub 仓库。几周后：110k 星。

我第一次看到这个数字，呆了好几秒。80行文字，零代码，比很多运营了好几年的开源框架还火。这事本身就值得认真想一想。

先把这80行读懂：它在管什么

这个文件的核心，是四条行为约束。每一条针对一类 AI 失控模式。

我把它翻译成大白话：

第一条：编码前先想清楚（Think Before Coding）

原文核心：

State your assumptions explicitly. If uncertain, ask. If multiple interpretations exist, present them — don't pick silently.

说人话就是：不许自作主张，不确定就问，有多种解读就都说出来让我选。

这条针对的是 AI 最常见的失控模式——它脑子里有一个它自己选的方案，然后闷头实现，完成之后你才发现它理解错了方向。

你改需求说了三个小时，它动手之前沉默地选了一个解读方式，然后给你交付了一个不是你要的东西。

这条规则强制它在动手前"暴露假设"——把它的理解说出来，让你确认或纠正。

第二条：简单优先（Simplicity First）

原文核心：

No features beyond what was asked. No abstractions for single-use code. If you write 200 lines and it could be 50, rewrite it.

说人话就是：我没要的别加，能50行解决的别写200行。

这条针对的是 AI 的"过度工程"倾向。AI 见过太多复杂的代码库，它的默认审美是"可扩展、可配置、有抽象层"。这在大型项目里可能是优点，但在你只需要一个临时脚本的时候，它给你的是一个框架。

文件里有一个很好的自问句："一位资深工程师会觉得这太复杂了吗？如果会，就简化它。"

第三条：精准修改（Surgical Changes）

原文核心：

Don't "improve" adjacent code, comments, or formatting. Don't refactor things that aren't broken. Every changed line should trace directly to the user's request.

说人话就是：只动我让你动的，周围的代码给我放着别碰。

这条针对的就是我开头说的那个痛点——让它改一个函数，它把整个文件重新格式化了；让它修一个 bug，它顺带"优化"了附近的注释。

Diff 变得巨大，Code Review 变成噩梦，你根本不知道它在你不知情的情况下动了什么。

第四条：目标驱动执行（Goal-Driven Execution）

原文核心：

Transform tasks into verifiable goals: "Add validation" → "Write tests for invalid inputs, then make them pass"

这是四条里面最有价值的一条，也是 Karpathy 的核心洞察：

不要告诉 AI 做什么，给它成功标准，然后看着它执行。

命令式 vs 声明式的区别，放到 AI 编程里，效果差异非常明显：

❌ 命令式（告诉它做什么）
✅ 声明式（给它成功标准）
"加个输入验证"
"写测试覆盖无效输入，然后让测试通过"
"修这个 bug"
"写一个能复现 bug 的测试，再修它"
"重构 X"
"确保重构前后测试全部通过"

区别在于：命令式的结果你没法验证，声明式的结果 AI 自己就能验证。 有了明确的成功标准，它可以自主循环，而不是每做一步都来问你"对了吗"。

真正的问题：为什么80行文字能值110k星

技术上没什么神奇的。CLAUDE.md 本质上就是 Claude Code 的项目级 System Prompt——每次启动，Claude Code 会自动读取项目根目录里的这个文件，把里面的内容作为上下文。

说人话就是：给 AI 一份入职手册，它每次启动都会重新读一遍。

那为什么这么简单的东西会火成这样？

我想了很久，最后的答案是：它击中了一个正在被数百万开发者同时经历的痛点，而且给了一个任何人都可以立刻用上的解决方案。

不需要改代码，不需要学新工具，不需要等 Anthropic 更新模型。curl 一行命令，文件拉下来，问题解决70%。

这是一种新型开源。Karpathy 把它叫做 idea file——分享的不是代码实现，而是思想本身。每个人拿走这个思想，根据自己的项目定制，AI 会根据自身上下文执行。

开放的不是代码，是认知。

这件事让我意识到：AI 时代的"基础设施"，有一部分是提示词。就像每个团队都有代码规范、有 linter 配置，以后每个项目都会有 CLAUDE.md——定义 AI 在这个项目里的行为边界。

怎么用：从复制粘贴到真正属于你的 CLAUDE.md

方式一：直接拉取原始文件（最快）

新项目：

curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md

已有项目（追加到现有 CLAUDE.md）：

echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md

注意：这里用 >> 而不是 >，追加而不是覆盖。如果你已经有项目配置，别把它冲掉了。

方式二：用 Claude Code 插件全局生效（推荐）

/plugin install andrej-karpathy-skills@karpathy-skills

这样每个项目都自动继承这套规则，不用每个仓库单独配置。

但原版还不够用：给出海开发者的定制版

原版 CLAUDE.md 是通用的。对于做出海 SaaS 的开发者，我在原版基础上加了一层出海专属约束。

这是我实际在用的完整版本：

# Behavioral Guidelines (Based on Andrej Karpathy's observations)

## 1. Think Before Coding
Don't assume. Don't hide confusion. Surface tradeoffs.

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First
Minimum code that solves the problem. Nothing speculative.

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- If you write 200 lines and it could be 50, rewrite it.

Ask: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes
Touch only what you must. Clean up only your own mess.

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution
Define success criteria. Loop until verified.

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

# Project-Specific: Overseas SaaS Constraints

## Money & Payments
- All monetary values stored as integers (cents). Never floats.
- Stripe Webhook handlers MUST be idempotent — check event_id before processing.
- Payment state machine is one-directional only. No rollback from `succeeded`.

## Time & Internationalization
- All timestamps stored as TIMESTAMPTZ (with timezone). Never naive datetime.
- Display layer handles timezone conversion; storage layer stays in UTC.
- User-facing strings go through i18n. No hardcoded English in UI components.

## Security Defaults
- Passwords: bcrypt only, cost factor >= 12. SHA/MD5 is not acceptable.
- JWT: access token 15min, refresh token 7 days with rotation.
- All external inputs validated with zod schema before use.
- SQL: parameterized queries only. No string concatenation.

## When You Spot a Risk
If implementing a request would introduce a security vulnerability or production risk,
say so BEFORE implementing. Don't silently make it "safe" — explain the tradeoff.

这个文件放在项目根目录。Claude Code 启动就读。

关键细节： 把出海约束单独放在一个 section，用 --- 分隔。这样和通用规则之间有清晰的边界，以后迁移到新项目时，通用部分直接复制，项目特定部分按需修改。

踩坑实录

坑一：文件太长，关键规则失效

我第一版 CLAUDE.md 写了将近 400 行。以为越详细越好。

然后发现 Claude 开始忽略里面的安全规则——它能遵守前 100 行，后面的内容像是没读到一样。我卡了整整一个下午才想明白原因：Claude 的注意力不是均匀分布的，System Prompt 越长，后面的内容权重越低。

解决方法：把 CLAUDE.md 控制在 150 行以内。最关键的规则放在最前面。剩下的细节，用项目内的具体代码注释来补充，而不是全堆进 CLAUDE.md。

坑二："精准修改"这条规则，我一开始理解反了

看到 Surgical Changes 这条，我以为它的意思是"让 AI 少做事"。所以我在 CLAUDE.md 里加了一句："Don't proactively fix bugs you notice"。

结果适得其反——它发现了一个明显的安全漏洞，因为我的规则它没提，然后就真的没提，我后来自己发现的时候差点上线了一个有 SQL 注入风险的接口。

正确理解是：精准修改管的是"范围"，不是"信息"。它不应该悄悄改你没让它改的代码，但它发现了问题应该主动说出来，而不是动手改。

改法：加上 "If you notice unrelated dead code or security issues, mention it — don't fix it silently."

总结

80行文件，110k星，不是因为它有多技术含量，而是因为它精准地说出了每个用 AI 写代码的人都踩过但说不清楚的那个坑。

AI 不缺能力，缺的是边界。CLAUDE.md 做的事情，就是给 AI 划边界——哪里能动，哪里不能动，做到什么算完成。

这也是我现在最深的感受：AI 时代，写好提示词的能力，和写好代码一样重要。甚至在某些场景下，更重要。

最后问你一件事

你现在 CLAUDE.md 里，有没有"Goal-Driven Execution"这一条——把任务定义成可验证的成功标准？

我很好奇：在你的实际项目里，这种声明式描述任务的方式，有没有让 Claude Code 的执行质量发生明显变化？还是说你发现了它在某些场景下反而不好用？
