不用LangChain、不用CrewAI，50行Python写个能用的AI Agent：就一个while循环

 


我每天都在用 Claude、Codex、Cursor、Gemini、Copilot 或 Junie，但我仍然说不出"聊天机器人"究竟在哪一行代码变成了"智能体"。我无法解释是什么让它们成为智能体。所以我决定从零写一个最小版本，亲自搞清楚。

对我来说，理解新概念的最佳方式就是动手实现它，然后向别人解释。

我们将从 50 行 Python 代码开始，接入 OpenAI，通过 Ollama 切换到本地模型，构建一个混合模式（两者都用），添加工具，实现 MCP，最后与 Claude CLI 对比。到最后，你会清楚看到底层究竟发生了什么。

没有LangChain，没有LangGraph，没有CrewAI。只有Python、一个LLM，和一个while循环。

智能体的本质：不是模型变聪明了，是循环

动手之前，先明确我们要造什么。

一个 AI 智能体是这样一个程序：

  1. 1. 接受用户的高层级任务
  2. 2. 推理下一步该做什么
  3. 3. 执行行动（调用工具、搜索网页、读取文件）
  4. 4. 观察结果
  5. 5. 决定继续执行还是返回最终答案
  6. 6. 维护对话历史，让每个决策都建立在之前的基础上

一个AI智能体和普通LLM调用的区别，不在于模型本身，而在于结构：

普通的 LLM 调用是一次性操作：你发送 prompt，得到回复，结束。智能体不同，因为它会循环。它接收高层级任务，推理下一步，执行行动，观察结果，然后继续，直到任务完成。

这种"思考 → 执行 → 观察 → 决定"的重复循环，就是把语言模型变成智能体的关键。

如今大多数智能体遵循一种叫 ReAct（Reason + Act，推理+行动）的模式。LLM 不会直接跳到最终答案。它先产生一个关于"该做什么"的思考，然后是一个行动（工具调用），接着等待观察结果，再决定下一步。

模型没有意识。没有任何有意义的自我反思。它拥有的是对话历史——它执行的每一个行动和获得的每一个结果，都存在于上下文窗口中。ReAct 模式把这些变成了类似自我反思和自我修正的行为。而且这确实有效。

每个循环发生的事如下：

  1. 1. 你把当前对话发送给 LLM：系统 prompt、用户消息、以及之前的任何工具结果
  2. 2. LLM 返回最终答案，或它想执行的工具调用列表
  3. 3. 如果是最终答案，任务结束
  4. 4. 如果是工具调用，你执行它们，将结果追加到对话中，回到第 1 步

这就是整个架构。

50行核心代码：OpenAI版本

def run_agent(task: str, client: OpenAI, model: str = "gpt-4o-mini") -> str:
    messages = [
        {
            "role": "system",
            "content": (
                "You are a helpful assistant. Use tools when needed. "
                "When you have a final answer, respond without calling any tools."
            ),
        },
        {"role": "user", "content": task},
    ]

    while True:  # ← 这就是全部"智能"的来源
        response = client.chat.completions.create(
            model=model,
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",
        )

        message = response.choices[0].message
        messages.append(message)

        # 决策点：模型说"我答完了"，还是"我要调工具"？
        if not message.tool_calls:
            return message.content  # 没调工具 → 任务完成

        # 调了工具 → 执行，追加结果，继续循环
        for tool_call in message.tool_calls:
            name = tool_call.function.name
            args = json.loads(tool_call.function.arguments)
            print(f"  > calling {name}({args})")

            fn = TOOL_FUNCTIONS.get(name)
            result = fn(**args) if fn else f"Unknown tool: {name}"

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": result,
            })

关键代码行是 if not message.tool_calls。如果模型返回文本而没有请求任何工具，它就是在发出信号：已有足够信息作答。智能体退出并返回该文本。如果模型请求工具，智能体执行它们，将结果追加到对话历史，然后把一切发回模型进行下一轮。

messages 列表是智能体的短期记忆。每个工具调用和每个结果都被追加进去。当 LLM 决定完成时，它已经看到了自己做过的每一件事，以及从中学到的所有东西。

系统 prompt 也很重要。它是方向盘。它告诉模型何时使用工具、何时停止、最终答案应该长什么样。在真实生产智能体中，这个系统 prompt 往往非常大，我们从 Anthropic、Apple 等公司的偶尔泄露中已经见识过了。

定义工具：让LLM"长出手"

三个简单工具让概念具体化：当前日期/时间、计算器、和一个天气占位符。在真实智能体中，你会把占位符换成实际的 API 调用。

def get_current_date() -> str:
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

def calculate(expression: str) -> str:
    try:
        result = eval(expression, {"__builtins__": {}}, {})
        return str(result)
    except Exception as e:
        return f"Error: {e}"

def get_weather(city: str) -> str:
    return f"Weather in {city}: 72°F, partly cloudy"  # 占位符，可换真实API

TOOL_FUNCTIONS = {
    "get_current_date": get_current_date,
    "calculate": calculate,
    "get_weather": get_weather,
}

工具 schema 告诉 LLM 有哪些工具可用。这份 JSON 就是模型在决定调用哪个工具、用什么参数时看到的内容：

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_current_date",
            "description": "Returns the current date and time",
            "parameters": {"type": "object", "properties": {}, "required": []},
        },
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "Evaluates a math expression and returns the result",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {
                        "type": "string",
                        "description": "A Python math expression, e.g. '2 + 2' or '100 * 0.15'",
                    }
                },
                "required": ["expression"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Gets current weather for a city",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "City name"}
                },
                "required": ["city"],
            },
        },
    },
]

运行一下子：

task = "What's today's date? Also, what is 15% of 900? And what's the weather in Beijing?"
answer = run_agent(task, client)

输出：

  > calling get_current_date({})
  > calling calculate({'expression': '900 * 0.15'})
  > calling get_weather({'city': 'Beijing'})

Answer: Today is 2026-05-10 19:56:22. 15% of 900 is 600.
The weather in Beijing is 32° and partly cloudy.

第一轮，LLM 识别出需要的全部三个工具，逐个调用，获取结果，然后组装成最终答案。没有框架。没有编排层。

通过 Ollama 将云端 API 替换为本地 LLM

Ollama 暴露了 OpenAI 兼容的 API，这意味着同样的 agent 代码只需改一处就能在本地模型上运行：

ollama_client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",  # 占位符，Ollama不校验
)
answer = run_agent(task, ollama_client, model="qwen3.5")

启动Ollama：

ollama pull qwen3.5
ollama serve

之后，agent 完全离线运行。我用这个来测试新工具，不用消耗 API 额度；也用于数据不该离开本机的场景。

构建混合模式（本地编排，云端委托）

你可以本地编排，只在任务真正需要时才付费调用云端。默认用本地模型运行 agent，但给它一个工具，用于在复杂推理任务时调用云端模型。本地模型处理循环和简单工具。遇到需要深度推理的，它委托出去。

def ask_cloud_expert(question: str) -> str:
    """把难题扔给GPT-4"""
    cloud_client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
    response = cloud_client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": question}],
    )
    return response.choices[0].message.content

把它加入 TOOL_FUNCTIONS，schema 加入 TOOLS。现在运行：

answer = run_agent(
    task="What's 5+2? Also, explain the philosophical implications of the Ship of Theseus paradox.",
    client=ollama_client,
    model="qwen3.5"
)
task = "What's 5+2? Also, explain the Ship of Theseus paradox."
# 本地模型：5+2用计算器，哲学问题→调用ask_cloud_expert

本地模型处理 （通过计算器工具），意识到哲学问题超出它的能力，于是调用 ask_cloud_expert() 从云端获取正经答案。你只付一次云端 API 调用的钱，而不是几十次。

硬编码工具的局限，MCP来解决

上面这个 agent 缺少一样东西：跨项目共享或复用工具的能力。所有东西都是硬编码在脚本里的。如果我想让另一个 agent 用同样的工具，我得复制粘贴。如果我想用别人的工具，我也得重写。

MCP（Model Context Protocol，模型上下文协议），Anthropic 2024年11月推出的标准，解决的就是这个：让任何Agent从任何服务器发现工具，不管工具在哪、谁写的。

你的Agent变成MCP客户端。不再硬编码，而是问服务器："你有什么工具？"拿到描述，直接传给LLM。Agent逻辑完全不变，变的只是工具从哪来。

MCP服务器端更简单，10行代码：

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("mini-tools")

@mcp.tool()
def to_uppercase(text: str) -> str:
    """Convert text to uppercase."""
    return text.upper()

@mcp.tool()
def count_words(text: str) -> int:
    """Count words in a string."""
    return len(text.split())

if __name__ == "__main__":
    mcp.run()

Agent调用时自动拉起，执行，返回。你可以把它部署到任何地方，Agent代码不用改。

Claude Desktop、Cursor、任何MCP兼容的Agent都能用你的工具。写一次，所有人用。 这才是生态该有的样子。

框架什么时候用

你不需要 LangGraph 来理解 agent 是什么。你需要它，当重试、检查点、审批门不再是可选项的时候。

上面的代码没有错误处理。工具抛异常，agent 崩溃。没有重试逻辑。没有风险操作前暂停等人批准的方式。没有单会话之外的记忆。没有生成子 agent 并行工作的能力。那LangChain、LangGraph、CrewAI是干什么的？

不是让你"能做"Agent，是解决"做好"的问题：

  • • LangGraph：把Agent建模为显式状态机。节点、边、条件跳转。换来检查点（失败从哪恢复）、人工介入门、完整可观测性。
  • • CrewAI/AutoGen：多Agent编排。研究员、写手、审稿人分工，定义他们怎么通信。适合复杂任务需要不同角色、不同模型的场景。
  • • Claude Agents SDK / OpenAI Assistants API：托管运行时。你把状态管理、线程处理交给平台，上线快，控制少。

50 行版本是草图。LangGraph 是同样的草图，但变成了有正经承重墙的建筑。

生产用框架，理解从循环开始。

构建这个50行Agent可以学到什么

以前看Agent框架的文档，总觉得它们在故意模糊边界——"认知架构""推理引擎""工具编排"... 现在我知道这些词背后是什么了。

我能看到Agent在哪可能卡住：上下文窗口满了怎么办、工具描述写得不好导致选错、加太多工具反而让决策混乱。我知道Claude Code启动子Agent时发生了什么，Cursor重试失败操作时发生了什么。

有些项目我会用LangGraph或Claude SDK——它们解决的是我不想重新实现的真问题。但有些会从这个 50 行版本开始，因为我确切知道它做什么，我能修改它而不用跟我不理解的抽象打架。

当你伸手拿框架时，你会知道它在替你做什么。当你不需要时，你不会引入一个无法调试的依赖。

这就是理解的价值。
