Claude Code 使用系列 04｜Skill：把 Claude 从"通才"变成每个领域的"专才"

最近让 Claude 帮我起一份技术评审稿，已经记不清是第几次了——每次出来的初稿都"差点意思"。这次漏了容量评估、上次漏了非目标边界、还有一次直接跳进了实现细节没先讲核心概念。每一次我都要把那段熟悉的 prompt 再贴一遍：

"先对齐目标和非目标、再讲粗粒度主逻辑、关键概念先定义、最后才进细化方案。每一版必须包含：背景、目标、非目标、核心概念、方案对比、容量评估、风险点、灰度策略……"

模型不是不听话，是它根本不知道我团队评审稿的标准长什么样。

问题不在模型记性，在我把"流程"塞错了地方：写在 CLAUDE.md 里太散、做成 slash command 太死、扔进项目文档太重，每一种都不对——所以 LLM 时灵时不灵。

直到我把这段 prompt——连同它配套的反例、检查清单、过往技术评审的样本——打包成一个 skill，模型才第一次稳定地把每个环节都写到位。从那之后，新人 push 一句"帮我起一份 X 服务的技术评审稿"，Claude 自动找到那个 skill，按上面的流程走，连容量估算的占位表格都自己补了。

这就是 skill 该出场的时刻。

一、Skill 是什么：一个被自动加载的文件夹

机制层面就一句话：skill 是一个有约定结构的文件夹，agent 启动时只读它的"目录页"，触发后才把全文加载进上下文。

Anthropic 官方在 Engineering Blog 的发布博文（Barry Zhang、Keith Lazuka、Mahesh Murag 合著，2025-10-16）里反复用一个比喻：

"Building a skill for an agent is like putting together an onboarding guide for a new hire."

为 agent 构建一个 skill，就像为一位新员工拼出一份入职指南。

这个比喻不是修辞——它是 skill 设计哲学的核心：既要让新人能找到对的那一页（路由），又不能把全本手册压到他面前（上下文）。

Skill 的最小骨架

一个 skill 长这样：

my-skill/
├── SKILL.md            # 入口：frontmatter (name + description) + 主流程
├── scripts/            # 可执行脚本，给 agent 直接跑（不进上下文）
├── references/         # 重型文档，按需读
└── assets/             # 模板、schema、数据

SKILL.md 的 frontmatter 在 agentskills.io 开放标准 和 Anthropic 官方文档 里只有两个必填字段：

字段 必填 约束
name 是 ≤64 字符，小写字母 / 数字 / 连字符。开放标准额外要求与父目录名一致；Anthropic 额外禁止保留字 anthropic / claude
description 是 ≤1024 字符，描述"做什么 + 何时用"。不能含 XML 标签
license / compatibility / metadata / allowed-tools 否 全部可选

最小可用示例（来自 Anthropic 官方 anthropics/skills 仓库的 pdf skill）：

---
name: pdf
description: Use this skill whenever the user wants to do anything with PDF files. This includes reading or extracting text/tables from PDFs, combining or merging multiple PDFs into one, splitting PDFs apart, rotating pages, adding watermarks, creating new PDFs, filling PDF forms, encrypting/decrypting PDFs, extracting images, and OCR on scanned PDFs to make them searchable. If the user mentions a .pdf file or asks to produce one, use this skill.
license: Proprietary. LICENSE.txt has complete terms
---

这段 description 在说什么？

每当用户想对 PDF 文件做任何事时，使用此 skill。包括：从 PDF 读取或提取文本 / 表格、把多个 PDF 合并成一个、拆分 PDF、旋转页面、加水印、新建 PDF、填 PDF 表单、加密 / 解密 PDF、提取图片、对扫描版 PDF 做 OCR 使其可搜索。如果用户提到 .pdf 文件或要求生成一份，就用这个 skill。

注意这一段 description——300 多字符，把"做什么、何时用、关键动作清单"全列出来，几乎就是一份微型的路由表。这是官方推荐的写法。

核心机制：Progressive Disclosure（渐进式披露）

这是 skill 工程价值的全部所在。Anthropic 官方对 skill 设计了三层加载：

层 加载时机 Token 占用 内容性质
Metadata（name + description） agent 启动时常驻 ~100 token / skill 路由触发器
SKILL.md 主体 skill 被触发后加载 建议 < 5000 token 主流程 + 路由表
References / Scripts agent 真正需要时才读 不进上下文 重型文档、脚本

按这个算账，你装 50 个 skill，启动只付 ~5000 token 的开销——大约相当于一篇短文章。具体哪个被触发、付哪个的全文。如果不分层，把所有内容都堆进单个 SKILL.md，5 万字常驻上下文就崩了——模型注意力被严重稀释，多 skill 共存时连锁退化。

skill 像一座大型图书馆。进门不是把全馆几十万本书堆在借阅台上，而是分层暴露——大厅看分类索引（文学、科学、历史各在几楼），到对应楼层再看子分类，走到具体书架前才把那一本翻开。每一层只暴露下一层的入口，不暴露内容。skill 的 metadata 就是大厅的索引牌，SKILL.md 是楼层的索引牌，references/ 里才是真正的"书页"，只在你走到面前那一刻才打开。

Skill 在生态里的位置

Anthropic 工程师 Barry Zhang（也是 skill 原型作者）在 X 上对 skill 的来历有一句话定性（原帖）：

"Skills actually came out of a prototype I built demonstrating that Claude Code is a general-purpose agent. It was a natural conclusion once we realized that bash + filesystem were all we needed."

skill 实际上来自我做的一个原型——它证明了 Claude Code 是一个通用 agent。一旦我们意识到 bash + 文件系统就是我们所需要的全部，这就成了一个自然的结论。

skill 不是为 Claude.ai 设计的新功能，是在 Claude Code 上证明"bash + filesystem 就够了"之后倒回去做的——所以 skill 的本质特别朴素：给一个会用 bash 的 LLM 塞一个有结构的文件夹。

回到 Claude Code 这一侧，skill 跟其它扩展机制的关系，可以拉一张表对齐——这也是系列 01（hook）和 02（settings）之后，第三件该理清的事：

机制 解决什么 与 skill 关系
Prompt 单次会话的临时指令 Skill 是"持久化、按需加载"的 prompt
CLAUDE.md 项目级常驻上下文（事实/约定） 当 CLAUDE.md 的某段从"事实"变成"流程"时，就该抽成 skill
Slash command 用户主动触发的快捷指令 已被 skill 合并：.claude/commands/X.md 和 .claude/skills/X/SKILL.md 等价；skill 是 command 的超集
Hook（系列 01） tool 事件触发的强制脚本 skill frontmatter 可配 hooks 字段限定生命周期
Settings（系列 02） 启动和运行时的配置 / 权限 skill 的开关与管控面之一
MCP 跨进程的工具 / 数据连接 互补：skill 教 agent "怎么做流程"，MCP 提供"做流程要调的工具"
Plugin 整包分发渠道 skill 是 plugin 可打包的资产之一

记住一个判断：当 prompt 开始重复、CLAUDE.md 开始膨胀、slash command 不够灵活、工程师每人一套口诀的时候，skill 就该上场。

description 是路由触发器，不是文档

这是 skill 工程化里被低估最严重的一条。

中文圈一位作者做过一个 650 次实验：同一个 skill，只改 description，把它的激活率从 37% 拉到 100%——20 倍差距。

写法 反例 正例
视角 "This skill helps you..."（介绍式） "Use when user mentions X / Load when..."（触发式）
关键词 "code review tool"（笼统） "Triggers on: code review, PR review, refactor suggestion..."（穷举触发词）
长度 一句话简介 3-5 句话 + 触发词清单 + 不适用场景
人称 第一 / 第二人称 第三人称客观描述 + 行为动词

Anthropic 官方 Authoring Best Practices 给的三条铁律：第三人称、含 what + when、关键词具体。

记住：description 不是给人读的"产品介绍"，是给 LLM 看的"路由表条目"。一个 skill 写得再好，description 写错了，模型永远不会调它。

二、值得装的 skill：从官方到职能清单

光讲机制没用，得给具体例子。挑 skill 实际上沿两条线走：要么按来源（官方 / 标杆个人 / 公司），要么按职能（开发 / 产品 / 设计）。下面把这两条线串起来看——所有数字都是 2026 年 6 月中旬的实时核对。

1. Anthropic 官方 anthropics/skills（17 个，14w star）

开放标准发布时的 reference implementation。按用途分四组：

  • 文档系：pptx / xlsx / docx / pdf — 让 Claude 真正能"做"一份能交付的 Excel / Word / PPT / PDF，不再只是输出 markdown 代码块
  • 创作系：canvas-design / algorithmic-art / brand-guidelines / theme-factory / slack-gif-creator — 画封面、做图、生成可交付海报、按品牌色调
  • 工程系：mcp-builder / webapp-testing / claude-api / frontend-design / web-artifacts-builder — 建 MCP server、用 Playwright 测网页、调 Anthropic API
  • 协作系：skill-creator / doc-coauthoring / internal-comms — 用 skill 写 skill 的自举案例 / 文档协作 / 内部沟通

第一次想造 skill 直接调 skill-creator——它按官方 Best Practices 带你过一遍 description 写法、目录结构、命名规范。

2. 标志性的个人作品

Garry Tan / garrytan/gstack（10.5w star）

这是 2026 年 3 月以来最值得关注的一个 skill 案例。Y Combinator 现任 CEO Garry Tan 直接把自己每天用的 Claude Code 配置开源，叫 gstack——23 个 slash command 各自对应一个"职能岗"：CEO / Eng Manager / Designer / DevEx / QA / Security / Release Manager / Doc Engineer / Browser 九大职能。

三个月冲到 10w+ star，Hacker News 双榜霸榜。一个掌管硅谷头部孵化器的 CEO 亲手开 skill repo——这件事本身就是"skill 已经不是程序员玩具"的最强证据。

但要补一句前提：gstack 是一个 CEO + 重度 vibe coder 的工作配置，把"评审 / 设计 / 安全 / 发布"全摊给 agent。普通工程师团队照搬不一定合适——你团队需要的可能就 5-6 个 skill，而不是 23 个。gstack 真正的参考价值是**"按职能岗划分 skill"的思路**，不是"把 23 个全装上"。

围观争议也是这个角度：Mo Bitar 在 X 上发了一个尖锐的视频指责"AI is making CEOs delusional"（AI 让 CEO 们产生了妄想），说 gstack 不过是"一堆 prompt 文件"——争议反过来证明了关注度，也提醒大家不要把别人的工作流直接当模板抄。

Jesse Vincent / obra/superpowers（21w star，14 个 skill）

资深工程师风格的 skill 框架，全部用 gerund form 命名：brainstorming（强制头脑风暴前置）、writing-plans（多步任务写实施计划）、test-driven-development（强制 TDD）、systematic-debugging、requesting-code-review（让 Claude 自己找 reviewer）、executing-plans、subagent-driven-development……每一个都是把"资深工程师的工作纪律"硬编码成模型行为。

三、几条 skill 工程化的最佳实践

机制和清单讲完，再讲怎么写。这部分把过去半年公众号写过的几个相关话题串起来看——skill 不是单独的一件事，是 AI 工程化基线的一环。

1. 把"事实"留给 CLAUDE.md，把"流程"抽成 skill

CLAUDE.md 适合放项目级的常驻事实——技术栈是什么、目录约定、命名规约、不准跑的命令。它一直在上下文里，模型每次对话都看得到。

skill 适合放触发式的流程——"写技术评审走 8 步、每步有自检规则"、"评审代码按 5 个角度看"、"做产品方案先对齐目标边界"。这些是只在做某件事时才需要的细节，常驻代价太大、不放出来又会"重复教模型"。

判断信号：当 CLAUDE.md 的某一节越写越长、最后看起来像个 workflow 而不是事实清单时，把它抽出来做 skill。

2. Hub-and-Spoke：SKILL.md 只放路由，细节进 spoke

我之前在公众号写过一篇关于 Perplexity Agent Skill 工程化方法论的解读，里面 Perplexity 那句话特别值得记住：

"If you write skills like you write code, you will fail."

如果你像写代码那样写 skill，你一定会失败。

代码追求稳定、可读、可复用；skill 追求"在恰当时机以最少 token 把模型行为搬到正确轨道上"。两者目标不同，原则自然相反。

具体的写法就是 hub-and-spoke：SKILL.md 是 hub，只放路由表 + 主流程概述 + 对 spoke 文件的引用；details / templates / 长清单全放进 references/ 目录，hub 在主流程里说"如果要做 X，去读 references/x.md"。模型只在真的需要时才去付 spoke 的 token 成本。

anthropics/skills 里的 pdf skill 就是这个模式的典型——SKILL.md 主体只几百行讲流程，遇到"填表单"路由到 forms.md、遇到"OCR 扫描件"路由到 ocr.md、复杂任务则交给 scripts/ 下的 Python 脚本。常驻只有 hub，spoke 按需读。这是一个 skill 能写得很重又不破上下文预算的关键。

3. 配合 hook 做强制校验（呼应系列 01）

skill 是"建议怎么做"，hook 是"做完必须过"——两件事配合一起用。

举个例子：一个评审 skill 里写了"段落控制在某个长度"、"必须有目标和非目标章节"等格式规则。但模型还是会偶尔忘——这时候 hook 就该上场了。挂一个 PostToolUse hook，每次模型写完 .md 文件，自动跑一遍 lint，把不合规的地方直接 flag 出来，强迫修。

Skill 教模型该怎么做，hook 兜底"必须做对"。前者是软建议（可被遗忘），后者是硬约束（不可绕过）。

4. Eval-driven：用 skill 写 skill / 用 skill 审 skill

skill 是文本，不是代码——但写完同样需要 eval。

实操办法：写一个 audit skill 自动跑你的 skill 库——按 Anthropic Best Practices 和 Perplexity 公开的方法论挨个扫 ~/.claude/skills/ 下的 SKILL.md，找 description 写法、长度、token 浪费、redundancy 之类的问题，输出审计报告，再决定哪些 skill 该改。这个 audit skill 大约每周跑一次。

更进一步是用 skill-creator 写新 skill——它会按官方 Best Practices 带你过一遍 description 写法、目录结构、命名规范，比自己从头写少踩很多坑。

让 skill A 帮你管 skill B，这个递归套路是真的能跑通的——也是 skill 不同于 prompt 的一个关键性质：skill 可以被另一个 skill 当对象操作。

5. 命名：gerund form 是官方推荐，但不是硬规则

skill 名字用"动词 + ing"（gerund form）形式，是 Anthropic Authoring Best Practices 明确推荐的：

"Consider using gerund form (verb + -ing) for Skill names, as this clearly describes the activity or capability the Skill provides."

考虑使用 gerund 形式（动词 + -ing）来命名 skill，因为这种形式能清晰描述 skill 所提供的活动或能力。

文档给的正例：processing-pdfs / analyzing-spreadsheets / managing-databases / testing-code / writing-documentation。

但这里有一个有意思的反差：Anthropic 自家仓库的 17 个官方 skill（pdf / pptx / docx / xlsx / skill-creator / mcp-builder / webapp-testing 等）几乎全部用名词形式。文档原文用的是 "Consider using"（建议）不是 must，并把名词形式列为 "Acceptable alternatives"。

所以这条是推荐风格不是硬规则——Jesse Vincent 的 superpowers 框架把它执行得最彻底（全部 gerund），Anthropic 自己仓库反而更松。

在团队范围内定一种风格比"用哪一种"更重要。挑一种风格、所有 skill 统一——避免一半 gerund 一半 noun 的混乱。

四、几条最值得记住的启发

把这四节拉回到一个判断上：skill 是 AI 时代团队最小的工程化沉淀单元。

具体一点：

第一条：每个工程师手里都有"口诀"——做评审 / 写 PRD / 出测试 / 接 API 时反复贴的那段 prompt。在 skill 之前，这些口诀只能散在脑子里、笔记里、Slack 历史里。在 skill 之后，它们终于有了一个可分发、可版本化、可评估、可演进的载体。不写 skill = 团队每个人都在重新教 LLM 同一件事。

第二条：前两天 Claude 用那个评审 skill 跑了一份新稿子，又踩到一个新坑——"非目标"那节漏了一条边界。我回去给 SKILL.md 补了一行："生成前必须自检 8 个章节是否齐全"。这种动作每周会发生一两次。每补一条，下次模型自动避开。这才是 skill 和 prompt 模板最大的区别——skill 是踩坑库的容器。prompt 模板只能告诉你"应该这么写"，写完出问题没法回追；skill 的 Gotchas / 反模式 / 救场命令可以长出来。一个用了半年的成熟 skill，往往背后是几十次真实事故沉淀下来的教训。

第三条：skill 改写了团队的知识沉淀路径。过去做团队 wiki：写一篇文档、放到 Confluence、希望大家读、半年后发现没人读。skill 翻转了这个流程——文档不是给人读的，是给 agent 读的；不需要团队成员主动学，agent 在他们调用工具时自动按 skill 执行。新人入职拉个仓库，全套规范当天上手——这是 wiki 时代做不到的。

第四条：skill 工程化能力，决定一个团队从 AI 时代拿到多少红利。这话听着抽象，但已经有一批公司用真金白银证明了——Garry Tan 把 CEO 视角的工作流打成 23 个 skill 开源、Vercel 把最佳实践打成 skill 分发给开发者、Stripe 把 API 文档暴露在 well-known、Microsoft 一家放出 192 个覆盖 Azure / .NET / M365 的 skill、skills.sh 已经累积 61 万 skill。这些公司和个人不是在"用 AI"——他们在让自家的产品和经验被 AI agent 自动消费。SaaS 文档形态正在被改写，护城河形态也在被改写。

另一种节奏完全不同：把 skill 当 prompt 的高级版本——攒一堆"装哪些 skill"的清单，但 SKILL.md 没有 hub-spoke、description 写不到位、装上后从没被自动触发过、更没想过自己也可以"发布"skill 让别人消费。这两种节奏的距离不会一直在——但谁先从"用 skill"跨到"做 skill 工程化"，谁就先到下一个台阶。

回到开头那个场景。当我把那段反复贴出去的技术评审 prompt 终于打包成 skill 之后，我没有立刻感到"哇 AI 帮我做了好多事"——我感到的是"我终于不用再贴一遍了"。

但更深一层的事情是：那个 skill 现在是团队资产，不是我个人的口诀。任何一个新人写技术评审，Claude 会自动按上面规则跑；任何一次新踩的坑，可以回去补一条，下次大家都不会再踩；任何一个之前没意识到的盲点，可以让另一个 audit skill 审出来再改。

这个杠杆放大的不是"我能更快完成任务"——是"团队的隐性经验，第一次可以被显性沉淀、版本化分发、持续演进"。

不写 skill，你不是在用 prompt 工程，你是在反复教 LLM 同一件事。

写 skill，你才真正进入了 AI 工程化。
