怎么像技术主管那样指挥 Claude，而不是当一个高级工程师

 


一个月前我写过一篇，讲要把 Claude 当初级同事，别当搜索框——交代清楚，先规划再写码，回来审 diff。

那篇是地板。这篇是往上再一层。

因为大概七月份的时候，我干的事儿已经不是"跟 AI 结对编程"了，变成了另外一码事。

我同时开着四个 Claude Code 会话。

一个在写功能。

一个在测试它。

一个在工作树（worktree）里啃一个迁移。

还有一个在审我自己都没读过的 PR。

我没在写代码。

我甚至不跟单个 agent 交代任务了。

我在带一个团队。

而带团队，跟"自己活儿干得好"，完全是两种技能。

凡是被提拔成 lead 的工程师都懂那种感觉：让你成为一个好执行者的那份"自己动手、凡事仔细"，现在成了拖慢所有人的东西。

大部分 Claude Code 用户就卡在这儿。

不是提示词写得烂。

是他们还在以"一个超级能打的个体贡献者 + 一个手速极快的助手"的方式干活。

下面讲怎么改。

第一步：别开一个会话，开一个团队

第一个要改的习惯：cd 进仓库，敲 claude，然后把那一个窗口当成"Claude 住的地方"。

那窗口只是一个队友。

你手上是有一支队伍的。

跑这个：

claude agents

这就是 agent 视图——你所有在跑的 Claude Code 会话，一屏看完。

谁在干活、谁卡在你身上、谁干完了。

每行有一个带颜色的状态词，加一句标题说明这个会话实际在干嘛；跟 PR 或 MR 绑定的会话还会带上 PR 号。

我第一次打开的时候，有六个会话活着，其中两个我是真忘了。

这是技术主管的那块屏。

不是终端，是看板。

思路上的转变很小，但改变一切：你不再问"Claude 在干嘛"，开始问"什么卡住了"。

第二步：像拆 ticket 一样拆活

让我突然开窍的那个工作流，说出来简单得有点蠢。

两个会话。

一个叫 developer。

一个叫 QA。

developer 那个拿到 PRD，负责写。

QA 那个装上模拟器测试环境，把 App 跑起来，把流程点一遍，然后汇报哪儿炸了。

两边都不干对方的活，这才是重点——写代码的那个会话，是最差的代码审查者。

然后就出现了这么个东西，它才是把"两个会话"变成"一支队伍"而不是"两个标签页"的关键：

你的会话之间可以互相发消息。Claude 通过 ListAgents 找到你其他的会话，再用 SendMessage 发过去——你可以让它发，它也可能自己发，比如它改的东西影响到了另一个会话正在做的活。

你直接说人话就行：

告诉那个在做 payments API 的会话，users.name 现在叫 users.display_name

对方那边会冒出一行 Message from。

按 Ctrl+O 展开。

或者在输入框里敲 @，直接按名字点名另一个会话。

如果这名字只对上一个活着的会话，那消息就直接过去，没有确认步骤。

跑 /list-agents 看看谁在线。

同一台机器上的会话名是唯一的，所以你要是起了个重名的新会话，Claude Code 会自动把它改成 name-word-word 这种变体，并且告诉你。

macOS、Linux 都支持，八月底开始原生 Windows 也支持了。

它替掉的是那个你压根没意识到每天在花你一小时的东西：重复解释上下文。从一个终端里把某个决策抠出来，粘到另一个终端里，还粘得不全，推理过程缺了一半。

主管不会挨个给每个人重新交代一遍。

主管做的是让信息横向流动。

第三步：分清楚什么时候 fork，什么时候开新会话

这俩看着像，其实完全不是一回事。

fork 是一个已经知道你前面聊过所有内容的支线任务。现在交互式会话默认开着 fork 模式，所以 Claude 能起一个 fork 子 agent，继承完整对话外加 prompt 缓存，而不是冷启动。

> /subtask 给目前改过的 parser 起草一下单元测试

它会出现在你输入框下面的面板里，后台跑，跑完结果直接掉进你当前对话。

这期间你该干嘛干嘛。

注意"目前改过的"这个说法。fork 就是干这个的——只有在这个对话上下文里才讲得通的活。

给我们刚写的东西补测试。

把刚做的决策整理成摘要。

对我们刚争过的那套方案给个第二意见。

新会话则是一条并行轨道。不同的问题，不同的上下文，独立的大脑。/fork 会把你当前对话复制成一个新的后台会话，而且——这是关键——它的代码改动是在它自己的工作树里做的，不动你的 checkout。

我自己用的规则：

任务需要知道我们刚才说了什么，就 fork。任务需要不在乎我们刚才说了什么，就给它开个自己的会话。

搞混这一步，就是为什么很多人并行跑 Claude 跑成一团乱麻。

他们在同一个 checkout 上开五个会话，然后纳闷为什么几个 diff 互相打架。

第四步：做隔离，不然你自己的 AI 会给你制造合并冲突

这一步，高级工程师会跳过，技术主管从来不跳。

四个会话改同一份工作副本，这不叫并行。

这叫一个署着你名字的竞态条件。

答案是工作树，而且这东西现在做得挺狠：

claude --worktree https://github.com/org/repo/pull/128

它直接从 PR 本体上拉出一个会话分支。

GitLab 的 MR 链接一样能用。

工作树隔离现在管的不只是文件编辑——它会拦下所有想伸回主 checkout 的 Bash 命令和 git 重定向，所有会话类型都拦，会话下的子 agent 也拦。

所以后台 agent 没法偷偷 git checkout 到你工作目录里去。

而且，凡是在工作树里改了代码的后台会话，收工前会 commit 并 push、该开 draft PR 就开、并且遵循你 CLAUDE.md 里的 git 说明。

这句话再读一遍，因为这才是真正的解锁点：你的 CLAUDE.md 现在是团队制度，不是个人配置。分支命名、commit message 格式、要不要开 draft PR——写一次，你起的所有会话都照做。

这才是主管干的事。

不是逐条审 commit message。

是把约定写下来，让谁都不用再操心。

第五步：把角色写进文件，别一遍遍口述

如果你发现自己在第四次敲"你是个 reviewer，对并发要严格，别动模块结构"，停下。

那是一个角色，角色应该待在文件里。

把这玩意儿丢进 .claude/agents/ios-reviewer.md：

---
name: ios-reviewer
description: 审查 Swift 改动中的并发问题和 API 兼容性问题。共享模块有任何改动之后都应该调用。
tools: Read, Glob, Grep, Bash
model: opus
effort: xhigh
isolation: worktree
maxTurns: 8
---
 
你是一个证券交易类 App 的资深 iOS 审查者。
默认到处都是并发访问。任何改动只要动了公开 API 却没附迁移说明，
一律标出来。不要提没人要求的重构。
用编号列表汇报问题，带上文件名和行号。

看看那段 frontmatter 在干什么。tools 是白名单，所以这个 reviewer 物理上就写不了文件。isolation: worktree 给它自己的一份副本。effort: xhigh 让它在一个硬活儿上动真格的推理。model: opus 是给这个任务挑对的人。

你可以把它钉到整个会话上：

claude --agent ios-reviewer

或者点名调用，保证拿到它：

@"ios-reviewer (agent)" 审查一下订单确认流程

agent 放在项目里的 .claude/agents/、你个人所有项目的 ~/.claude/agents/，或者放进 plugin 里给整个团队用。

这是全文里性价比最高的二十分钟。

你写下来一次的角色，就是一个你再也不用重新 onboarding 的队友。

第六步：在你需要之前就把上限设好

主管要给团队立规矩。

下面这几条是真的重要。

并发数。 默认能同时跑二十个子 agent。超过就报 Concurrent subagent limit reached。真需要的话在设置里调高：

{
  "env": {
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "30"
  }
}

嵌套层数。 子 agent 默认能在你对话下面往下嵌三层。把 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH 设成 1 就直接关掉嵌套。凡是碰生产代码的活，我都让它保持浅——一个四层深的 agent 链条，你根本没法有效地审。

权限。 从 8 月 14 号开始，auto 模式成了 Pro、Max、Team 新会话的默认权限模式。

有个分类器会审每个动作，安全的放行，有风险的拦下，而且这些分类器调用不计入你的用量额度。

auto 模式挺好。

但这不是你在关键路径上可以放松的理由。

凡是碰钱、碰鉴权、碰持久化的地方，我照样跑严格权限。因为"分类器觉得没问题"这句话，我不想在一家证券公司的事故复盘会上说出口。

Effort（力度）。 按难度给，逐个 agent 设。无聊的活用 standard，并发 bug 用 xhigh，那种真·地狱级的一次性任务上 max。让整支队伍都跑 max，只是更慢更贵，没有任何好处——跟把最强的工程师派去改文案是同一种错误。

没人警告过你的那部分：你自己会变成瓶颈

下面是坦诚环节。

我跑四个会话的第一周，产出比只跑一个的时候还少。

不是因为 agent 不行。

是因为我审不过来。

四个会话产出四份 diff，结果我四份都扫了一遍，而不是把一份认真读完。

其中一份改了订单确认流程里的一条错误路径，看上去完全合理，实际上完全是错的。

我抓到了。

在 review 里。

险之又险。

这就是技术主管真正的失败模式，带真人团队时也一样：你把团队扩到了超出你维持质量的能力，最后崩掉的不是吞吐量，是判断力。

所以真正的约束不是你能跑多少个会话。

是你今天能真正读懂几份 diff。

对我来说这个数字是三。有时候是二。开会开满的一天，是一。

超过这个数，你就不是在带团队，你是在盖章。

第七步：审的是团队，不只是代码

审四个 agent 跟审一个不是一回事。

让 review 跟干活并行跑。

/code-review 现在在所有 effort 级别下都作为后台 agent 运行，/review 是它的别名。踢出去，然后继续干你的。

真正要紧的东西，换一双新眼睛。

/ultrareview 会把一队找 bug 的 agent 派到云端，结果回到你的 CLI 或桌面端。

重点不是它更聪明——重点是写代码的时候它不在场，没什么要维护的立场。

像开站会那样读 agent 视图。

哪些会话卡在你身上？

卡住的那些就是在吃你吞吐量的，而如果你埋头在一个终端里，它们是完全隐形的。

不用守在机器前也能查岗。

在你机器上跑 claude remote-control，它就会以一张设备卡片的形式出现在 Claude App 里 Code 标签页的顶部。

我有一次踢了个迁移出去，去吃了个午饭，回来的路上在手机上把 diff 读了。

你还能在手机上改 effort 级别，改完会作用到机器上那个会话。

还有一条永远不变、也永远不会变的规矩：

commit 还是你签的。不是写它的 agent，也不是审它的 agent。是你。

真实的一天长什么样

放到一个普通功能上，它是这么拼起来的：

  1. 1. 打开 claude agents。看看昨天还有什么在跑。先把卡住的清掉。
  2. 2. 用 plan 模式起构建会话，给一份像样的 brief——范围、约束、完成的定义。
  3. 3. 在自己的工作树里起第二个会话，叫 QA。它的活是把 App 跑起来、把功能搞崩，不是帮着写。
  4. 4. 构建跑着的时候，/subtask 一个 fork 去起草单元测试，反正它已经有完整上下文了。
  5. 5. schema 一变，让一个会话去通知另一个。别自己再解释一遍。
  6. 6. 在你读任何东西之前，先把 /code-review 丢到后台跑。
  7. 7. 读 diff。真读。这就是现在的工作本身。
  8. 8. 哪儿不对，就把那个会话回滚到某个 checkpoint，然后去修你的 brief——别跟 agent 吵架。
  9. 9. commit，署你的名字，因为你审过了。

注意这份清单里你没有在做的事：写代码，以及重复解释上下文。

注意你正在做的事：派活、解阻塞、审代码。

这就是技术主管的岗位说明书。

一直都是。

把 lead 和"重度用户"分开的五个习惯

如果你别的都记不住：

  1. 1. 开的是看板，不是终端。claude agents 就是你的站会。卡住的会话就是在花你时间的那批。
  2. 2. 让信息横向流动。 会话之间能互相发消息。别再当自己 agent 之间的复制粘贴层了。
  3. 3. 要上下文就 fork，要隔离就新起会话。 任务需要你刚说的话，就 fork。不需要，就给它自己的会话和自己的 worktree。
  4. 4. 角色只写一次。 一个带工具白名单的子 agent 文件，就是一个你再也不用重新 onboarding 的队友。
  5. 5. 按你的审查能力给团队封顶。 会话数超过你能诚实读完的 diff 数，那不叫杠杆，那叫一种更慢的交付 bug 的方式。

2026 年真正从 Claude Code 里吃到杠杆的工程师，提示词并没比你写得好。

他们只是跑了更少的、范围更清晰的 agent，角色明确，分支隔离，然后把回来的每一份 diff 都读了。

仔细想想，这就是好的工程管理——只不过管的是打字比你带过的任何人都快的队友。
