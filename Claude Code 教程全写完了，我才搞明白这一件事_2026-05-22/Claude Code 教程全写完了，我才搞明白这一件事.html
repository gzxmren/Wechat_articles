为什么编写这套教程


去年 10 月份左右，我第一次接触 Claude Code。


当时 Skill 功能刚火起来，网上各种教程铺天盖地。


我看了很多，有的讲得很深入，有的用一篇短文就把核心功能和流程全讲完了。


看完之后我的感觉就是——懂了，会了。


但真到自己上手用的时候，完全是另外一回事。


比如 CLAUDE.md 文件，我一开始根本不知道该往里面写什么。


哪些内容属于 CLAUDE.md？


哪些应该拆成 SKILL 文件？


哪些任务该交给子代理去做？


我的配置一开始全乱了。


SKILL 文件里规定了用简体中文，CLAUDE.md 里又写了"必要时用英文"。


这不仅让模型产生幻觉，后期维护起来也特别痛苦——改一个地方，另外两个地方跟着出问题。


我当时就觉得，不对劲，肯定哪里出了问题。


后来反复和 AI 沟通、反复调试，我才慢慢搞明白：我缺的不是教程，而是工程化思维。


说白了，就是缺少对"高内聚、低耦合"的敏感度。


之前我的 CLAUDE.md 就是个大杂烩，什么都往里塞。


后来才学会按职责拆分——配置规则放 CLAUDE.md，流程和业务逻辑做成 SKILL，需要并行处理的任务交给子代理。


💡

配置这件事，没有捷径，就是踩坑踩出来的。


我想，肯定有很多人和我一样，看了教程觉得懂了，上手就懵了。


所以我就想把自己踩过的坑和 AI 交流的内容整理成教程，分享出来。




我是怎么用 Claude Code 写这套教程的


其实这套教程的编写过程本身，就是一次 Claude Code 的实战。


我的流程大概是这样的：


第一步，遇到问题就问 AI。


使用过程中遇到任何疑问，我都会向 AI 提问，而且必须让自己彻底搞懂才算结束。


不是大概明白就行，是真的搞清楚"为什么这样做"。


第二步，把聊天记录导出为文件。


搞明白之后，我会把这段对话导出保存。


这些对话就是最真实的"踩坑记录"和"思考过程"。


第三步，放入项目的 reference 目录。


我把所有导出的对话文件，统一放在配置好的 Claude Code 教程项目的 reference 目录下。


这样 AI 编写教程时，可以直接参考这些真实对话。


第四步，让 AI 编写，我来审核。


在 Claude Code 里输入编写指令，AI 会基于 reference 中的对话内容生成教程初稿。


我只需要审核、优化、补充就好。


说实话，这个流程跑通之后，效率真的很高。


我把整个项目开源到了 GitHub，算不上多专业，但希望能给大家一些参考。


GitHub 仓库：https://github.com/lingxiaobc/claude_code_guide.git

关于 Claude Code 的一些感想


刚开始接触 Claude Code 的时候，我疯狂地从网上找各种教程、各种心得分享。


我天真地以为，只要看得够多、理解得够深，就能熟练使用。


但事实证明我错了。


看懂是一回事，自己真正下场去做，又是另一回事。


因为每个人的项目不同、需求不同、基础也不同。


💡

真正学会一个工具，一定要自己亲自去用，去踩坑，去优化，去总结。


教程是起点，不是终点。


它能帮你少走弯路，但没法替你走路。




写在最后


回过头看这套教程，从最基础的安装配置，到 CLAUDE.md 的编写，再到 SKILL、子代理、MCP、Hooks……


其实写的过程，就是我自己不断踩坑、不断重新理解 Claude Code 的过程。


💡

教程不是看会的，是用会的。


这句话既是写给你们，也是写给我自己的。
