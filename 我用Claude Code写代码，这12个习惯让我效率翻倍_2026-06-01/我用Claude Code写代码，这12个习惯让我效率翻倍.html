习惯 1：Plan Mode——先想，再动

大多数人上来就让 Claude 改代码，这是最贵的用法。

Claude Code 有个隐藏模式：Shift+Tab 切换进入 Plan Mode。这个模式下 Claude 只分析、不执行。你能看到它打算怎么做，审查通过再放手。

三步走：探索 → 计划 → 执行。能消灭 90% 的"改坏了再改回来"返工成本。

单文件小修改可以跳过。涉及多个文件的改动，必须先 Plan。

习惯 2：.claude/ 目录——你的 AI 大脑

Claude Code 真正的威力藏在这个目录里，大多数人甚至不知道它存在：

.claude/
├── CLAUDE.md          ← 项目规则说明书
├── CLAUDE.local.md    ← 你的私人规则（不提交 git）
├── settings.json      ← 权限与行为配置
├── agents/            ← 自定义子 Agent
├── skills/            ← 可复用知识包
├── rules/             ← 细粒度路径规则
└── .mcp.json          ← MCP 工具集成

配置一次，整个团队受益。新人克隆仓库，几分钟内就能达到团队的 AI 使用水准。

习惯 3：CLAUDE.md——只写"去掉会出错"的规则

很多人把 CLAUDE.md 写成百科全书。这是错的。

Claude Code 作者 Boris Cherny 对每条规则只问一句话：

"去掉这条，Claude 就会犯错吗？"

不会出错的，全删。他真实在用的 CLAUDE.md 长这样：

# Development Workflow
Always use `bun`, not `npm`.
Run `bun run typecheck` before claiming done
Never push to main directly
All API routes go through src/api/middleware/auth.ts
`User` 和 `UserRecord` 是两种类型，不能混用

五条。全是血教训。没有废话。

更妙的一招：每次 Claude 犯错后，说一句：

"把刚才这个错误的避免规则，写进 CLAUDE.md"

Boris 说，Claude"很擅长把自己的失败提炼成精准的规则"。用几周，文件自动进化成最适合你项目的防错手册。

习惯 4：CLAUDE.local.md——把 PR 反馈变成 AI 记忆

这个文件和 CLAUDE.md 一起加载，但不提交 git，只属于你一个人。

每次 code review 收到反馈，立刻粘进去：

# 来自 PR 反馈（私人）
- 新建 SQS consumer 必须同 PR 附带 DLQ 和告警配置
- 用 Optional<T>，不用 null 返回值
- 新接口的测试必须包含"auth 失败"的 case
- 接口有变化就更新 OpenAPI spec，不能漏

# 自己的习惯问题
- 别用 console.log，用项目的 logger

这个文件的效果是：你的 code reviewer 帮你训练 AI。两周后，Claude 自动附上 auth 失败测试、自动更新 OpenAPI spec，你在 PR 上的重复反馈会肉眼可见地减少。

习惯 5：Skills——把专业知识打包复用

Skills 放在 .claude/skills/，是比 CLAUDE.md 更细粒度的知识包。

对比 CLAUDE.md Skills
粒度 项目全局 主题级
加载时机 每次自动 按需调用
复用性 限本项目 跨项目复制
适合内容 项目规则 技术规范/流程

Skills 的核心优势是渐进式加载：Claude 启动时只读 frontmatter（约 100 token），需要时才加载全文。上百个 skill 也不会拖慢会话。

社区资源：Jeffallan/claude-skills 提供了 66 个语言专属 skill（9.4K Stars），Go、Python、TypeScript、Rust 一应俱全，直接拿来用。

习惯 6：自定义子 Agent——让 Claude 并行干活

在 .claude/agents/ 放一个 Markdown 文件，就有了一个专属 Agent：

---
name: pr-review
description: 审查当前 branch 的 diff，找 bug、安全漏洞、规范违反
model: claude-opus-4-5
tools: Read, Grep, Bash
---

1. 运行 git diff main...HEAD
2. 对照 CLAUDE.md 和 rules/ 检查规范
3. 标记严重性：Critical / High / Medium / Low
4. 结尾输出 SHIP / FIX FIRST / REWORK

触发方式：对话里说"用 pr-review agent 看一下这个 diff"，子 Agent 在隔离上下文里运行，结果汇报回来，主会话不受干扰。

社区资源：VoltAgent/awesome-claude-code-subagents 收录了 100+ 开箱即用的 agent（20.7K Stars），security-reviewer、test-writer、debugger、performance-auditor 全有。

习惯 7：插件市场——一行命令扩展超能力

运行 /plugin 打开插件市场浏览器。现在有 1000+ 插件、75+ 社区市场。

入门必装四件套：

插件 干什么的
/code-review 4 个并行 Agent 同时审代码，置信度打分，高信噪比
/feature-dev 给个需求说明，7 阶段自动完成：需求→探索→架构→实现→测试→Review→文档
Language Server 符号级跳转 + 编辑时即时 lint，Anthropic 团队评为最高性价比插件
/batch 把迁移任务扇出给几十个并行 Agent，每个在独立 worktree 跑

/batch 最值得单独说：把"把所有 class component 迁移成 functional component"这种重复性工作交给它，几十个文件同时跑，你去泡杯咖啡回来看结果。

习惯 8：/goal + /rewind + /compact——三个命令改写工作流

/goal — 设定完成条件，Claude 自动循环直到达成：

/goal 所有 test/auth 里的测试通过，lint 干净

设完可以去干别的，回来看结果。

/rewind — Claude 走错了方向时，别往上下文里加"那不对，换个方向"。加这句只会让错误路径留在上下文里继续干扰。直接 /rewind 回到犯错之前，重新来。

/compact — 会话跑长了，上下文变浑浊，Claude 开始绕圈。这时 /compact <hint> 压缩会话，hint 说明哪些结论要保留。比 /clear 温和，比什么都不做聪明。

三个组合用：/goal 定目标，跑偏用 /rewind，跑长了用 /compact。

习惯 9：MCP——让 Claude 看到你的整个技术栈

MCP（Model Context Protocol）是让 Claude 直接读取外部系统的协议。

MCP 解锁能力
GitHub MCP 直接读 PR、Issues、代码搜索
Context7 实时最新官方文档注入（终结幻觉 API）
Sentry MCP 读真实报错堆栈和 breadcrumb
Playwright MCP 浏览器截图 + UI 自动测试
Figma MCP 读设计稿直接生成代码
Postgres MCP 直接查询开发数据库

配置在 .claude/.mcp.json，团队共用同一份。

不要贪多：装太多 MCP，Claude 需要从一大堆工具里选择，决策质量下降。入门先装 GitHub + Context7，再按实际需要加。

习惯 10：Obsidian 三层记忆——给 Claude 持久化项目记忆

Claude 原生是无状态的，每次会话从零开始。但通过 Obsidian + MCP 可以给它装上长期记忆。

安装 obsidian-claude-code-mcp，在 vault 里建三层结构：

层级 存什么 多久更新
热存储 10-Daily/ 每次会话日志，Stop Hook 自动追加 实时
温存储 20-Projects/ 项目 README、架构决策、最近 3 次会话摘要 每 PR 一次
冷存储 30-Decisions/ ADR（架构决策记录）、跨项目通用知识 决策敲定后

新会话开始时，Claude 自动读项目 README + 最近 3 次会话日志——两周的上下文 30 秒内重载完毕，不用你每次从头解释项目背景。

习惯 11：并行会话——最被低估的力量倍增器

一个会话做所有事情，是效率杀手。

正确做法：3-5 个 git worktree，每个跑独立 Claude 会话：

会话 1  →  写新功能
会话 2  →  修 bug
会话 3  →  写单测
会话 4  →  重构旧代码

用 claude --worktree 或桌面版 agent view 当控制台，一眼看到所有会话状态，随时切换。

Boris 团队实测：并行会话把日均代码产出提升约 3 倍。不是比喻，是实测数字。

习惯 12：Writer/Reviewer 双会话——内置质量门

这是最后一个，也是质量提升最直接的一个。

会话 A 写代码。写完后：

"用一个新 session 扮演 staff engineer，审查刚才的实现，不带任何先入为主的上下文"

会话 B 在完全干净的上下文里审查。它没有"我刚才这么做是有原因的"这种自我辩护，发现问题的概率高得多。

把 B 的 review 结果粘回 A，修完，再让 B 审。循环直到 B 说 LGTM。

这是用两个 AI 做你的 pair programming 搭档，而不是一个。
