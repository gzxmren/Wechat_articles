别再让AI"裸奔"写代码：一份让团队不掉链子的Harness规范

本文基于腾讯技术工程公众号公开文章《驾驭AI Coding：一份面向团队的Harness Engineering落地规范》（作者 atreusliu，2026-07-17）的独立解读与延展，结合浚枢科技自身多智能体协作实践。非转载，属二次创作。原文链接见文末。

代码生成成本归零，质量却成新瓶颈。本文用第一性原理拆解腾讯团队级AI Coding落地规范Harness Engineering，附可直接抄的三阶段路线图、8条反模式清单与对抗式审查，3人小团队也能落地。

你团队里现在每个人都在用AI写代码了吧？

那我问个扎心的问题：交付速度翻倍了吗？bug是多了还是少了？

前两天跟一个做SaaS的朋友吃饭，他吐槽特别典型。他们组年初全员上了AI工具，老板很高兴，说效率要起飞。结果三个月后复盘，功能交付周期没短多少，技术债倒是堆成山。一个新来的实习生用AI十分钟写了个支付回调，没走任何规范，上线当天把订单状态机搞乱了，半夜被运维叫起来回滚。

"我们不是不会用AI，"他说，"是每个人用的AI，说的都不是同一种语言。"

我见过太多团队，Copilot、Claude Code、CodeBuddy全上了，第一周爽得飞起，一个月后开始怀疑人生——代码量是上去了，可没人敢动别人AI生成的文件，review变成走形式，一个新功能改出三个旧bug。

问题不在模型。模型够聪明了。

问题在：你让一匹没驯服的马直接去耕地。

第一性原理：代码免费了，好代码没免费

先把表层现象扒开，看底下那个不变的事实。

过去二十年，软件行业的瓶颈一直是"人力"。一个人一天写不了多少行，所以管理、流程、考核全围着"怎么让人写得更多更快"转。

ChatGPT之后，这个瓶颈塌了。生成代码的边际成本，正在趋近于零。你让AI写个登录接口，两秒。

但"写好代码"的成本，一分没降。

什么叫好代码？架构清晰、边界明确、别人看得懂、改得动、跑得稳。这些东西，AI不会自动给你——它只会给你"能跑"的代码。能跑和好，中间隔着一整个工程质量体系。

腾讯那篇文里有一句话我抄在笔记本上："交付代码的成本已经接近免费了，但交付好代码的成本依然很高。"

这就是根。所有AI Coding的乱象，都能从这句话推出来。

Vibe Coding为什么"起步极快→中期混乱→后期崩盘"？因为前期你只验收"跑没跑"，没人验收"好不好"。等我们把这三个阶段拆开看，几乎每个团队的崩法都一模一样：

起步极快（第1-2周）：原型嗖嗖出，demo惊艳老板，所有人觉得"以后不用招人了"。这时候没人觉得有问题，因为东西小，AI上下文装得下，出错也好查。

中期混乱（第3-8周）：文件过50个，上下文雪崩。AI开始"忘事"——第一天叫user_id，第三天自己改成了uid，你修一个bug，它顺手给你埋俩。更要命的是，A用AI生成的模块和B用AI生成的模块，命名风格、错误处理、目录结构全是两个世界的物种，谁都不敢动对方的代码。

后期崩盘（第2个月+）：新需求要在旧逻辑上改，可旧逻辑没人说得清为什么那么写。AI基于错误的前提继续生成，债务复利式增长。这时候你面临一个残酷选择：推倒重来，或者养着一坨谁都不敢碰的代码。

三个阶段的本质，是"能跑"和"好"之间的裂缝，随时间指数级扩大。

所以真正的命题不是"怎么让AI写代码"，而是"怎么让AI持续写出好代码，而且是一个团队一起写，还写得稳"。

核心隐喻：Agent = Model + Harness

解法有个漂亮的名字：Harness Engineering。

Harness是马具。马鞍、缰绳、眼罩那一套。

一匹野马力量很大，但你没法让它耕地、运货、上战场。得先套上马具，它才知道往哪走、停在哪、别踩庄稼。

裸模型就是那匹野马。Harness就是套在它身上的马具——规则、技能、工具、记忆、度量，把"好代码"的标准焊进工具链，而不是指望每个工程师脑子里都装着同一套标准。

公式就一句：Agent = Model + Harness。

模型提供智能，Harness让智能变成生产力。

这解释了一件很多人没想通的事：为什么同样用Claude，有人做出玩具，有人做出生产线？差的就是Harness的厚度。

六根支柱，撑起"马具"

腾讯把Harness拆成六根支柱，我用大白话翻译一遍：

  • 上下文管理：AI得知道自己在干啥。Spec、AGENTS.md、知识库，渐进式披露，别一上来把整个仓库倒给它。

  • 工具系统：AI得能碰到东西。MCP是开门的钥匙，Skills是进门后干的事，知识库是进门前的说明书。三样缺一样，Agent就是个嘴强王者。

  • 执行编排：按什么顺序、谁来做。Plan模式先想清楚，再动手；多Agent按角色分活。

  • 状态与记忆：得记住干过啥。Git是真相源，Memories记偏好，Spec Deltas记需求变化。

  • 评估与观测：干得对不对。自动测试加AI CR，从L1到L4分级审查。

  • 约束与恢复：什么不能做。Rules画红线，出事自动回滚。

注意，这六样没有一样是"让AI更聪明"，全是"给AI套缰绳"。这才是Harness Engineering的精髓——它不跟模型较劲，它跟系统较劲。

举个具体例子你就懂了。上下文管理这一根，很多人以为"把代码全给AI看"最省事，其实大错。正确做法是AGENTS.md当索引（100行讲清架构和常用命令），具体实现让AI按需读文件，配合知识库做渐进式披露。工具系统那根，MCP接多了反而坏事——Agent面对十几个工具描述，选工具都选花眼，这就是"上下文变脏"。所以腾讯强调只接P0/P1。评估那根，AI CR按L1（语法）到L4（架构安全）分级，简单改动L1-L2自动过，核心逻辑必须L4人工兜底。

浚枢视角：我们早就在套这副马具了

看到这，做过我们「浚枢-协同循环操作指挥（LoopOrchestrator）」Skill的人应该一拍大腿。

那个Skill干的事，本质就是给WorkBuddy的多智能体协作套马具：S1~S9定义了角色分工、循环节奏、验收返工、自愈诊断。腾讯讲的是团队级AI Coding，我们讲的是团队级AI Agent编排——底层是同一个第一性原理：把"什么叫做好"固化进系统，而不是依赖每个人临场发挥。

所以这篇文章对我们不是新概念，是同行印证。腾讯用六支柱，我们用S1~S9，殊途同归。区别只在于：他们面向"写代码"，我们面向"跑Agent任务"——但马具的织法，是一套。谁先想通"把标准焊进系统"，谁就先过AI Coding的下半场。

为什么是"团队级"，不是"个人级"

有人会杠：我自己用AI写得挺好啊，要什么Harness？

个人玩和团队干，完全两回事。

个人Vibe Coding，崩了你自己扛，改起来快。团队不行——十个人十个写法，没有共同语言，没有质量底线，没有可追溯的变更记录。今天AI生成的代码，明天换个人根本不敢动。

Harness Engineering的"团队级"价值，就三个词：共同语言、质量底线、可追溯。

它把"好代码"从某个牛人的脑子里，搬到了team-harness仓库里，变成所有人看得见、改得了、Git管着的规则文件。新人入职，拉一遍仓库，水平直接对齐团队中位数，不用跟在老员工屁股后头学半年"咱们的暗规矩"。

能直接抄的落地规范（干活的部分来了）

别光听理念，给一套能落地的。腾讯原文给的是三阶段路线图，我压缩成能立刻动手的版本。

阶段一：基础建设（1-2周）

建一个team-harness仓库，作为团队唯一真实来源。结构长这样：

rules/        # global / golang / python / frontend 分层规则
skills/       # common 通用 / business 业务
templates/    # AGENTS.md、project.md 模板
sync-harness.sh  # 自动同步到各业务项目的 .codebuddy/

用脚本把规则同步进每个项目，别靠人手动复制——人一定会漏。

Rules分三层：User级（个人习惯）、Team级（团队公约）、Project级（项目专属，放.codebuddy/rules）。AGENTS.md控制在100行左右，当目录索引用，别堆成论文。

举个Project级rules的真实样例，你就知道该写到多细：

---
alwaysApply: true
---
# 分层架构红线
- Controller 禁止写业务逻辑，只做参数校验与转发
- 跨服务调用必须走 MCP，禁止硬编码内网地址
- 数据库变更必须带 migration，禁止临时改表
- 中文注释，变量名 camelCase

注意那个alwaysApply: true的frontmatter——它决定这条规则是"每次都加载"还是"按需触发"。写错这一行，规则等于没写。这种细节，恰恰是Harness Engineering的门槛：理念人人懂，落地全是坑。

AGENTS.md也别写成长篇小说。一份能用的模板长这样（控制在100行内）：

# 项目概述
XX系统，面向B端客户的订单中台。

# 架构
三层：Gateway(gin) → Service → Repository。
禁止Service层直接调DB，必须过Repository。

# 目录
/cmd 入口 /internal 业务 /pkg 公共 /api 协议

# 常用命令
make run 本地起 | make test 单测 | make migrate 迁移

# 进行中需求
- [需求A] 订单导出，预计本周五合入
- [需求B] 退款状态机重构，待Plan评审

就这五块：概述、架构、目录、命令、进行中。新人拉下来十分钟看懂全局，不用抓着老人问"咱这项目啥结构来着"。这东西看着简单，但它是团队"共同语言"的载体——没有它，每个人的AI都在各自的认知孤岛里生成代码。

阶段二：工具接入（2-4周）

MCP按优先级接：P0是数据库和代码仓库（能读表结构、能提PR），P1是文档和任务系统，P2才是CI/CD。别一上来接十几个MCP，Agent会被工具清单淹没。

Skills要原子化——一个Skill解决一类问题，别写成瑞士军刀。description写清楚"什么时候该触发它"，不然根本调不起来。

阶段三：持续优化

建个harness-audit自检Skill，定期扫一遍：上下文配置齐没齐、Rules覆盖够不够、Skill描述准不准。腾讯那个案例，对go_scaffolding_svr跑审计，7个维度打分（AGENTS 15分、Rules 20分……），报告写进.codebuddy/reports/。分数不重要，重要的是知道哪漏了。

日常SOP：把规范变成肌肉记忆

规范不进日常流程，就是墙上的标语。三条SOP：

  • SOP-A 新需求：简单需求可以让Agent直接干，但必须守Rules；半天以上的需求，先走Plan出requirements，人审完再动。

  • SOP-B 修Bug：一个PR只修一个Bug，必须带复现测试，commit写明fix: [模块] 啥问题 (#issue号)。

  • SOP-C 审PR：自查或审别人，查架构、错误、性能、安全、commit信息五样。

再看五条红线，谁踩谁负责：

先Spec后Code｜Rules必须进Git同步｜通用逻辑抽象成Skill复用｜MCP优先用实时元数据别硬编码｜所有变更可追溯。

演练一遍更直观。 假设要新增"用户操作日志"模块。走Plan模式，Agent生成requirements.md：记录用户操作（增删改）、支持按用户/时间查询、90天自动清理。你作为人审，重点看四件事——边界（清理任务失败怎么办）、API（入参出参字段）、表结构（新表还是加列）、异常（批量操作超时）、验收标准（怎么算"完成"）。审完Agent出task.md开始实施，最后Evaluator自动跑合规+逻辑审查，Archiver把这次的经验归档进知识库。一轮下来，下一次类似需求，Agent直接调历史Skill，不用从零想。

这就是"3+1 Phase"多Agent协作的真身：Planner定计划、Generator写码、Evaluator审查、Archiver沉淀。四个角色不是一个人在战斗，是流水线。

8条反模式（建议打印贴显示器）

这部分读者最爱，因为全是血泪。

  1. 把几千字需求一股脑丢给AI → 先Plan拆requirements。

  2. 跳过审核直接编码 → 半天以上的需求必须走Plan。

  3. Rules写完不维护 → 月度Review，技术栈变了规则就废了。

  4. MCP接十几个 → 只接P0/P1，工具多=上下文脏。

  5. Skill不原子化 → 一Skill一类问题，别搞万能膏药。

  6. 盲信AI直接合入 → 必须人工CR，AI写的bug更隐蔽。

  7. 把聊天记录当文档 → 持久化到.codebuddy/plan，Chat一关就没了。

  8. 一个PR改所有 → 一PR一问题，回滚和review都崩溃。

对抗式审查：别被10倍忽悠了

写到这得泼盆冷水。任何"用了就起飞"的方法论，都得先过一遍反驳视角，不然就是卖课话术。我特意站在"坚决反对派"的位子推演了一遍，找出十个可能让这套规范翻车的地方——你要是真打算落地，这些比前面的漂亮话更值钱。

盲区一：案例有幸存者偏差。 原文引了OpenAI"3人团队禁手写码、5个月AI写超100万行、合并1500 PR、效率升10倍"。这事是真的（2026.2公开文章），但OpenAI有顶级基建和极强工程文化，你的团队大概率没有。10倍是结果，不是承诺，别拿去跟老板打包票。

盲区二：小团队可能过度工程。 team-harness仓库+Knot平台+MCP全套，对3人小团队可能是负担。我们浚枢就3个人还没专职运维——我的建议是轻量化：一个SKILL.md加一份rules文件，先跑起来，别一上来建中台。具体怎么轻？我们自己的做法：把团队公约写进一份AGENTS.md放仓库根目录，Rules压成10条以内的硬红线（比如"禁止Controller写逻辑""跨服务必须走MCP"），Skills只沉淀真正复用的3-5个。MCP先接一个最痛的（我们接的是数据库，因为查表结构最频繁）。其余等疼了再加。这样既吃到Harness的红利，又不养中台的闲。

盲区三：人工CR变成新瓶颈。 说"必人工CR"，可AI一天能产50个PR，人看得完吗？度量层用AI CR（L1-L4）分担，但L4以上的关键逻辑，机器目前真替不了人。这条红线不能省，代价是review人力要补上。

盲区四：Rules会腐烂。 "月度Review"四个字轻松，实际没人排期就会烂。我们做法是把Rules Review钉进每个迭代末尾，和发版检查表绑死，不review不准发。

盲区五：度量分数能刷。 7维打分看着科学，但AGENTS占比15%、Rules占比20%这种权重是人拍的。分数高不代表代码好，可能只是文档写漂亮了。别把体检分当KPI。

盲区六：工具锁定风险。 原文大量依赖CodeBuddy/腾讯生态。如果你的团队用Claude Code或Cursor，方法论能平移，但具体Skills、Commands得重写。换工具成本要算进去。

盲区七：MCP优先实时元数据这条红线，反过来可能是依赖陷阱。内部MCP挂了，Agent直接瞎。关键路径别只靠实时接口，留本地缓存兜底。

盲区八：记忆也有维护债。 "Chat历史当文档"是反模式没错，但Memories加Spec Deltas本身要养。记错一条偏好，比不记更坑。

盲区九：度量层可能反噬节奏。 为了刷7维高分，团队可能过度写文档、过度拆Skill，反而拖累交付速度。Harness是手段不是目的，分数高了交付慢了，等于本末倒置。建议只盯两个真指标：AI生成代码的合入率和线上故障率，其余都是过程量。

盲区十：人会被系统驯化。 这是最隐蔽的。全套Harness跑顺后，工程师容易变成"需求翻译+审核员"，深度编码手感退化。长期看，团队的创新上限可能反而被模板框死。得故意留一部分"裸写"空间给核心成员练手，保持对底层的直觉。

八条盲区分完，结论反而更扎实：Harness Engineering不是银弹，它是一套"把质量成本从人脑转移到系统"的工程纪律。值不值得做，看你团队规模和长期维护意愿。

回到你团队的三问

看到这，别急着All in。先问自己三个问题：

你的团队，是三个人还是三十个人？三人轻量套马具，三十人必须建中台。别看腾讯那套完整就焦虑，人家体量和你不是一个量级。

你的核心交付，是长期维护的产品，还是一次性的原型？原型Vibe Coding爽完就跑，产品必须上Harness。这条线划不清，容易在错误的地方过度投资。

你愿不愿意为"质量"付持续的维护税？Harness不是装完就灵，是得养的。Rules月度Review、Skill持续沉淀、度量定期跑——这些动作没人排期，三个月就腐化成摆设。

三个问题想清楚，再决定套多厚的马具。套错了方向（小团队建中台、原型上重规范），比不套还浪费。

绕了一大圈，回到第一性原理那句话收个尾：当生成的边际成本趋零，"写"不再是瓶颈，"写好"才是。Harness Engineering的所有动作——规则、工具、编排、记忆、评估、约束——没有一项是在让AI更聪明，全是在把"好"的定义从人脑搬运到系统。这才是它经得起对抗式审查的根本原因：它不赌模型突然变神，它赌系统能兜住人的下限。

凌晨三点还在交付的，从来不是某个Agent，是一套围绕目标持续运行的系统。把"好代码"焊进系统，马才能真的替你耕地。

浚枢说

说到这你可能会问，规范写进去就一劳永逸了。哪有那么简单。规范本身也会老化，业务变了，技术栈换了，昨天的红线今天可能就成了绊脚石。所以才需要第三阶段那个度量看板，它不是摆设，是拿真实数据告诉你，哪条规则真的在起作用，哪条在拖后腿。好的 Harness，是活的系统，不是死的文件。

我始终坚信一件事，真正的工程纪律，不是靠人盯人，是靠系统兜住人。你把标准写进系统，系统替你守住底线。人，才能腾出手去做那些真正需要创造力的事。

大时代啊，朋友们，这话我上次也说过，今天再说一遍不嫌多。AI 把写代码的成本压到了趋近于零，这是挡不住的。但交付好代码，从来都是一门手艺，一门需要纪律、需要沉淀、需要把认知写进系统的手艺。

2.8 万亿参数的模型都能开源了，你团队那点工程规范，更没有理由锁在某个人的脑子里。把它抽出来，写进 Harness，让它在你团队里，自己跑起来。
