Hermes Learn上线后，Agent 真正开始沉淀经验了

Agent 最大的问题不是不会做事，而是每次都像第一天上班。

你刚带它跑通部署流程，下次它又问环境变量放哪、构建顺序是什么、日志在哪。你刚调好一篇文章的风格，下个会话它又回到 AI 腔。你刚让它读透一个 SDK，换会话，它又从 README 第一行开始。

Hermes 的 /learn 解决的就是这件事。

它不是记忆功能，也不是收藏夹。更准确的定位是：把一次经验压缩成可复用的 skill。官方文档描述得很清楚：/learn <要学什么> 可以从目录、URL、刚走过的 workflow 里蒸馏出 reusable skill，生成符合规范的 SKILL.md。

接下来讲两件事：/learn 和 skill_manage 到底是什么关系，以及五个你能马上试的场景。


/learn 学的是做法，不是资料

很多人把 Agent"失忆"归因于上下文不够。其实更多时候，问题不在窗口长度，在经验没固化。

这些信息放进普通 memory 太碎，放进知识库又不够动作化：

•这个项目测试前要先启动本地依赖

•这个 API 的分页和鉴权写法容易踩坑

•部署必须先 migration，再 build

•公众号文章不能用教学腔，要先判断再解释

•客户周报有固定格式

它们不是事实，是程序性知识：遇到这类任务时应该怎么做。

Skill 本来就是给 Agent 看的操作手册。/learn 的价值在于不需要你手写这份手册。给它材料，它自己采集、归纳，写成 SKILL.md。


/learn 和 skill_manage，不是一回事

这两个容易混，但入口和用途完全不同。

/learn 是用户侧 slash command。你在聊天框输入，让 Hermes 从材料或刚完成的流程里"学出"一个 skill。

skill_manage 是 Agent 侧工具，Hermes 用它创建、更新、删除 skills。底层调用类似 skill_manage(action="create", ...)，但通常不需要你手打这个工具名。更常见的用法是直接告诉 Hermes：

“

请用 skill_manage 创建一个叫"公众号编辑"的 skill。

两者最后都生成 ~/.hermes/skills/<skill名>/SKILL.md，但适用场景完全不同。

我的判断：/learn 适合从经验里长出 skill；skill_manage 适合把成型的方法写成 skill。


什么情况用哪个

用 /learn：

•刚跑通一个复杂流程，想下次复用

•有一批文档、URL、项目目录，希望自动提炼

•不确定 skill 该怎么写，只知道资料在哪

用 skill_manage create：

•已有清晰 SOP，要 Agent 严格执行

•做团队标准、发布规范、代码 review 规范

用 skill_manage patch/edit：

•/learn 生成的初稿有几处不准，不想重学一遍

推荐的路线不是二选一，是组合：先用 /learn 从真实材料生成初稿，再用 skill_manage patch/edit 精修触发条件、步骤和边界。



五个值得马上试的场景

STEP

1. 学一个 SDK 或内部 API

text
/learn ~/docs/payment-api 目录下的支付接口文档，重点关注鉴权方式、幂等机制、分页逻辑和退款相关错误码

把接口文档变成 Agent 可调用的开发手册。减少写代码时漏鉴权、忘重试、搞错错误处理的概率。

STEP

2. 沉淀部署流程

text
/learn 刚才 staging 环境的完整部署过程：包括构建命令、环境变量检查、数据库迁移顺序、冒烟测试步骤和回滚路径

部署不是一条命令，是一串有顺序的检查和操作。把刚验证过的流程固化，下次不用重新解释。

STEP

3. 生成故障排查手册

text
/learn 刚才怎么修好定时任务没运行的问题：按顺序检查时区配置、服务运行状态、错误日志、文件权限，最后手动执行命令验证

debug 之后最值得保存的不是最后那行修复命令，而是排查路径。团队复用价值很高。

STEP

4. 创建内容写作 skill

有代表作目录时用 /learn：

text
/learn ~/写作/AI专栏 目录下我的文章风格，重点学结构模式、语气控制、案例用法和去 AI 味规则

已经有明确写作规则时用 skill_manage create。前者学旧文章的风格模式，后者制定未来的写作标准。

STEP

5. 固化日常发布 SOP

text
/learn 我的公众号发布流程：先检查标题、摘要、封面文案、错别字和外部链接，再生成朋友圈转发文案和小红书改写版

这类流程不难，但每次都要重复。正因为重复，才值得 skill 化。


几个注意事项

不是知识库。 如果只是保存资料，放 Obsidian、Wiki 更合适。/learn 适合保存"以后还要照着做"的流程。

不是越多越好。 一个 skill 太大，触发模糊；规则太细，维护困难。覆盖"部署 Python 应用到 Fly.io"比覆盖"所有 DevOps"更实用。官方也建议保持 skill 聚焦。

敏感操作保留审批。 涉及生产环境、财务、客户沟通、删除文件的 skill，不要把审批关掉。Skill 会影响未来行为，不能像普通回答一样看完就算。


最后

/learn 和 skill_manage 不是竞争关系，是同一个流程的前后环节：

COMMAND
真实任务 → /learn 生成初稿 → skill_manage 精修 → 下次直接调用

模型决定临场上限，skill 决定长期复用。

别想一口气把所有东西都 skill 化。从最近刚跑通的一件事开始——一次部署、一次 bug 修复、一次文章改稿。让 Hermes 学下来，下次直接调用。真正省时间的不是这次少写了几行提示词，是以后不用再把同一套流程解释第二遍。
