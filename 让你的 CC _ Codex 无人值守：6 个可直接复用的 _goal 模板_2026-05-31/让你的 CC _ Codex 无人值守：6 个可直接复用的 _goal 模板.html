让你的 CC / Codex 无人值守：6 个可直接复用的 /goal 模板

随着 /goal 模式的成熟，在使用 Codex、Claude Code 这类 local agent 时，动辄执行 30 分钟以上的任务，已经是家常便饭。这带来一个问题，越长程的执行，在定义出现误差时，结果偏离的越多。而目标描述越清楚，标准定义越清楚，/goal 模式的执行结果越稳定。

尤其是涉及重构、发布、数据清洗、测试修复、依赖升级这类工程任务时，只定义“帮我做一下”的目标，会带来大问题。必须把目标、输入、成功标准、常见失误和收尾短测一次性写清楚。以下是我们团队在实际生产中使用的 6 个可直接复用到 Codex / Claude Code 的 /goal模板，覆盖：

  • 代码重构
  • 发布流水线
  • 数据清洗
  • 轻量写作
  • 测试修复
  • 依赖升级

使用前，只需让 AI 改成你的技术栈，把每个 inputs补齐，再交给 CC / Codex 执行即可。

一旦验证稳定，改成定时任务，或者用 Webhook 调用，使用效果更佳。


1）代码重构：可回归、无行为改变

/goal YAML 模板
/goal
title: Refactor target module without behavior change
inputs:
  repo: <git url or local path>
  target_paths: [<src/...>]
constraints:
  - preserve public APIs and I/O behavior
  - keep tests green; add missing unit tests for new seams
  - budget_limit_minutes: 60
success_criteria:
  - code passes existing tests (and new ones) locally + CI
  - cyclomatic complexity ↓ ≥15% on target_paths
  - no public signature changes; diff is mostly moves/rename/extract
common_failure_modes:
  - silent behavior drift; hidden globals left behind
  - partial refactor breaks imports or circular deps
  - tests only mocked; no end-to-end guard
short_test:
  - shell: |
      pnpm test && npx complexity-report ./src | grep "Total Cyclomatic"
      git diff --name-only | wc -l
deliverables:
  - PR with commit series: (1) safety tests, (2) pure moves, (3) extraction, (4) cleanup

2）发布流水线：从分支到产物与变更日志

/goal YAML 模板
/goal
title: Ship pipeline from main->release with changelog & artifacts
inputs:
  repo: <git url>
  release_type: <patch|minor|major>
  ci_provider: <gh-actions|gitlab|circle>
  build_cmd: <e.g., pnpm build>
  artifact_paths: [<dist/**>]
success_criteria:
  - tag vX.Y.Z created with semantic versioning
  - CHANGELOG.md updated via conventional commits
  - CI job builds + uploads artifacts; release notes include highlights & breaking changes
  - rollback doc and dry-run job provided
common_failure_modes:
  - tag/version mismatch between package.json 与 git tag
  - artifacts 未上传或可执行位缺失
  - CI secret/permission 导致发布卡住
short_test:
  - shell: |
      gh release view || echo "no release"
      jq -r .version package.json
      test -d dist && ls dist | head
deliverables:
  - PR: ci yaml、release script、CHANGELOG、rollback指南

3）数据清洗作业：幂等、可追溯

/goal YAML 模板
/goal
title: Create idempotent data-clean job with audit log
inputs:
  source: <s3://...|db conn|csv path>
  rules: <spec: trim, normalize, dedupe keys, date parse, schema cast>
  output: <target table or file>
success_criteria:
  - job 可重复运行；对同一输入输出一致
  - 100% 通过 schema 校验；不合格行写入 quarantine 区并含原因
  - 审计日志：输入行数、输出行数、丢弃/修正统计
common_failure_modes:
  - 非幂等（时间戳、随机值）
  - 无错误分类，直接丢数据
  - 大文件内存爆；未流式处理
short_test:
  - shell: |
      python job.py --dry-run --sample 100 | tee run.log
      grep "quarantine" run.log
deliverables:
  - job 源码、配置示例、README、quarantine 样例文件

4）写作简报 → 博文：可发布、含元数据

/goal YAML 模板
/goal
title: Turn brief into publishable blog post with assets
inputs:
  brief_md: <path or text>
  target_cms: <markdown|hashnode|ghost>
  seo:
    - slug: <auto/from title>
    - meta_desc: <120-160 chars>
    - og_image: <generate or pick>
success_criteria:
  - 1500±300 字，结构：引子→问题→方法→实例→结论→CTA
  - 3-5 个代码/图示块，均可单独复制运行或查看
  - 语气一致、无事实错误；通过拼写与链接校验
  - 生成封面图（或占位图）与 alt 文本
common_failure_modes:
  - 图文不匹配/外链失效
  - 只改写 brief，缺证据与示例
  - SEO 元信息缺失或冲突
short_test:
  - shell: |
      npx markdown-link-check post.md
      wc -w post.md
deliverables:
  - post.md、images/、og_image.png、publish checklist

5）测试套件修复：红转绿 + 最小回归护栏

/goal YAML 模板
/goal
title: Repair failing test suite and add regression guard
inputs:
  repo: <git url>
  test_cmd: <e.g., pnpm test -u>
  flake_threshold: <max 1% re-run variance>
success_criteria:
  - 所有测试在 3 次重复运行均通过（≤ flake_threshold）
  - 对每个失败用例附 root cause 注释与修复 commit
  - 新增回归测试覆盖原失败路径
common_failure_modes:
  - 用 sleep 掩盖竞态
  - 只改 snapshot 导致语义回退
  - 忽略跨平台差异（path/locale/timezone）
short_test:
  - shell: |
      for i in 1 2 3; do pnpm test || exit 1; done
deliverables:
  - PR: 修复 commits、测试报告、CI 并行/缓存优化

6）依赖升级：安全基线与可回滚

/goal YAML 模板
/goal
title: Safe dependency upgrade with lockfile hygiene
inputs:
  repo: <git url>
  scope: <all prod deps | selected>
  allowlist: [<pkg@range>]
  blocklist: [<pkg>]
success_criteria:
  - 升级后通过构建、lint、tests、typecheck
  - 生成兼容性报告（破坏性变更与迁移步骤）
  - lockfile 稳定；CI 复现一致
  - SCA 扫描 0 高危
common_failure_modes:
  - 只升不测；忽略 transitive 破坏
  - 未 pin engines/node 版本
  - 忽略生成产物（dist）差异
short_test:
  - shell: |
      pnpm install --frozen-lockfile=false
      pnpm build && pnpm test && pnpm audit --prod
deliverables:
  - PR: 升级脚本、迁移说明、对比基准（bundle size、启动时延）

使用提示

  • 先把每个 inputs补齐，再丢给 /goal。
  • 若要持续推进，给 success_criteria加上“可观察的完成信号”，例如 CI 通过、tag 落地、制品存在。
  • 任何需要外部权限的任务，例如 CI、S3、CMS，都在一开始声明并校验。

使用前，请让你的 CC / Codex 把模板按自己的项目仓库与技术栈进行实例化和补全，例如：

  • Node / Python / Go
  • GitHub Actions / GitLab / CircleCI
  • S3 / GCS
  • Markdown / Hashnode / Ghost

这样可以显著减少 agent 执行过程中的歧义，也更容易得到可验证、可回滚、可交付的结果。

Happy building！
