一、AI 编程最大的误区：太早开始写代码

我们先来看一个非常常见的需求。
老板说：

做一个用户管理模块。

于是你直接把需求交给 AI：
使用 Spring Boot 3。
帮我开发用户管理模块。
需要：
  1. 用户新增
  2. 用户修改
  3. 用户删除
  4. 用户查询
Claude Code 开始工作。
很快生成：
UserController
UserService
UserMapper
UserEntity
UserDTO
UserVO
甚至数据库表也生成好了。
看起来非常高效。
但是问题来了。
你突然想到：
用户是否允许删除？
又补充：
不允许物理删除。
然后：
需要逻辑删除。
过了一会儿又发现：
手机号必须唯一。
然后又想到：
手机号注销后是否可以重新注册？
再后来：
需要支持多租户。
然后：
不同租户的手机号是否允许重复？
最后：
用户删除后历史订单怎么办？
这个时候你会发现：

AI 写代码其实没有浪费你的时间。

真正浪费时间的是：

你在没有想清楚问题之前，就让 AI 开始执行了。

二、Brainstorming 到底是什么？

很多人看到 Brainstorming，第一反应是：

头脑风暴。

然后想到：
大家坐在会议室。
想到什么说什么。
但在 AI 编程场景中，Brainstorming 的意义远远不只是：

随便讨论几个方案。

它更接近：
AI-Assisted Problem Discovery
也就是：

利用 AI 帮你发现那些你还没有想到的问题。

例如：
我要做一个用户管理模块。
普通 AI 编程：
AI：
好的，我开始写代码。
Brainstorming 模式：
AI：
在开始设计之前，我们需要先确认：
  1. 用户是否支持逻辑删除？
  2. 用户名是否唯一？
  3. 唯一范围是全局还是租户内？
  4. 是否支持多租户？
  5. 是否存在用户状态？
  6. 禁用用户是否允许登录？
  7. 删除用户后关联数据如何处理？
  8. 是否需要操作审计？
  9. 是否需要分页查询？
  10. 是否需要数据权限？
这两种方式的区别非常大。
前者是：

你告诉 AI 怎么做。

后者是：

AI 帮你发现问题。

这才是 Brainstorming 真正有价值的地方。

Claude Code 很擅长执行。

↓

问题是：

执行能力越强，越需要正确的任务。

假设你给了一个错误的需求：

↓

↓
Claude Code 高效率执行

快速生成大量错误代码
于是：

↓

所以未来 AI 编程可能出现一个非常有意思的现象：

AI 不一定会减少错误。

如果需求不清晰：

AI 可能只是让你更快地制造错误。

因此：
在 AI 开始写代码之前，先进行 Brainstorming。
这一步会越来越重要。

五、第一步：不要告诉 Claude Code “直接写”

假设现在有一个需求：

医院绩效系统增加绩效方案版本管理。

很多人的第一反应：
帮我开发绩效方案版本管理。
然后 AI 开始写。
我不推荐。
更好的方式是：
现在不要修改任何代码。
我们先进行 brainstorming。
当前需求：
医院绩效系统需要增加
“绩效方案版本管理”。
请不要直接给出代码。
你的任务是帮助我发现需求中没有明确的问题。
请从：
  1. 业务规则
  2. 数据模型
  3. 版本生命周期
  4. 状态流转
  5. 并发问题
  6. 权限
  7. 数据一致性
  8. 历史数据
  9. 审计
  10. 性能
十个方面提出问题。
一次不要假设所有需求。
优先识别最影响架构设计的问题。
这时候 Claude 不应该：
直接写代码。
而应该开始问：
当前系统是否允许多个绩效方案同时生效？
你回答：
允许。
Claude 继续：
那么同一个科室是否允许绑定多个方案？
你回答：
不允许。
继续：
旧版本是否允许修改？
你：
不允许。
继续：
那么是否采用不可变版本模型？
你：
是。
这个过程才是真正的：
AI Brainstorming

七、Claude Code 最适合 Brainstorming 的地方

很多人认为：

Brainstorming 只能讨论产品需求。

其实不对。
对于程序员来说，AI Brainstorming 最有价值的地方之一是：
技术决策。
例如：

这个功能到底应该使用 Redis 还是本地缓存？

不要直接问：
Redis 好还是 Caffeine 好？
因为这种问题 AI 很容易回答：
Redis：
优点……
Caffeine：
优点……
看完还是不知道选哪个。
更好的方式：
我们需要设计一个缓存方案。
当前项目：
Spring Boot 3
MyBatis
Redis
单体部署
预计 1000~2000 用户
10~30 个部门
数据更新频率：
每天一次
查询频率：
高
要求：
数据修改后必须尽快生效。
请不要直接推荐技术方案。
先通过 brainstorming 帮我分析：
  1. 数据访问模式
  2. 一致性要求
  3. 缓存容量
  4. 部署模式
  5. 更新模式
  6. 故障恢复
然后再给出推荐方案。
这时候 AI 的工作方式就改变了。
从：
回答问题
变成：
帮助决策。

八、真正高级的 Prompt：让 AI 反驳你

这是我认为 Brainstorming 中最重要的一点。
不要只问：
这个方案怎么样？
因为 AI 很容易：
这个方案很好。
然后给你一堆优点。
更好的 Prompt：
现在进入架构 brainstorming。
不要默认我的方案是正确的。
你的角色是：
资深 Java 架构师
+
数据库专家
+
安全工程师
请主动挑战我的设计。
重点寻找：
  1. 错误假设
  2. 隐藏风险
  3. 性能问题
  4. 并发问题
  5. 数据一致性问题
  6. 扩展性问题
  7. 安全问题
  8. 维护成本
如果认为方案有问题，请明确反对。
不要为了迎合我而同意。
这一点非常重要。
因为真正有价值的 AI：

不应该只是一个“永远同意你的助手”。

而应该是：

能够挑战你的技术搭档。

九、一个真实 Java 项目的 Brainstorming 示例

假设需求：

医院绩效系统需要每个月自动计算科室绩效。

第一版需求：
每个月计算一次。
听起来非常简单。
但是进入 Brainstorming：
问题一：计算是否允许重复执行？
如果：
9 月份已经计算完成。
后来：
HIS 数据发生修正。
怎么办？
是否：
重新计算？
如果重新计算：
旧结果怎么办？
于是开始出现：
计算批次
问题二：计算过程是否需要可追溯？
如果：
科室提出申诉：
为什么我的绩效是 98,321？
系统能不能回答：
基础数据
↓
计算规则
↓
权重
↓
指标
↓
最终结果
如果不能：

这个系统以后一定会出问题。

于是：
计算快照
出现了。
问题三：方案修改怎么办？
假设：
2026 年 9 月使用方案 A。
10 月：
修改了绩效方案。
那么：
9 月的历史结果
是否重新计算？
答案通常是：

不应该。

于是：
版本冻结
出现了。
问题四：计算失败怎么办？
假设：
100 个科室。
计算到：
第 72 个科室。
数据库异常。
怎么办？
全部回滚？
还是：
保留前 71 个结果？
还是：
支持断点续算？
这时候：

一个看似简单的“自动计算”，已经变成了完整的软件工程问题。

而这些问题：
AI 直接写 CRUD
是不会帮你解决的。
只有：
Brainstorming
才能提前发现。

Brainstorming 最终必须产出结果。
否则：

↓

↓

所以一个完整流程应该是：

↓

探索
↓
Challenge
挑战
↓
Compare
比较
↓
Decide
决策
↓
Converge
收敛
最终得到：
Decision Record
例如：
决策：
绩效方案采用不可变版本模型。
规则：
  1. 已发布版本不可修改。
  2. 修改必须创建新版本。
  3. 历史计算绑定方案版本。
  4. 新版本通过复制旧版本创建。
  5. 一个版本只能处于：
  6. 草稿 / 审核中 / 已发布 / 已停用。
这时候才可以进入：
Claude Code Implementation

十二、现在 Claude Code 才真正开始写代码

经过前面的工作之后。
终于可以告诉 Claude Code：
现在开始实施。
请严格按照以下文件执行：
specification.md
architecture.md
database.md
api.md
tasks.md
acceptance.md
要求：
  1. 先阅读所有 Specification。
  2. 检查当前项目结构。
  3. 对照项目现有编码规范。
  4. 按 tasks.md 顺序实施。
  5. 每完成一个任务进行验证。
  6. 不修改 Specification 中没有涉及的业务。
  7. 如果发现 Specification 存在冲突，暂停并报告。
  8. 不要自行改变架构决策。
注意最后一句：

不要自行改变架构决策。

因为：
Thinking
和
Doing
最好适当分离。
Brainstorming 阶段：

可以挑战架构。

执行阶段：

应该遵循已经确认的架构。

否则：
今天 Redis。
明天 Caffeine。
后天又换本地缓存。
项目就会越来越混乱。

↓

↓
确认方案
↓

也就是：
Brainstorming
↓

↓
发现冲突
↓
Brainstorming
↓
Decision
↓

未来的软件开发很可能就是这种循环。
