Agent 越来越强，为什么框架反而越来越重？
过去一年，很多做 Agent 的人都会遇到一个反常识现象：
模型越来越强，框架却越来越重。
最早接一个 LLM API，就能做一个聊天助手。后来要加工具调用。再后来要加状态、工作流、记忆、失败恢复、人工确认、沙箱、权限、日志、评测、部署。
现在又开始讨论 Runtime、Harness、Managed Agents、Agent Observability。
看起来像是技术栈越做越复杂。
但真正的原因不是开发者过度设计，也不是厂商喜欢造新词。
更准确的说法是：
Agent 正在从“回答问题”，回到它原本的定义：为了目标，在环境中行动。
在经典 AI 教材里，Agent 从来不是聊天机器人。Agent 是能够感知环境，并通过行动影响环境的系统；要设计一个理性 Agent，必须说明它的 performance measure、environment、sensors 和 actuators。
这几个词翻译成人话就是：
它要完成什么目标。
它面对什么环境。
它能看到什么。
它能做什么。
所以 Agent 的核心从来不是“会说话”。
而是“为了目标做动作”。
大模型只是让 Agent 有了更强的大脑。现在框架变重，是因为这个大脑终于开始接触真实世界。
只会回答问题时，框架当然可以很轻
如果 AI 只是回答问题，框架可以非常轻。
用户问一句，模型答一句。最多加一点上下文、结构化输出、简单工具调用。
这时的核心问题是：
模型是否聪明？
回答是否准确？
成本是否能接受？
但只要目标变成“帮我修好这个 bug”“帮我调研这个技术方向”“帮我处理一张工单”“帮我把客户线索录入 CRM”，问题就变了。
它不再是一次问答。
它要读文件。
要查资料。
要调用工具。
要根据结果调整下一步。
要失败重试。
要在关键动作前等待确认。
要结束后留下可回放的记录。
这时真正的问题变成：
它做到哪一步了？
中断后能不能继续？
工具调用错了怎么办？
上下文满了怎么处理？
动作有没有权限边界？
出了问题能不能复盘？
谁批准了这个动作？
这些问题，不是一个模型 API 能解决的。
所以 Agent 框架不是突然变重。
而是 Agent 的任务责任变重了。
Agent 框架的每次升级，都在补“行动系统”的一块能力
可以把 Agent 框架的发展看成一条很清楚的链路。
LLM API 解决的是“怎么获得模型能力”。
Tool Calling 解决的是“模型怎么调用外部工具”。
Agent SDK 解决的是“开发者不用每次手写 Agent Loop”。
Workflow 和 State Machine 解决的是“多步任务怎么组织”。
Runtime 解决的是“任务怎么持续运行、失败后怎么恢复”。
Harness 解决的是“模型怎么在工具、沙箱、权限和反馈中被约束”。
Managed Infrastructure 解决的是“企业怎么把 Agent 当成可管理的工作负载”。
这不是概念堆叠，而是 Agent 一步步接近真实任务后的工程结果。
ReAct 这篇论文已经把 reasoning 和 acting 放在一起讨论：模型不只是生成推理过程，还要在推理过程中产生行动，并从外部环境获得反馈。
Toolformer 进一步说明，语言模型可以学习什么时候调用 API、传什么参数、如何把工具返回结果纳入后续预测。
这两件事放在今天看，意义非常清楚：
大模型 Agent 从一开始就不应该只被理解成 prompt 技巧。
它本质上是一个“推理、行动、反馈”的循环。
只是早期任务简单，所以循环可以很轻。现在任务变长、动作变多、风险变高，框架自然就变厚了。
为什么 LangGraph 这类框架会变重要
LangGraph 的流行，不是因为大家突然喜欢画图。
它抓住的是一个真实变化：Agent 任务开始变成长期、多步、有状态的执行链。
LangGraph 官方把自己定位为 supporting infrastructure for any long-running, stateful workflow or agent，并且明确说它不抽象 prompt 或架构，而是提供 durable execution、human-in-the-loop、memory、debugging、deployment 等底层能力。
这句话很关键。
它说明 LangGraph 不是另一个“聊天封装库”。
它更像一个面向 Agent 的工作流运行层。
当任务只有一步时，你不需要它。
当任务有分支、有循环、有暂停、有恢复、有人工确认时，你就会需要它。
比如一个代码修复 Agent，要读仓库、定位问题、修改文件、跑测试、根据失败结果再改、最后生成总结。
这个过程不是一次模型调用。
它是一个持续推进的任务状态。
所以 Agent 框架开始像状态机、工作流引擎、任务运行时，并不奇怪。
只要 Agent 要承担任务，就必须知道自己在哪里、做过什么、下一步该做什么。
Harness 很重要，但不是终点
最近行业开始频繁讨论 Harness。
这个词可以简单理解成：Agent 的“行动框架”。
模型是大脑，但大脑不能直接碰世界。
它需要通过 Harness 去调用工具、进入沙箱、读写文件、执行命令、请求人类确认、记录过程。
Anthropic 的 Claude Managed Agents 文档把它定义为运行在 managed infrastructure 里的 configurable agent harness，适合 long-running tasks 和 asynchronous work。
Anthropic 工程博客也把 Managed Agents 拆成 session、harness、sandbox 这样的结构，用来支持长期运行的 Agent 工作。
这说明 Harness 确实是当前非常重要的阶段。
但它不是终点。
如果只说“Agent 框架下一站是 Harness”，还是停在表面。
更深的逻辑是：
Agent 越接近真实行动，框架越会变成控制系统。
今天叫 Harness。
明天可能叫 Runtime。
后天可能叫 Agent Control Plane。
名字会变，但要解决的问题不会变：
目标怎么拆。
环境怎么接。
行动怎么控。
失败怎么恢复。
过程怎么观测。
责任怎么追溯。
所以 Harness 是阶段性形态，不是最终答案。
最终牵引框架演进的，仍然是 Agent 的本义：为了目标，在环境中行动。
Coding Agent 为什么最先跑出来
如果要找一个最能看懂 Agent 框架演进的场景，我会先看 Coding Agent。
原因不是程序员最容易被替代。
而是软件工程天然适合 Agent 工程化。
代码仓库就是环境。
终端就是工具。
测试就是反馈。
diff 就是行动结果。
Git 就是版本记录。
CI 就是自动验证。
Code Review 就是人类审查。
Rollback 就是恢复机制。
这套环境天然给 Agent 准备好了“目标、行动、反馈、审查、回滚”的闭环。
所以 Claude Code、OpenHands、SWE-agent、Qwen Code 这些方向会先成熟，不是偶然。
AI Coding 的下一步，也不再只是“写代码更快”。
而是“软件变更能不能被 Agent 稳定接管”。
这会倒逼框架提供更多能力：
仓库上下文管理。
任务拆解。
测试执行。
失败重试。
权限边界。
沙箱环境。
代码审查。
过程记录。
所以 Coding Agent 是一个窗口。
它让我们提前看到：当 Agent 进入真实任务，框架到底会被迫长成什么样。
MCP 说明 Agent 正在连接更多环境
Agent 要行动，首先要接触环境。
这也是 MCP 变重要的原因。
MCP 官方文档把它称为连接 AI applications 和 external systems 的开放标准，还用 “USB-C port for AI applications” 做类比。它解决的不是模型聪不聪明，而是 AI 应用如何连接文件、数据库、工具和工作流。
这件事很关键。
Agent 不能只待在聊天窗口里。
它要接数据源。
接工具。
接企业系统。
接本地文件。
接工作流。
但连接环境之后，风险也随之上升。
一个不能调用工具的 AI，最多是回答错。
一个能调用工具、读文件、改代码、发邮件、写数据库的 Agent，错误就会变成行动后果。
所以 MCP、工具生态、工作流协议越发展，权限、沙箱、审计、评测就越重要。
这不是两条线。
这是同一条线的两面：
连接环境带来行动能力，也带来治理需求。
未来的关键，不是框架名，而是任务责任
开发者和企业到底怎么选 Agent 框架？
我不建议先问“哪个框架最好”。
这个问题本身就不对。
更好的问题是：
你的 Agent 到底承担多重的任务责任？
如果只是简单对话和少量工具调用，轻量 SDK 就够。
如果你需要稳定的结构化输出、类型约束、依赖注入，可以看 Pydantic AI、OpenAI Agents SDK 这类路线。
如果任务有多步流程、分支、状态和中断恢复，就应该看 LangGraph、LlamaIndex Workflows、Microsoft Agent Framework 这类工作流和状态层。
如果是代码修复、仓库理解、终端执行和测试反馈，就要单独看 Coding Agent 路线。
如果要接企业系统，就不能只看模型和框架，还要看身份、权限、审计、观测、部署和治理。
如果要做个人常驻 Agent，就必须先考虑沙箱、凭据隔离、插件安全和运行环境，而不是先看它能接多少渠道。
一句话：
任务越短，框架可以越轻；任务越长，框架必须越稳；动作越危险，系统必须越可控。
接下来，Agent 框架还会继续变
未来一两年，Agent 框架大概率会沿着几条线继续演进。
第一，环境连接会更标准化。
MCP 只是一个开始。Agent 需要接入更多数据、工具、应用和企业系统。只要它还要行动，就会持续需要更稳定的连接协议。
第二，行动控制会更严格。
工具调用不会只停留在 function call。它会继续向审批、权限、沙箱、凭据隔离、策略执行发展。
第三，状态管理会更重要。
长任务一定会跨上下文、跨时间、跨工具。Agent 不可能每一步都从零开始，所以 state、memory、checkpoint、resume 会成为核心能力。
第四，评测会从结果走向过程。
一个 Agent 最后答对了，不代表过程安全。未来评测要看它调用了哪些工具、有没有越权、有没有绕路、失败时怎么恢复。OpenTelemetry 的 GenAI observability 工作已经在推动 AI agent observability 的语义约定标准化。
第五，企业会需要控制平面。
当组织内部有几十个、几百个 Agent 时，企业真正关心的不是每个 Agent的 prompt，而是谁能统一注册、授权、监控、审计、下线这些 Agent。
这就是为什么 Microsoft Agent Framework 会把自己称为 open-source SDK and runtime，并强调 multi-agent workflows、interoperability、state、telemetry 这些能力。
未来不是所有框架都会变成同一种形态。
但它们都会被同一个问题牵引：
如何让 Agent 不只是会说，而是能在真实环境里持续、可靠、可控地做事。
最小行动建议：先不要急着选框架
如果你现在正在做 Agent 选型，不要第一步就比较框架功能表。
先做三件事。
第一，写清楚任务形态。
这个 Agent 是回答问题，还是完成任务？
是一步完成，还是多步推进？
是只读信息，还是会写入系统？
是低风险辅助，还是高风险动作？
第二，标出责任边界。
它能看哪些数据？
能调用哪些工具？
哪些动作必须人类确认？
失败后谁负责？
过程是否要记录？
第三，设计一个最小验证任务。
不要一开始就做大系统。
用一个简单任务验证四件事：
能不能稳定调用工具。
能不能保存状态。
失败后能不能恢复。
过程能不能被回放。
这四件事比“demo 看起来很酷”重要得多。
因为真正进入生产环境后，Agent 的价值不是一次惊艳表现，而是长期稳定交付。
写在最后
Agent 框架变重，不是坏事。
这是 AI 真正开始做事的代价。
过去我们主要关心模型能不能回答。
现在我们必须关心 Agent 能不能行动。
再往后，我们会更关心这些行动能不能被组织管理。
Agent 越像一个真正做事的人，框架就越要像一个能管理责任的系统。
未来的分水岭，不是谁更会调用模型。
而是谁更能把模型安全、稳定、可恢复、可审计地放进真实任务里。
