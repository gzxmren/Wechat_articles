Agent 自进化的四块拼图，DeepSeek Harness 拼出了三块

全文约 6000 字 · 阅读需要 15 分钟


DeepSeek Harness（下面简称 DSH）疯狂刷屏：插件树、创造模式，还有「会自我修改的 Agent」。这篇就从自进化的角度看：DSH 做了什么？缺了什么？

让 AI 系统改进自己是个老命题，学界叫 RSI（Recursive Self-Improvement）；把它缩小到今天工程上可操作的版本，姑且叫做「轨迹自进化」。原料是 Agent 干活留下、今天大多用完即弃的完整记录——哪步对了、哪步错了、错在哪里。学到的东西，可以训进模型权重，也可以落在模型外面那层 Harness 上。

不管走哪条路，有四样东西缺一不可。轨迹要可信：记录掺了假，学到的就是假经验。对象要可改：学出来的改进，得有一个标准化的落点。验证要可靠：改完总得有办法确认改对了没有。最后，还得有一个会从失败里学习的优化器。前三样是基础设施，优化器才是「自」进化本身。

这四块拼图，DSH 拼出了三块——可信的轨迹、可改的对象是完整的，验证有了源码层面的底座，但没有看到从失败里学习的优化器。

01

循环自己就是插件

装之前不难猜它是什么：模型公司标配 CLI Coding Agent，大概是 DeepSeek 版 Claude Code。MIT 协议，Developer Preview，README 用全大写提醒会有破坏兼容的改动，都符合这个预期。

装好之后一看，不是这么回事。我让 CLI 把生效配置完整打印出来，得到一棵四百多行的插件树，其中一行是 agent-loop——Agent 的主循环本身——和文件工具、模型适配器排在同一张列表里，格式一模一样。

多数 Agent 产品里，循环是核心，插件围着核心转。这里的循环自己就是插件。

1991 年，Torvalds 在邮件列表里发布 Linux 时说，这只是个业余爱好。他发布的东西今天看再清楚不过——一个内核；「拿来就用」的体验，后来由 Debian、Red Hat 这些发行版补上。

放回今天：Claude Code 和 Codex 走得更接近发行版逻辑，开箱即用、体验完整。前者早有 Skills、Hooks、Subagents、Plugins、MCP、LSP 一整套官方扩展点，后者也是 Apache-2.0 开源；Agents SDK、OpenHands、LangGraph 这些 runtime 同样能深度定制执行流程。

「别人都不能改」从来不成立。DSH 的不同在于，它把开放边界一直压到循环、日志、工具注册表这一层——别家收在里面的最底层，它摊开给你。按 1991 年那个类比，DSH 摊出来的这一层，对应的就是内核。

摊开的方式，来自 DSH 底下垫着的元框架 Cordis。所谓元框架，就是造框架的框架：自己不提供具体功能，只规定部件怎么拼装、怎么拆卸。

它的口号是 Everything is a Plugin。口号很多项目都喊过，差别在覆盖范围：这里的模型适配器、工具注册表、会话日志和主循环，全部由插件提供；从官方架构文档能读出的立场是，没有一个必须改源码才能动的特权核心。Cordis 也不是临时造的轮子，它同时撑着 Koishi 聊天机器人生态的上千个插件；DeepSeek 做的，是把这套组合文法从聊天机器人推进到 Agent 控制面。

对四块拼图来说，这补上的是「可改的对象」：要改进 Agent，学到的改法得有一个标准化、彼此通用的落点。此前论文里的「编辑 Harness」，编辑对象多是各家实验室自搭的脚手架，改法互不通用；在 DSH 里，patch（增量的配置修改）、preset（预设的插件组合）和插件本身都是标准件，而且这套官方文法一直覆盖到循环这一层——而以往的开放格式，比如 Anthropic 的 Skills，多停留在外围产物。

改得动，还得退得回。Cordis 的 effect 机制要求插件把事件监听、服务注册、计时器这些副作用登记在案，并附上清理逻辑；卸载时框架按登记逆序撤销。

别把它当成普通的工程洁癖。撤不干净的副作用就是幽灵状态；一个要成百上千次试补丁的优化器，如果每次失败的实验都留一点残渣，后面每一次实验都跑在被污染的运行时上。先有可逆，才谈得上自动实验。

它也有边界。这种可逆只管框架内的副作用，写进数据库的行、发出去的消息、跑完的 shell 命令，谁也不能倒放；「循环可替换」也有分寸——卸载循环插件时，框架会先停掉正在跑的 Agent、处理完队列里的消息、再拆掉实例；有持久日志才能在重挂后重建，这是架构层的能力，不是当前对话里无感「热换」循环。

还有一条：preset 在会话内是固定的，已经产生内容的会话禁止中途切换插件组合，以免历史里的工具调用和新工具集对不上。一个把「可组合」做到循环这层的系统，反而禁止会话中途重组——编辑自由划到这里为止；再往前，会话历史的一致性就保不住了。

02

轨迹自进化的四条路线

DSH 为什么把「可改的对象」做到这个深度，放回整个领域看得更清楚。做「轨迹自进化」的，路线分成四派；判断谁是谁，两个问题就够。

第一，轨迹怎么用？一条路当资产：把干活记录提炼成技能、规则、记忆，往后靠检索复用。另一条路当训练信号：拿轨迹做强化学习，把经验写进模型权重。

第二，改进落在谁身上？落在 Harness 的外围产物上，落在干活的模型本体（下文称执行模型）上，或者落在一个专门养出来的外部模型上。

两问交叉本来是六个格子，有两格是空的：训练信号只能写进权重，落不到提示词和配置文件上；给干活的模型本体喂经验，直接用原始轨迹就行，先压成资产再训等于白丢一道信息。剩下四格，就是四派：

两个问题交叉出四条路线，斜纹格为天然空白

工程复用派走得最远，已经从论文走进产品：Anthropic 把技能定成了开放文件格式，AWS 把「从经验中学习」做进了托管服务，OpenAI 在官方 Cookbook 里给出成套的改进流程。在我看来，这一派的长处和短板是同一件事：把轨迹蒸馏成资产，可解释、可审计、能跨模型迁移；但蒸馏本身有损耗——一项 ICML 2026 的因果干预实验发现，Agent 一致依赖原始轨迹，却经常忽视甚至误读压缩后的经验。难怪这一派的严肃系统，比如维护上下文手册的 ACE（arXiv:2510.04618），都把功夫花在验收门控上：资产入库之前，先重跑验证。

训本体派论文最多，思路也最直接：拿原始轨迹直接训权重。EvoHarness-RL（arXiv:2608.05446）把 ALFWorld——一个在模拟环境里做多步任务的 Agent 测试集——的成功率从 47.9% 训到 96.9%。代价同样直接：训练一次的成本摆在那里；而且能力焊在那一个模型上，模型换代，这份经验很难原样带走。

同一篇论文还观察到：训练之后，模型对 Harness 的调用频率自己降了下来——能稳定内化的行为，强化学习会把它从 Harness 里吸进权重；吸不进去的，比如跨任务的经验查询，顽固地留在外面。内化与外置的分界线由任务结构决定，不由哪家厂商的路线图决定——这也是工程复用派和训本体派会长期共存的理由。

训外部派最年轻：不动执行模型，专门训一个外部「工程师」模型来读轨迹、改 Harness，8 月刚出实物——正是第四块拼图的雏形。

资产训外部派接近空白——截至我调研的时点（8 月 16 日），没有找到把这条链路完整走通的公开工作：先把轨迹压成资产，再拿资产去训外部模型。冷清不难理解——比起直接用原始轨迹，多压一道就可能多丢一道信息；这条路要成立，资产层得沉淀出单条轨迹里读不出来的结构——比如跨任务、跨 Agent 聚出来的规律——才行。是逻辑死路还是没人走到，我倾向于后者：这一格值得有人试。

翁荔 7 月初那篇 Harness Engineering 文章给过一个优化对象的演进序列：提示词 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码，并判断 RSI 的近期路径，不太可能从模型直接改写权重开始。DSH 开源后摊开的，正是这个序列中段的 Harness 代码层；序列末端那个会学习的优化器，仓库里没有。

03

轨迹要可信，先看 session log

四派吃的都是同一种原料。原料靠不靠得住，取决于日志层的设计纪律——DSH 把这套纪律直接写进了源码。

单一事实源。session log（会话日志）是 append-only 的，只增不改；每一轮发给模型的消息，都从日志现推出来，系统里不存在第二份可以随手改的「真实对话」。好处要从反面看：如果存在两份，它们迟早不一致，而你永远说不清哪份是真的。

会计史上有个先例。复式记账普及之后，「生意有没有做对」开始变成可以事后核查的问题。session log 干的是同一件事——不保证每一步都对，但保证每一步都能被查。

调用前先校验。装配了 invariant 组件（一致性校验）之后，每次调用模型前，框架会从日志重新投影出应该发给模型的消息序列，和循环实际组装的请求逐项比对——invariant.ts 里能数出它盯的字段：model、system 提示、采样参数、工具列表。对不上就拒绝调用，宁可停在模型调用之前，也不带着一段无法从日志解释的上下文继续跑。不过它是可选的诊断组件，随包发布的 TUI（终端字符界面）和 Web 版默认没有挂载。

并发执行，顺序提交。工具调度允许多个工具同时执行，但结果提交严格按模型发起调用的顺序推进。道理不玄：要是谁先跑完谁先提交，同一段历史每次重跑顺序都不同，重放从此免谈——执行可以抢时间，历史不能抢顺序。中止也照记不误：已中止、还没派发的调用，会补一条「派发前已中止」的合成结果，重放时不会出现只有调用、没有结果的悬空记录。

压缩不改写历史。上下文太长要压缩，难在压缩和单一事实源怎么共存。DSH 的做法是拆成两层：审计历史原样保留，被替换的只是模型当前可见的片段。摘要也不是自由发挥——输出固定为八个部分（原始诉求、关键概念、改过的文件、错误与修复、下一步……），新摘要会合并前一份，避免「摘要的摘要」逐层失真。压缩请求还会尽量沿用已有的消息开头——开头不变，就有机会命中模型服务的前缀缓存，复用上次算过的部分，更快也更省钱。

一条完整、可重放、调用与结果配对的轨迹，正是工程复用派蒸馏资产、训外部派读失败记录时要的输入格式。

改完，凭什么信改对了。每一派都躲不开这个问题——四块拼图里「可靠的验证」，说的就是这件事。DSH 的答案在 test-support 里：llm-replay 能把日志里的模型输出按轮次重放——真实的循环和工具链照常跑，只是不请求真实模型，同一段历史可以反复重放；配套的 mock server 是一台专演故障的假模型服务器，我读的快照里带 23 种具体故障脚本——断连、限流、流中断、畸形 JSON、挂起。

Agent 测试最怕「模型今天刚好答对了」；确定性重放加可编排故障，能把恢复、取消、脏流量变成可复现的测试。这部分我只读了实现，没有实跑，成色待验。

04

会学习的优化器，仓库里还没有

第四块拼图呢？DSH 里确实有一个最容易被当成优化器的功能。

UI 里有个 preset 叫「创造模式」。这是官方界面的中文名——仓库里没有对应的正式英文名，preset id 和技术目录都叫 cordis。把它和「循环也是插件」放在一起，很容易推出一个响亮的结论：Agent 可以在运行中把自己的循环拔掉，换一个新的上去。这话听着痛快，可惜是错的。

追进实现，先数工具。创造模式给模型装配一组自指工具，我读的快照里实际注册 7 个：三个检查当前运行时，四个负责定义、运行、停止和删除动态插件（README 里还写着五个，同一个 commit 内文档就没跟上源码，Developer Preview 的日常）。

模型确实能用它们做一轮完整实验：查运行时、写插件、挂载观察，不满意就更新，出问题就回滚；第一次运行要用户审批，失败不推进版本指针。它把「给 Agent 加一个工具」的成本，从改代码、重启、重新进入上下文，压缩到一次会话内的往返——对研究 Harness 的人，这是很稀罕的实验条件。

但它离「会学习」差得远。动态插件默认只活在当前进程里，重启就消失；不会自动写进仓库、配置或永久 preset，也没有内建机制把实验晋升成生产插件。改动只落在运行时组合这一层：模型权重没动，主循环的源码 agent.ts 也没有被原地重写。官方对信任问题也不含糊：动态代码跑在 host 进程里，node:vm 明确不是安全边界，应该按接近 shell 权限的高信任代码对待。

还有一条证据，是仓库自己留下的。8 月 11 日的命名决策里，团队把旧的 self-modification 目录改名成 extensions，理由之一是：这个名字描述稳定职责，而不是声称 agent modifies itself。外面把「自我修改」越传越大，项目自己在给这个词降温。

拆开看，「自我修改」其实是三层：

「自我修改」的三层拆解

「能当场实验、默认不落地」，不只创造模式如此。仓库里最像自动迭代循环的组件叫 Ralph：围绕同一个目标，一轮一轮创建全新的子 Agent，轮与轮之间传一份有上限的结构化报告，长期事实源是工作区，不是子 Agent 的对话记录。外层循环怎么转、最多转几轮，由部署代码控制——模型可以填内容、报状态、给证据，外层循环不归它管。

而它的「完成」是子 Agent 自报的，没有独立的验收者替它把关。连仓库里最像优化器的循环，都还缺那个说了算的验收环节。

真正的优化器长什么样，仓库之外已有实物。8 月 3 日，上海交通大学、小红书和东南大学的研究者放出 Harness-R1（arXiv:2608.02276）：执行模型冻结不动，另训一个同基座的 9B（90 亿参数）「Harness 工程师」，专门读失败轨迹、生成 Harness 补丁，奖励来自任务重跑的结果——正是上一段 Ralph 缺的那个独立于自报的验收信号。三个 Agent 任务基准平均从 44.3% 提到 53.6%，还高过了参数量大得多的前沿模型即兴改 Harness 的成绩（48.8%）——论文自己的解读是，把少量失败转化为普遍有用的编辑，是规模本身给不了的能力。论文里另有一组叠加实验：先把执行模型微调到 59.2%，工程师在这之上再推到 64.2%——改权重与改 Harness，两条路可以叠起来走。训练代码和 9B 工程师的权重也已开源（Apache-2.0）。

理论上，它正好可以把 DSH 当实验场。

第四块拼图今天最现成的实现，其实是人。在 Claude Code 里改配置、调提示词、写技能，这些本来就是 Harness 工程师的活，只是眼下由人来干，靠的还是各自的手感。DSH 把干这份活的工作台摊成了标准件，Harness-R1 预演了把这份活交给一个模型。真到交出去那天，人大概也不会退场，只是挪位置：往前一步，定义目标；往后一步，评估结果——中间那段靠手感拧参数的活，本来就不是人最值钱的部分。

05

把 DSH 当实验场，先看三个维度

假设你也认同这个方向，想把一个会学习的优化器——Harness-R1 那样的工程师模型也好，自己写的也好——接到 DSH 上，值得先看三个维度。

第一个维度是接口。用强化学习的语言说，一个合格的实验场要给三样东西：观察、动作、奖励。DSH 恰好都有对应物。

观察，是从 append-only 日志投影出来的上下文，可复现；动作，是三级编辑面——patch 改配置、preset 改组合、动态插件改运行时；奖励这条最弱：llm-replay 加故障 mock server 能把「同一段历史再跑一遍」变成确定性操作，够做回归验收的地基。但真要给一次改动打分，仍得像 Harness-R1 那样重跑任务拿结果（重放设施未实跑的保留意见照旧）。在我看来，三样拼起来已经接近强化学习意义上一个现成的环境接口——只是今天还没有优化器来接。

第二个维度是执行面。先看消息这一侧：followup、steer、inject 三种消息共用同一个 Inbox，区别只在进哪个队列、要不要唤醒——followup 排进下一轮并唤醒，steer 插进下一步并唤醒，inject 同样插进下一步，但不唤醒。数据到达和唤醒决策解耦，后台结果可以安静地变成下一步的上下文，不必每来一条消息就多烧一次模型调用。

再看工具调用这一侧。一次工具调用不是一步跳进函数：从写入日志的 tool/call 到写入日志的 tool/result，中间排着固定的工位——预执行检查、可选审批、执行、结果规范化——策略、超时、沙箱都插在工位之间，不用改循环本身。对一个要自动改 Harness 的优化器，这些工位就是现成的插桩位。

第三个维度是集成成本。DSH 是 TypeScript / Cordis 栈，四派的训练管线几乎都在 Python 生态；轨迹导出、headless 驱动这些桥得自己架（我实测用的就是 headless 模式）。还要掂量 Cordis 本身的维护集中度：要把长期实验押上去，得先想清楚它停更了怎么办。

该不该押注，取决于你是谁。做 Agent 平台的，拆解它是一笔很便宜的研发情报——一个行为可重放、部件可对照的实验对象，能替你自己的架构决策省学费。做 Harness 优化方向的，这里有一个还没人占的位置：第四块拼图空着，实验场接口现成，先付集成成本的人先拿到数据。只想给团队配一个稳定顺手的 Coding Agent 的，别急着进场——架构漂亮不是迁移的理由；兼容承诺、插件生态、多人环境的安全边界、长会话稳定性，Developer Preview 都还给不了。

06

内核、发行版，以及往后十二个月

真机实测的成绩单不差。给 deepseek-v4-flash 和 deepseek-v4-pro 各出两道题——修一个带边界错误的缓存，写一个带优先级和环检测的依赖规划器，合计 12 项验收、由独立脚本执行、不采信模型自报——两边都是 12 / 12 全对；按测试当日官方单价估算，总成本折成人民币不到两毛钱。

不过，能干活和成品是两回事。随包的 TUI 和 Web，是内核附带的参考实现；打磨过的默认体验、兼容承诺、生态，这些发行版的正业它今天还没有。

最后，是个人对未来十二个月的三个猜测。

一，专职的 Harness 工程师模型，会比让通用大模型即兴改更划算。Harness-R1 用 9B 的专职模型，在同一组基准上打过了参数量大得多的前沿模型即兴改 Harness——「读失败轨迹、出补丁」看起来更像一个专业工种，不是通用能力的自然溢出。我判断会有更多团队沿这条路训小模型。证伪条件：某个通用前沿模型在同类基准上免训练反超。

二，验证设施会从测试环节升格为训练基础设施。四派共用一个难题：改完凭什么信。Ralph 的短板（完成靠自报）和 Harness-R1 的解法（重跑当奖励）指向同一件事——奖励信号的质量，决定这条路的上限。剑桥和 NVIDIA 的一组研究者把这个难题又推进了一层（红皇后哥德尔机，arXiv:2606.26294）：验证器固定不动，优化器迟早学会钻它的空子，所以验证器得和 agent 一起进化。llm-replay 这类重放设施，今天待在 test-support 目录里，明天可能站到训练管线的正中间。证伪条件：出现完全不重跑任务、纯靠离线信号也能稳定改进 Harness 的工作。

三，「经验」会有一场文件格式之争。Anthropic 的 Skills 把外围产物定成开放格式，DSH 把文法推进到循环层；轨迹、patch、preset 的交换格式，一旦有人用脚投票，生态会聚得很快。观察信号有两个：一看 DSH 什么时候摘掉 rc——摘了，说明团队想把它补成发行版；二看第三方插件里长不长得出真被人复用的东西——长出来了，内核生态才算成立。证伪条件：十二个月内，轨迹、patch、preset 仍是各家自有格式，没有一种被第二个独立项目实际采用。

三条之外，还有一篇论文把时间尺度拉得更长。Matei Zaharia 组 7 月的 Recursive Harness Self-Improvement（arXiv:2607.15524）把 Harness 定义成数据生成组件：运行轨迹既改当下的 Harness，也喂未来的基座模型训练。照这个方向走，四条路线的终局更可能是融合——同一条经验管线，四个更新落点，成熟的系统会同时占用其中几个，而不是选边站。

Linux 内核发布的时候，没人能预料发行版生态后来长成什么样。DSH 会不会有自己的 Debian 时刻，现在说不准。

接下来我最想看到的一步，是谁第一个把 Harness-R1 这样的工程师模型，接到 DSH 这样的实验场上？

在那之前，「自进化」里的那个「自」，还是人。
