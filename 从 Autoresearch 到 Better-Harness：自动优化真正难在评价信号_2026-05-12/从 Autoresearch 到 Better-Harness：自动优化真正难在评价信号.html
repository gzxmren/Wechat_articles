从 Autoresearch 到 Better-Harness：自动优化真正难在评价信号

01 自动优化先要有正确方向

最近 Karpathy 的 Autoresearch 很火。

它把改进拆成了一套实验循环。

跑实验，看指标，变好就保留，变差就丢弃。

但这个循环能跑起来，靠的是一个前提——评价信号必须足够清楚。

如果指标本身错了，自动优化会把错误放大。

那类似的实验循环，能不能用在 Agent harness 的改进里？

LangChain 在 Better-Harness 这篇文章里给出的答案是：可以，但要加约束。

02 Better-Harness 的六步流程

所以 Better-Harness 这篇文章，其实不是在说：再写几句更聪明的 prompt，就能把 Agent 调好。

他们把这套改进 harness 的方法，叫做 Better-Harness。

本质上，它是一套受控的实验流程。

我们先从一个小例子开始。

假设你有一个 Agent，任务是：先搜索资料，再整理摘要，最后帮用户写一封邮件。

你发现它经常犯一个错：明明资料已经够了，它还在反复搜索，迟迟不进入写邮件这一步。

那你不能只凭感觉说：我把 prompt 改一下，应该就好了。

Better-Harness 的第一步，不是立刻改 prompt，而是先把这种失败整理成 eval。

eval 可以理解成一组测试题。每道题都描述一个真实任务，并且标清楚什么叫做“做对了”。

比如这道题里，做对就不是“搜得越多越好”，而是：信息够用以后，要停止搜索，开始写摘要和邮件。

这就是六步里的第一步：收集并标注 eval。

也就是把一批真实或人工设计的任务，整理成测试题，再给它们打上行为标签。

比如这道题的标签可能是：搜索是否适时停止，是否进入下一步，邮件是否覆盖关键信息。

第一步完成以后，才进入第二步：把 eval 拆成优化集和留出集。

优化集用来发现问题、提出改动；留出集先藏起来，不参与改 prompt。

这一步很关键，因为如果你只在同一批题上反复调，Agent 很可能只是把这几道题“背熟了”，并不是真的变强。留出集是为了测试改进后的harness的泛化能力。

第三步，跑基线。

也就是先用当前版本的 harness 跑一遍 eval，记录原始表现。

比如十道搜索加写邮件的任务里，它有六道会过度搜索，两道会漏写邮件重点。这个数字就是基线。

第四步，看 trace，做一个定向改动。

trace 就是 Agent 执行任务时留下来的过程记录：它搜了什么、点了什么工具、在哪一步开始绕圈。

如果 trace 显示它的问题是“不知道什么时候停止搜索”，那这次改动就只针对这个问题，比如给工具说明加一条原则：当已有信息能覆盖用户目标时，停止搜索并进入输出阶段。

注意，这里一次只改一个方向，不要同时改多个。

第五步，验证有没有回退。

先看优化集分数有没有变好，再看留出集有没有也变好。

如果优化集变好、留出集变差，就说明它可能只是在刷熟悉题，并没有获得更稳定的能力。

第六步，人工审核。

因为分数通过，不代表产品体验一定能上线。

比如新指令虽然减少了过度搜索，但也可能让 Agent 太早停下来，摘要变浅。这个时候就需要人看一遍：这个改动放到真实用户那里，是不是确实更好。

所以这六步连起来，就是先建测试题，先跑原始分数，看过程记录，做一个小改动，再用没见过的题防作弊，最后由人挡住上线风险。

03 为什么要拆优化集和留出集

六步里面，最容易被低估的是第二步——拆数据。

为什么要拆？

打个比方。你给一个新同事一组工单，让他练手。练完之后你考他，用的还是同一组工单。他全对了，你能说他学会了吗？

不能。他可能只是记住了答案。

所以你得留一部分工单，练的时候不给他看，考的时候才拿出来。

这就是留出集。

优化集用来让系统提出改动。留出集只负责检查：这个改动在没见过的样例上，还能不能成立。

六步里另一个容易忽略的是第六步——人工审核。

留出集能告诉你，改动有没有通过更多样例。

但它不一定能告诉你，改动适不适合上线。

有些指令虽然能涨分，但写得过度具体，只服务某个样例。放到生产里会浪费上下文窗口。

人工审核就是检查：分数上涨之后，产品体验有没有真的变好。

留出集防作弊，人工审核防上线翻车。两道关卡，各管一件事。

04 eval 不只是验收表

流程讲完了，回到一个更根本的问题。

这套流程能跑起来，全靠 eval 提供方向。

eval 在这里的角色，跟机器学习里的训练数据很像。

训练数据里的每个样例，会给模型一个梯度信号，告诉它往哪个方向调权重。

eval 里的每条样例，也会给 harness 一个信号——Agent 有没有选对工具，有没有产出正确结果。

这个信号会推动下一轮 harness 改动。

可能是改 prompt，可能是改工具说明，可能是调工作流边界，也可能是调工具组合方式。

所以 eval 从验收表，变成了改进循环里的方向信号。

方向一旦偏了，harness 优化就会往错的地方走。

05 高质量 eval 从哪里来

既然 eval 是方向信号，那 eval 的质量就决定了系统能走多远。

学习系统追求的，是在没见过的新输入上也能工作。

但数据不可能无限多。你不可能把生产里所有 Agent 行为都写成样例。

所以解法是：一小组策展过的 eval，只要标签清楚，覆盖关键行为，它比几千条噪声很大的 eval 更有价值。

重点是你手里的 eval，能不能代表真实生产里的目标行为。

如果代表不了，系统会学到错误偏好。

它可能为了避免出错，总是追问用户。

这些行为在分数上可能变好，放进产品里会变差。

eval 从哪里来？

第一类，手工策展。团队自己写样例，把希望 Agent 在生产里怎样做，写成具体样例。价值高，但很难规模化。

第二类，生产 trace。真实用户怎么用，Agent 怎么失败，工具调用卡在哪里，这些都会留在 trace 里。一次失败 trace 可以变成一个 eval。用户纠正 Agent 的 trace 价值更高，因为它直接指出系统偏离了什么。

第三类，外部数据集。外部数据可以用，但要筛选、改写、对齐。它代表的是别人的任务和成功标准，所以更适合作为原材料。

06 标签让问题变成行为地图

光有 eval 还不够，每条 eval 都要打行为标签。

比如工具选择，比如多步推理。

标签把 eval 从一堆题目，变成一张行为地图。

没有标签，你只能看总分。

总分很容易骗人。一次修改让总分上升，可能只是工具选择变好了，追问质量已经回退。

标签能告诉你，每条 eval 在塑造哪类行为。

它也支持定向实验——只跑某类样例，成本更低，诊断也更清楚。

eval 质量够好，优化循环才有坡可以爬。

但 eval 一旦进入优化循环，它就不只是验收表了。

它会变成系统爬坡的方向盘。

方向盘如果偏了，Agent 就会学会一件事：让这批题的分数更好看。

这不等于它真的更会服务用户。

所以留出集和人工审核，在这里不是流程装饰，而是防止优化跑偏的刹车。

07 真正要看的不是涨了多少分

这套方法跑起来以后，LangChain 用 Claude Sonnet 4.6 和 GLM-5 在一小组代表性 eval 上做了实验。

先用优化集爬坡，再用留出集看泛化。

他们看到的效果，主要落在几类 Agent 行为上。

但对我们来说，真正值得看的不是某次实验涨了多少分。

而是它暴露了一个更普遍的问题：很多 Agent 失败，不是因为它完全不会做任务，而是行动节奏不对。

该停的时候继续搜，该动手的时候反复确认，该问目标的时候去问实现细节。

Better-Harness 的价值就在这里。

它把这些模糊的坏体验，变成可以被 eval 捕捉、被 trace 定位、再被 harness 定向修正的行为问题。

所以最后要改的，也不一定只是 prompt。

可能是工具说明，可能是工具调用顺序，也可能是整个工作流边界。

这比“LangChain 改了哪几条规则”更重要：它给了我们一种看 Agent 失败的方式。

08 eval 也需要长期维护

最后说一下 eval 的长期维护。

一条 eval 一旦被正确处理，它可以留下来做回归测试，防止未来改动把旧能力弄丢。

但 eval 集不能只增不删。

模型变强以后，有些样例没有区分度。产品目标变化后，有些样例在塑造错误行为。

这跟软件测试很像。测试太少会漏掉问题，测试太乱会拖慢迭代，测试只增不删会变成噪音仓库。

而 eval 维护能持续运转，靠的是 trace 提供的密集反馈信号。

第一，自动错误检测。持续监控生产 trace，把失败自动分类、聚类，不用等人工发现。

第二，从生产 trace 自动生成 eval。Agent 犯了错，那条 trace 就是一个 eval。用户纠正了 Agent，那条 trace 价值更高，因为它直接标出了系统偏离了什么。

第三，比较 harness 版本。两个版本的 harness 跑同一组任务，用 trace 做逐条对比，看哪个改动带来了新行为。

这三件事串起来，就是一个飞轮。

更多使用，产生更多 trace。更多 trace，沉淀更多 eval。更多 eval，改出更好的 harness。

长期看，成熟的 Agent 团队，核心资产会从单条 prompt，转向一套持续生长的 eval 和 trace 系统。

09 核心资产会转向 eval 和 trace

如果你有兴趣，可以直接把 LangChain 这个 GitHub 项目链接丢给你的 AI 去研究。

让它帮你看配置怎么写，脚手架怎么跑，哪些文件可以作为 harness 的可编辑面。

但真正要花力气的，是准备一组高质量 eval。

这组 eval 要能代表真实生产用户行为。

否则脚手架跑得再顺，也只是在错误信号上优化。

Autoresearch 提醒我们，自动优化需要实验循环。

Better-Harness 补上了更难的一半——当评价信号错了，系统会沿着错误方向跑得更快。

所以 eval、trace、留出集、人工审核，这些看起来不智能的东西，才决定系统会往哪里变好。
