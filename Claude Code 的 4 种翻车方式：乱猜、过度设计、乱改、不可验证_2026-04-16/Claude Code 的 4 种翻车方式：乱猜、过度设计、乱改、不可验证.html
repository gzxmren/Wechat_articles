Claude Code 的 4 种翻车方式：乱猜、过度设计、乱改、不可验证

你让 Claude Code “帮我加个功能”，它写完了。

更现实的问题是：你敢不敢合并？你能不能快速验证？以后谁来维护？

andrej-karpathy-skills 这份 repo 的定位很明确：不教你“怎么提示词更聪明”，而是给 Claude Code 加一层工程护栏，让它默认按更稳的方式工作。

它核心就是一份 CLAUDE.md：把 Karpathy 提过的 LLM coding 常见坑，整理成 4 条“行为准则”。你把这份文件放进项目根目录（或用插件方式全局安装），Claude Code 在每次执行任务时都会读到这些规则。repo 里你真正会用到的东西主要有几块：

     •CLAUDE.md: 四条原则的“最终版规则文本”，适合直接丢进项目里

        • EXAMPLES.md: 配套对照：同一个需求，LLM 常见错误写法 vs 更稳的写法
        • skills/karpathy-guidelines/SKILL.md: 把同一套原则包装成 skill 形态，方便通过工具链复用
        • .claude-plugin/*: 插件/市场相关的元数据，用来支持 Claude Code 里“一键装到全局”

换句话说：这不是一段提示词，而是一套可落地的“默认行为配置”。

🧰 它给 Claude Code 立了哪 4 条规矩

repo 把护栏压缩成四句话，每一句都指向一个工程痛点：

  1. 1. Think Before Coding：别猜，先把不确定点说出来
  2. 2. Simplicity First：最小实现，别先造系统
  3. 3. Surgical Changes：只改必须改的，不要顺手重构
  4. 4. Goal-Driven Execution：写清成功标准，循环到“可验证完成”为止

下面的“4 种翻车方式”，其实就是这四条规矩分别在对抗什么。

🛠️ 5 分钟接入（两种方式）

你不需要把 repo 整套搬下来，选一种接入方式就够。

方式 A：Claude Code 插件（全局）

适合你经常在不同项目间切换，希望行为基线一致。

/plugin marketplace add forrestchang/andrej-karpathy-skills
/plugin install andrej-karpathy-skills@karpathy-skills

方式 B：项目内 CLAUDE.md（跟仓库走）

适合团队协作：规则跟着代码库走，review 也更有共识。

先打开 repo，进入 CLAUDE.md 文件页，点 Raw，复制它的原始地址（Raw URL）。

新项目下载：

curl -o CLAUDE.md "<RAW_URL>"

已有 CLAUDE.md 想合并（追加）：

echo "" >> CLAUDE.md
curl "<RAW_URL>" >> CLAUDE.md

接入只是把规矩“装上”。真正的变化会出现在你最容易失控的四个环节：需求不清先问、实现尽量小、改动范围变窄、交付必须可验证。

下面我用“4 种翻车方式”来对照这份 repo 的四条原则，你会更直观地看到它到底把 Claude Code 往哪个方向掰。

🧯 翻车 1：乱猜（Think Before Coding 在兜底）

典型表现：

  • • 你没说清的数据结构、接口格式、边界条件，它自己补完并开干
  • • 等你发现不对，代码结构已经围绕错误假设展开了

这份 repo 的要求很硬：不确定就明说，缺信息就问；有多种解释就列出来让你选，而不是默认替你拍板。

新人用起来最直接的收益是：错误更早暴露，返工更少。

🧱 翻车 2：过度设计（Simplicity First 在刹车）

典型表现：

  • • 你只要一个功能，它先搭“可扩展架构”：配置层、抽象层、通用接口
  • • PR 变大、review 变慢、后续维护更贵

repo 给出的原则是：只写你要的；一次性逻辑不要抽象；能 50 行写完就别写 200 行。

你可以把它当作一个“反过度工程化”的默认开关。

🧼 翻车 3：乱改（Surgical Changes 在控范围）

典型表现：

  • • 你要改 A，它顺手把 B 的风格、注释、目录结构也“优化”
  • • diff 噪音太多，你没法判断风险边界

repo 的要求是：只动必须动的行；看到历史遗留可以提出来，但不要顺手清理；只清理“自己造成的垃圾”。

对新人来说，这相当于把 PR 从“装修式改动”拉回“手术式改动”。

✅ 翻车 4：不可验证（Goal-Driven Execution 在收口）

典型表现：

  • • 它说“完成了”，但没有测试、没有检查项、没有可复现的验证步骤

repo 推的做法是：别告诉它“做什么”，告诉它“满足什么条件才算完成”。

  • • “修 bug” → “写一个能稳定复现的测试，然后修到测试通过”
  • • “加校验” → “写非法输入测试，修到测试通过”
  • • “重构” → “重构前后测试都绿，且 diff 只包含必要改动”

多步任务固定用这个格式，让它自己闭环：

1. [步骤] → verify: [怎么验证]
2. [步骤] → verify: [怎么验证]
3. [步骤] → verify: [怎么验证]

🧪 新人可直接复制的任务模板（配合这份 repo 最好用）

用“给接口加 email 校验”练手最合适：需求小，但很容易被写成大工程。

你可以把任务直接写成下面这样，让 Claude Code 按 repo 的四条规矩跑：

任务：创建用户接口增加 email 校验，非法 email 返回 400

必须先澄清（缺信息就问，不要猜）：
- 现有接口路径、返回格式是什么？
- 校验逻辑放在哪一层更符合现有项目：controller / service / middleware？
- 项目测试框架是什么？是否已有 API 测试基建？

约束：
- 只改动与该功能相关的文件
- 不做无关重构、不改代码风格
- 不引入新的校验框架（除非项目已在用）

成功标准：
1) 新增测试：非法 email 返回 400（verify：测试先失败）
2) 新增测试：合法 email 正常创建（verify：测试通过）
3) 最终 diff 中每一处改动都能追溯到“email 校验或测试”，没有顺手优化

再让它按计划执行并逐条验证：

计划：
1) 先写测试用例 → verify: 测试红
2) 做最小实现让测试变绿 → verify: 测试绿
3) 逐行自查 diff 是否只改必要部分 → verify: 无无关改动

📏 你怎么判断它真的生效

不用看它“解释得像不像”，看产物有没有变得更工程化：

  • • diff 噪音更少：无关改动减少
  • • 代码更小：最小实现优先
  • • 澄清更早：先问清楚再动手
  • • 收口更硬：成功标准可验证
